# 要件定義書: 競馬予想 X投稿バグ修正（モーニング/穴予想 単発投稿化）

## 1. 背景・問題

### 観測されている不具合

VPS本番（`/opt/keiba-unified/jra/`）の **モーニング予想 X投稿（`post_morning_to_x`）が3週連続で失敗**している。

```
詳細: {"detail":"You are not permitted to perform this action.",
       "type":"about:blank","title":"Forbidden","status":403}
スレッド N/9 投稿失敗 — 中断
```

- 失敗日: 2026-04-12 / 2026-04-19 / 2026-04-26（毎週土曜の朝7:00 cron）
- 投稿1〜3本目までは成功、**4本目以降の `in_reply_to_tweet_id` 連鎖reply で 403**
- 同じX認証情報を使う **直前予想 / 穴予想 の単発投稿は成功している**（4/25土の `live.log` で12件以上の `tweet_id` 取得確認済み）

### 推定される真因

- スレッド形式（reply_chain）で `time.sleep(1)` 間隔の連投が、X側の自動スパム/Bot抑制ロジックに該当
- 認証情報・API tier 制限ではない（同条件の単発投稿は通っている）

### オーナー判断

> 単発投稿に切り替えて、文字数に合わせて数レースごとにまとめる。穴予想も同様に。

## 2. ゴール

モーニング予想・穴予想の X投稿を、**reply_chain スレッドではなく単発ツイートを複数投稿する方式**（chunk分割）に変更し、403 失敗を解消する。

## 3. スコープ

### やること

- `keiba-unified/shared/x_poster.py` の以下を改修
  - `post_morning_to_x()` — スレッドreplyを廃止し、Geminiリライト結果を **280字以内に収まるchunkで分割 → それぞれ独立した単発投稿** へ変更
  - `post_longshot_to_x()` — 同じく長文時は chunk 分割（現状は短いので影響なし、長文時の防衛策として実装）
- `keiba-unified/jra/scripts/run_morning.py` の **穴予想ブロックに `post_longshot_to_x` 呼び出しを追加**（HANDOFF 記録のとおり、モーニングの穴予想だけ X未投稿だった件もまとめて修正）
- ローカル ⇄ VPS で乖離している以下のファイルを **VPS現行版へローカルを同期**（ローカルが古い）
  - `jra/scripts/run_morning.py`（VPS 677行 / ローカル 619行）
  - `jra/scripts/run_live.py`
  - `jra/scripts/longshot_wide_predictor.py`（ローカル欠落）
  - `jra/scripts/longshot_wide_tracker.py`（ローカル欠落）
  - `shared/x_poster.py`（差分確認の上、現行VPS版へ寄せる）
- VPSへ修正版をデプロイし、**ドライランで動作検証**（cron発火を待たず手動確認）

### やらないこと

- X DevPortal 側のApp再認証・トークン再生成（不要 — 認証情報は健全）
- スレッド形式そのものの再設計（あくまで単発化）
- 穴予想ロジック本体の修正（4/26 HANDOFF で言及されていた pkl/DB乖離の調査は別チケット）
- ローカル銘柄の git commit（このセッションでは修正＋VPSデプロイまで。commit は最後 `/handoff` で実行）

## 7. 想定リスクと回避策

| リスク | 対策 |
|------|------|
| 単発投稿でも連投スパム判定される | sleep間隔を 5〜10秒に長めに設定。失敗を許容する個別エラーハンドリング |
| chunk分割で意味的に途中で切れる | `MORNING_PROMPT` を「各レース1ブロック・「---」区切り」に維持し、行/区切り単位で chunk組み立て（途中切断回避） |
| 280字超えのchunk が発生 | 組み立て時に逐次バイト長チェック、超えたら強制改ページ |
| 重複コンテンツ判定 | 各chunk末尾に「(N/M)」のページ番号を付与する案（必要に応じて） |
| VPSへの転送中ファイル破損 | `scp` 後に `md5sum` で整合性確認、失敗時はバックアップから復旧 |
