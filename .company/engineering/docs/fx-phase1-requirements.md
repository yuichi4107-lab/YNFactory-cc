# 要件定義書: FX自動売買システム Phase 1 改善プロジェクト

**作成日**: 2026-04-12
**対象システム**: ai-trade-system（FXモジュール）
**ステータス**: ユーザー承認待ち

---

## ゴール

高勝率FX戦略を選定・実装・最適化し、USD/JPYおよびEUR/JPYにおいて「月利+2〜3%、勝率65%+、PF 1.8+、最大DD 10%以下、月5トレード以上」を満たす戦略を少なくとも1本特定して本番向け設定を確定すること。

### 北極星目標（Phase 2以降）

月利+10%（年率+214%複利）はPhase 2以降の挑戦目標として記録する。Phase 1では月利+2〜3%の達成を優先し、月利+10%への道筋（Phase 2計画案）を工程7の成果物に簡易記載する。

---

## スコープ

### やること

- 高勝率FX戦略のリサーチと実装候補4〜6本の選定
- USD/JPYおよびEUR/JPYの1h/4h/1dデータ（2年分以上）の取得・整備
- 選定戦略4〜6本のPythonモジュール実装（フィルター有無の両バリアント）
- グリッドサーチによるパラメータ最適化（Walk-Forward検証含む）
- 全戦略×全時間足×両通貨ペアのバックテスト実行
- 比較レポートおよびヒートマップの生成
- 上位3候補の選定と本番向け設定（strategy_config.json）の確定

### やらないこと

- Saxo本番取引口座での実運用開始（Phase 1はシミュレーション・バックテストまで）
- MT5やWindows専用ツールの利用
- ナンピン・マーチンゲール等の高リスク資金管理手法の採用
- 既存BTC/JPY自動売買（Coincheck本番）への変更・影響
- EUR/USDなど円絡み以外の通貨ペア
- Phase 2以降のポートフォリオ運用実装

## 前提条件・リスク・矛盾点の整理

### 前提

| # | 前提 | 影響する工程 |
|---|------|-------------|
| A | Saxo Sim Tokenの残り有効期間は約20時間（2026-04-12時点）。工程2はToken失効前に完了する必要がある | 工程2 |
| B | Saxo Chart API単発最大Countは通常1200。1hデータ2年分（約17,500本）は15回以上のページネーション取得が必要 | 工程2 |
| C | 現在のバックテストはGemini Vision API（チャート画像→パターン判定）方式。新戦略はシグナル計算ロジックをPythonで直接実装する（APIコストと速度の観点から） | 工程3 |
| D | バックテスト対象期間（2024-09〜2026-04）は円安・日米金利差が顕著な特殊相場。バックテスト結果は同期間に最適化されたバイアスを持つ可能性がある | 工程4/工程6 |
| E | 既存 `src/backtest/` にはrunner.py（Gemini方式）、multi_runner.py、optimizer.pyが存在する。新戦略はルールベースシグナルに切り替えるため既存コードとの住み分けを明確にする | 工程3/工程5 |

### リスク

| # | リスク | 対応方針 |
|---|--------|---------|
| R1 | Saxo Sim Token失効による工程2の中断 | 工程2を最優先で実行。Token失効時は再取得ガイドを用意 |
| R2 | 1h×2年分の取得中にAPIレート制限に抵触 | ページ間にsleep（推奨2秒）を挿入。失敗した範囲のみ再取得できる再開機能を実装 |
| R3 | 過学習（バックテスト期間の特殊相場に過適合） | Walk-Forward Analysis（前半学習/後半検証の分割）を工程4で必須とする |
| R4 | グリッドサーチの計算時間超過 | 1戦略あたり最大30分を上限。並列化（concurrent.futures or joblib）を活用 |
| R5 | 目標値（勝率65%+、PF1.8+）を達成する戦略が存在しない | 達成できなかった場合は最良候補とギャップを報告し、Phase 2計画に反映する |

### 矛盾点・確認事項

| # | 矛盾・曖昧さ | 本要件での解釈 |
|---|------------|--------------|
| M1 | 工程3で「既存run_fx_backtest.pyに追加」と記載されているが、該当ファイルが現在存在しない（src/backtest/にはrunner.pyとmulti_runner.pyのみ） | 新規に `src/backtest/fx_runner.py`（ルールベースFX専用バックテストエンジン）を作成し、新戦略モジュールはその中で呼び出す |
| M2 | 工程3の「strategiesサブディレクトリ」が現在存在しない | `src/backtest/strategies/` を新規作成し、各戦略を個別モジュールとして配置する |
| M3 | FXのスプレッドがfee_rateのみで表現されている（現在0.005%）。USD/JPYの実際のスプレッドは0.2〜0.5pipが一般的 | fee_rateの意味をスプレッド込みのコストとして再定義し、USD/JPYは0.002%（0.2pip相当）、EUR/JPYは0.003%（0.3pip相当）をデフォルトとする |
| M4 | 月利計算の基準が不明（全資金に対してか、使用証拠金に対してか） | バックテストでは「ポジション価値に対するPnL%の累積」を月次換算する。レバレッジは計算外（現物相当）とし、工程7で本番向けポジションサイズを別途定義する |

## 工程4: パラメータ最適化（グリッドサーチ）

### 入力

- 工程3の戦略実装（`src/backtest/strategies/*.py`）
- 工程2のOHLCVデータ（学習期間: 前半2/3を使用）
- 検証期間: 後半1/3（Walk-Forwardに使用）

### 出力

- `results/optimization/{strategy_id}/best_params.json`（全戦略分）
- `results/optimization/{strategy_id}/grid_search_results.csv`（全組み合わせスコア）
- `results/optimization/{strategy_id}/heatmap_{param1}_{param2}.png`（主要2パラメータのヒートマップ）
- `results/optimization/optimization_summary.json`（全戦略の最優秀パラメータ一覧）

### パラメータ空間の定義ガイドライン

各戦略で以下のパラメータを最低限探索する:
- TP: 0.001〜0.010（4〜8点）
- SL: 0.001〜0.008（4〜8点）
- hold_bars: 3〜20（4〜6点）
- エントリー閾値（戦略固有のパラメータ）

### 評価関数

```
score = 勝率 × 0.3 + PF × 0.3 + 月利 × 0.3 + (1 - DD/10) × 0.1
```
ただし DD > 10% の組み合わせは失格（スコア=0）

### 完了条件

- [ ] 全選定戦略に対して `best_params.json` が存在すること
- [ ] 各戦略のグリッドサーチがUSDJPY 1hデータで実行されていること
- [ ] Walk-Forward検証が実施され、学習期間と検証期間のスコア差が記録されていること
- [ ] 過学習指標として「学習スコア / 検証スコアの比率」が `best_params.json` に含まれていること（比率 > 2.0 の場合は警告フラグを立てる）
- [ ] 1戦略あたりの実行時間が30分以内であること（並列化で対応）
- [ ] ヒートマップ画像が主要2パラメータ組み合わせで生成されていること
- [ ] 機械可読なJSONフォーマットで最適パラメータが保存されていること

## 全体の成功判定基準

### Phase 1 合格条件（最低基準）

以下を**すべて同時に**満たす戦略が少なくとも1本存在すること:

| 指標 | 最低基準 | 目標 |
|------|---------|------|
| 勝率 | 65%以上 | 70%以上 |
| プロフィットファクター | 1.8以上 | 2.0以上 |
| 月利（バックテスト） | +2%以上 | +3%以上 |
| 最大ドローダウン | 10%以下 | 7%以下 |
| 月あたりトレード数 | 5件以上 | 10件以上 |
| バックテストトレード総数 | 100件以上 | 150件以上 |

### Phase 1 不合格時の対応

上記基準を満たす戦略が存在しない場合:
1. 最良候補とギャップ（不足指標・乖離幅）をオーナーに提示
2. Phase 2計画の前倒しまたは範囲拡大（他通貨ペア、ML系戦略）を検討
3. 月利+10%の北極星目標は維持しつつPhase 1ターゲットを再設定
