# 症状
- `check_results.py` の結果取得で `_build_jra_result_cname_map()` → `_build_jra_cname_map(target_date)` が **0件** を返す。
- ログ（`data/logs/results.log`）に `0レース分の結果CNAMEを取得` が出力され、JRA公式からの着順取得が全レース失敗。
- 2026-04-04 までは `OK (JRA)` で正常取得できていた → **6/6・6/7で回帰**。

# 切り分け
- `_build_jra_cname_map` は JRA公式の「今週のレース」ページ
  `https://www.jra.go.jp/keiba/thisweek/{YYYY}/{MMDD}_{idx}/race.html` を起点にCNAMEを収集する。
- 本番VPS(163.44.101.31)から実HTTP確認:
  - `https://www.jra.go.jp/keiba/thisweek/2026/0606_1..3/race.html` → **全て HTTP 403**（本文56,039byteのブロックページ、dde01リンク0件）。
  - `0607` 各idxも同様に 403。
- → JRA公式 thisweek 配下が **403でブロック**されているため、起点CNAMEが1件も取れず全体が0件になる。

# 根本原因（推定）
- JRA側のbot対策強化で、データセンターIP（ConoHa VPS）またはUA/アクセスパターンに対し
  thisweek 配下が 403 を返すようになった可能性が高い。
- JRAトップ等は200が返る場合があり「IP完全BAN」とは限らない（thisweek配下のみブロック or URL構造変更の可能性も残る）。**未確定**: 「IPブロック」か「URL構造変更」かはこの時点で断定していない。

# 適用した回避策（恒久フォールバック）
- `scraper_legacy.py` に `scrape_result_live_netkeiba(race_id, conn)` を追加し、
  当日掲載が早い **`race.netkeiba.com/race/result.html`（EUC-JP・`ResultTableWrap`/`Payout_Detail_Table`）** から着順＋払戻を取得。
- `check_results.py scrape_day_results()` の取得順を **JRA公式 → 当日ライブnetkeiba → db.netkeiba(履歴)** に変更。
- これにより JRA公式が403でも当日中に結果照合が成立（6/7はライブで23/23取得）。**実害は解消**。

# 恒久対応の選択肢（別チケット）
1. JRA thisweek 403 の原因を確定（別UA/Referer/Cookie/セッション、または別IP/プロキシ経由でのアクセス可否を検証）。
2. もしくは JRA公式パスを廃し、当日ライブnetkeibaを正規ルート化（db.netkeibaは過去日バックフィル専用に降格）。
3. URL構造変更の可能性確認（JRAサイトの thisweek パス仕様が変わっていないか）。
