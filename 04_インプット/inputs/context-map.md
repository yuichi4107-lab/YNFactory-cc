# Context Map

## 1. 定義

このワークスペースにおける「コンテキスト」とは、AI・秘書・CEO・各部署が作業判断を行うための前提情報全体である。

コンテキストは、作業ごとに都合よく切り出す「今回使う情報」ではない。常に存在する判断体系であり、各作業ではその体系のどの層に関係するかを見極めて参照する。

TODOはコンテキストそのものではない。TODOは、コンテキストから導かれる実行キューである。

## 2. コンテキストの階層

### 2.1 恒久コンテキスト

長期的に変わりにくい判断前提。

- 事業方針
- 価値観
- 品質基準
- 禁止事項
- ユーザーの好み
- スキル運用方針
- 自動化・仕組み化への基本姿勢

主な参照先:

- ルートの `AGENTS.md`
- `.company/AGENTS.md`
- `.company/inputs/persona_profile.md`
- 各スキルの `SKILL.md`
- 明示的に保存された運用ルール

### 2.2 構造コンテキスト

会社組織とファイル配置に関する前提。

- `.company/` の構造
- 秘書・CEO・部署の役割
- 成果物の保存場所
- inbox / todos / notes / outputs / context の使い分け
- handoff と日別TODOの位置づけ

主な参照先:

- `.company/AGENTS.md`
- `.company/secretary/AGENTS.md`
- `.company/secretary/HANDOFF.md`
- `.company/secretary/todos/`
- `.company/inputs/CLAUDE.md`

### 2.3 プロジェクトコンテキスト

個別プロジェクトの目的・状態・成果物に関する前提。

- プロジェクトの目的
- 現在の進捗
- 完了済み成果物
- 未完了事項
- 判断待ち事項
- 品質チェック結果
- 次工程へ進む条件

主な参照先:

- 各プロジェクト配下の `README.md`
- `FINAL_HANDOFF.md`
- `progress.json`
- `quality_check.json`
- `KDP出版用/`
- `draft-status.md`
- プロジェクト固有の要件定義書

### 2.4 短期コンテキスト

直近の実行判断に使う情報。

- 今日の会話
- ユーザーの最新指示
- 今日の日付・曜日
- 今日のTODO
- 現在の作業対象
- 直近のブロッカー

主な参照先:

- 現在の会話
- `.company/secretary/todos/YYYY-MM-DD.md`
- 直近に更新された作業ファイル

### 2.5 証拠コンテキスト

実際に確認済みであることを示す根拠。

- 読んだファイル
- 実行したコマンド
- 検証結果
- QCスコア
- 生成物の存在確認
- エラー内容
- 実測した日時

証拠コンテキストは、報告や引き継ぎで最も重要な根拠になる。推測と確認済み事実を混ぜない。

## 3. 情報源ごとの役割

### 3.1 `AGENTS.md`

最上位の運用ルール。作業手順、品質ループ、出力制限、参照順序などを定める。

### 3.2 `.company/inputs/`

外部から取得・記録した一次情報、参考情報、素材情報を格納する場所。

このフォルダは旧称 `.company/context/` だが、実体はコンテキストそのものではなく「インプット」である。

`.company/inputs/CLAUDE.md` で定義されている通り、このフォルダは会話記録、参考資料、競合情報、クライアント資料、その他の外部情報を置く場所である。

この `context-map.md` は、同フォルダ内の情報を含め、ワークスペース全体のコンテキストをどう扱うかを定義する地図である。

Limitless などから取り込まれる会話記録には、予定、約束、思いつき、作業依頼、TODO候補が含まれることがある。これらはインプットとして保存された時点では未整理の材料だが、抽出・確認・既存コンテキストとの照合を経ることで、短期コンテキストや日別TODOに反映される。

インプットは原本のまま保存するだけでは活用しにくい。原本は保持しつつ、重要な内容は抽出・要約・タグ付けして整理済みインプットとして保存する。

保存の考え方:

1. `conversations/`、`references/`、`clients/` などに原本または取得情報を残す
2. `organized/` に要約、決定事項、TODO候補、人物情報、プロジェクト関連メモなどの整理版を残す
3. `indexes/` に人物、プロジェクト、予定、決定事項などの横断索引を残す
4. 整理済みインプットを、短期コンテキスト、プロジェクトコンテキスト、恒久コンテキストへ必要に応じて反映する

流れ:

1. `.company/inputs/conversations/` に会話記録を保存する
2. `extract_insights.py` などで予定・タスク・判断材料を抽出する
3. `.company/inputs/organized/` に整理済みインプットとして保存する
4. 必要に応じて `.company/secretary/inbox/` に候補として送る
5. `HANDOFF.md`、既存プロジェクト状態、ユーザーの最新指示と照合する
6. 今日実行すべきものだけを `.company/secretary/todos/YYYY-MM-DD.md` に反映する

この流れにより、インプットは短期的な予定やTODOにも影響する。ただし、インプット内の発話やメモをそのままTODO化せず、確認と優先順位付けを通して実行キューへ落とす。

### 3.3 `.company/secretary/HANDOFF.md`

セッション間の作業状態を引き継ぐためのファイル。

役割:

- 進行中作業の状態を残す
- 前回どこまで進んだかを示す
- 次回の再開点を示す
- ブロッカーや注意点を残す

HANDOFFは重要だが、すべての判断の中心ではない。個別プロジェクトの最新成果物と矛盾する場合は、実ファイルを確認する。

### 3.4 `.company/secretary/todos/`

日別の実行キュー。

役割:

- 今日やることを整理する
- 優先順位の暫定表示をする
- 完了・未完了を日次で記録する

TODOは判断体系の入口ではない。TODOは、恒久・構造・プロジェクト・短期コンテキストを踏まえて生成・更新される実行リストである。

Limitless由来の会話記録や外部インプットから抽出されたTODO候補は、短期コンテキストとして扱う。日別TODOへ反映する前に、重複、完了済み、既存プロジェクトとの関係、今日実行すべき優先度を確認する。

### 3.5 長期メモリ

過去の判断、ユーザーの好み、失敗回避策を再利用するための索引。

役割:

- 以前の決定を思い出す
- 関連ファイルや過去作業を探す
- ユーザーの好みや禁止事項を再利用する
- 同じ失敗を避ける

長期メモリは最終事実ではない。現行ファイルと矛盾した場合は、現行ファイルを優先する。

## 4. 優先順位と矛盾解決

複数の情報源が矛盾した場合は、次の順で優先する。

1. ユーザーの最新指示
2. ルートの `AGENTS.md`
3. 対象プロジェクト内の最新ファイル
4. `.company/inputs/context-map.md`
5. `.company/secretary/HANDOFF.md`
6. 日別TODO
7. 長期メモリ
8. 過去会話の要約

判断ルール:

- ユーザーの最新指示が最優先。
- メモリは古くなるため、現行ファイルで確認できることは現行ファイルを優先する。
- TODOに残っていても、成果物やユーザー指示で完了が確認できる場合はTODOを更新する。
- HANDOFFが古い場合は、対象プロジェクトの実ファイルを確認する。
- 日付・曜日は推測せず、ツールで確認する。

## 5. TODOの位置づけ

TODOは「今日の実行キュー」であり、コンテキストの中心ではない。

TODOに書くべきもの:

- 今日実行する作業
- 優先度
- 完了状態
- 短い補足

TODOに書きすぎないもの:

- 事業方針
- 長期ルール
- プロジェクト全履歴
- 詳細な要件定義
- 品質基準の全文

TODOは、他のコンテキストから導かれる結果として更新する。TODOから全体像を逆算しない。

## 6. メモリの位置づけ

メモリは、ワークスペース外にある長期索引である。

使うべき場面:

- 過去の判断やユーザーの好みが関係する
- 以前の失敗を避けたい
- プロジェクトの継続経緯が不明
- 似た作業の前例を確認したい

使い方:

- まず関連キーワードでメモリを探す
- メモリを根拠にしすぎず、現行ファイルで確認する
- メモリ由来の情報は、必要に応じて「過去メモリ上の情報」と明示する
- メモリ更新は、ユーザーが明示した場合のみ行う

## 7. 作業開始時の判断手順

作業開始時は、TODOを中心に置かない。まず依頼がどの層に関係するかを判定する。

基本手順:

1. ユーザーの依頼内容を読む
2. 関係するコンテキスト層を判定する
3. 必要な情報源だけを確認する
4. 日付・曜日が関係する場合はツールで確認する
5. `AGENTS.md` やスキルの必須手順がある場合は従う
6. 実作業が必要な場合は、要件定義から始める

例:

- 会社運営やTODO相談: 構造コンテキスト、短期コンテキスト、必要に応じてプロジェクトコンテキスト
- 電子書籍やマンガ制作: プロジェクトコンテキスト、証拠コンテキスト、該当スキル
- note運用: プロジェクトコンテキスト、アカウント履歴、過去記事、ブラウザ状態
- ルール設計: 恒久コンテキスト、構造コンテキスト、既存ルール

## 8. 作業終了時の更新手順

作業終了時は、更新先を分ける。

### 8.1 作業状態

セッション間で引き継ぐべき作業状態は `.company/secretary/HANDOFF.md` に残す。

### 8.2 実行予定

今日や次回の具体的な実行予定は `.company/secretary/todos/YYYY-MM-DD.md` に残す。

### 8.3 判断ルール

再利用すべき運用ルールは、該当するルールファイルに残す。

例:

- コンテキスト運用: `.company/inputs/context-map.md`
- 会社運営: `.company/AGENTS.md`
- 秘書運用: `.company/secretary/AGENTS.md`
- スキル運用: 各 `SKILL.md`

### 8.4 長期メモリ

長期メモリは、ユーザーが明示した場合のみ更新する。

## 9. 禁止する運用

- TODOをコンテキスト全体の中心として扱う
- 「今回使うコンテキスト」という表現で、作業ごとに都合よく文脈を切り出す
- メモリだけを根拠にして現行ファイルを確認しない
- HANDOFFが古い可能性を無視する
- 日付・曜日を推測する
- 実際に読んでいないファイルを読んだように扱う
- 長いファイルやログを無制限に出力する
- プロジェクト固有の最新成果物より古い要約を優先する

## 10. 運用メモ

このファイルは、コンテキスト運用の地図である。個別作業の詳細手順ではない。

具体的な作業では、この地図に従って関係する層を見極め、必要なファイルだけを確認する。確認した情報は、報告時に必要十分な範囲で明示する。
