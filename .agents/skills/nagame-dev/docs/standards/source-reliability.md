# 情報源信頼度分類

本ドキュメントは nagame-dev のリサーチフェーズで取得する情報の信頼度分類と、
各信頼度レベルの情報をどのように扱うかを定義する。

---

## 1. 4段階信頼度分類

| レベル | 定義 | 例 | 意思決定への使用 |
|---|---|---|---|
| **A** | 公式ドキュメント、利用規約、標準文書、一次ソース | API公式リファレンス、IEEE/ISO規格文書、利用規約ページ、公式Changelog、RFC文書、法令原文 | 確定根拠として単独使用可 |
| **B** | 公式に近い技術記事、メンテされたOSS、著名な技術資料 | 公式ブログ記事、有名OSSのREADME/Wiki、著名エンジニアの技術記事、カンファレンス発表資料、公式チュートリアル | 複数一致で確定根拠として使用可 |
| **C** | 個人ブログ、SNS、動画、コミュニティ投稿 | note記事、Qiita、Zenn、X投稿、YouTube解説動画、Redditスレッド、Stack Overflow回答 | 実務知見として参考。重要判断の根拠には使わない |
| **D** | 出所不明、古い情報、再現性不明 | 更新日不明のブログ、2年以上前のStack Overflow回答、匿名掲示板、ChatGPT等の生成AI出力そのもの | 参考扱い。意思決定への使用を禁止 |

### 信頼度判定のフローチャート

```
情報を取得した
  ├── 公式サイトのドキュメントか？ → Yes → レベルA
  ├── 公式ブログまたは著名OSSか？ → Yes → レベルB
  ├── 個人ブログ・SNS・コミュニティか？ → Yes → レベルC
  └── 出所不明・古い・再現性不明か？ → Yes → レベルD
```

### 「著名」の判断基準（レベルBの境界）

| 判断基準 | 具体例 |
|---|---|
| 著者がフレームワーク/ライブラリのコアコントリビューター | Next.js の Vercel 社員のブログ |
| 著者が当該技術の書籍の著者 | O'Reilly 等の技術書著者 |
| 記事が公式ドキュメントからリンクされている | 公式Docs内のリンク先記事 |
| GitHub Stars 1,000以上のOSSのREADME | 広くメンテされていることの指標 |
| カンファレンス（PyCon, JSConf等）の公式発表資料 | 査読プロセスを経た発表 |

## 2. リサーチ優先度分類

| 優先度 | 定義 | 扱い | 未解決時の影響 |
|---|---|---|---|
| **Blocker** | 調べないと実装可否・規約違反リスクを判断できない | 最優先で調査。未解決ならPhase進行禁止 | Phase進行が停止する |
| **Must** | 要件定義・仕様・設計に必須の情報 | V1リサーチで必ず調査 | 要件の品質が担保できない |
| **Should** | 品質を上げるために重要な情報 | V2リサーチで調査 | 品質は下がるが進行は可能 |
| **Later** | 後続フェーズで調べれば十分な情報 | 記録のみ。実装フェーズ以降で調査 | 当面の進行に影響なし |

### 優先度の判定基準

| 判定質問 | はい→ | いいえ→ |
|---|---|---|
| これが分からないと、実装できるかどうか判断できないか？ | Blocker | 次の質問へ |
| これが分からないと、要件定義・仕様書が書けないか？ | Must | 次の質問へ |
| これが分かると、設計品質が上がるか？ | Should | Later |

## 3. 使用ルール

### 信頼度と意思決定の対応表

| 意思決定の種類 | 必要な最低信頼度 | 理由 |
|---|---|---|
| Must要件の判断 | A（単独）または B（2件以上一致） | Must要件は全体の基盤。不確かな根拠で建てると崩壊する |
| 外部API/規約の判断 | A のみ | 規約違反はサービス停止・法的リスクに直結する |
| Should要件の判断 | B 以上 | Should要件は品質向上。一定の信頼性があれば採用可 |
| Could要件の判断 | C 以上 | 優先度が低いため、参考情報でも十分 |
| 技術選定の判断 | B 以上（2件以上推奨） | 技術選定の誤りは手戻りコストが大きい |
| セキュリティ判断 | A のみ | セキュリティは推測で判断してはならない |

### 禁止事項

| 禁止事項 | 理由 |
|---|---|
| 信頼度Dの情報で設計判断を下す | 出所不明の情報は検証不能であり、判断の根拠にならない |
| 信頼度C/Dのみを根拠にMust要件を設定する | 黄金ルール#1違反。Must要件には信頼度Aの根拠が必要 |
| 信頼度を付記せずにリサーチ結果を記録する | 後工程で根拠の信頼性を評価できなくなる |
| 古い情報（2年以上前）を現在も有効として扱う | API仕様・規約・ベストプラクティスは変化する |

## 4. リサーチ結果の記録形式

リサーチで取得した全ての情報は以下の形式で記録する。

```markdown
### [リサーチ項目名]

- **情報源**: [URL または ドキュメント名]
- **信頼度**: A / B / C / D
- **取得日**: YYYY-MM-DD
- **優先度**: Blocker / Must / Should / Later
- **要約**: [取得した情報の要約]
- **判断への影響**: [この情報が要件・設計にどう影響するか]
- **鮮度確認**: [情報の公開日・最終更新日]
```

## 5. 信頼度の格上げ・格下げ

### 格上げ条件

| 元レベル | 格上げ先 | 条件 |
|---|---|---|
| B → A相当 | なし | Bは公式同等にはならない。ただし3件以上のB情報が完全一致すれば「確定的」とみなす |
| C → B相当 | なし | Cの情報がBレベルの情報源から裏付けられた場合、B情報として再記録する |
| D → C | なし | 原則格上げ不可。出所が判明した場合のみ再分類 |

### 格下げ条件

| 元レベル | 格下げ先 | 条件 |
|---|---|---|
| A → B | 公式ドキュメントが「非推奨」「旧バージョン」と明記された場合 |
| B → C | 著者が当該技術から離れた、またはリポジトリがアーカイブされた場合 |
| 任意 → D | 情報の公開日から2年以上経過し、現在も有効か確認できない場合 |

## 6. 外部API調査の特別ルール

外部APIの判断は全て信頼度Aの情報に基づくこと。以下の項目は公式ドキュメントからのみ取得する。

| 確認項目 | 確認先（信頼度A） | NG例（信頼度C/D） |
|---|---|---|
| APIの認証方式 | 公式APIリファレンス | ブログ記事の「この方法で動いた」 |
| Rate Limit | 公式ドキュメントのRate Limitページ | Stack Overflowの「たぶんN回/分」 |
| 利用規約・禁止事項 | 公式Terms of Service | 個人ブログの「規約的にOKだと思う」 |
| 料金体系 | 公式Pricingページ | 古い比較記事の料金表 |
| 廃止予定・非推奨 | 公式Changelog/Migration Guide | TwitterでのAPI担当者の発言 |

---

## 7. 信頼度の表示記法

ドキュメント内で信頼度を参照する場合、以下の記法を使う。

- 本文中: `[信頼度A]` `[信頼度B]` `[信頼度C]` `[信頼度D]`
- Evidence Matrix内: `EV-001 [A]` のようにID末尾にレベルを付記
- リサーチログ内: 各エントリに `信頼度: A` フィールドを必須で記載
