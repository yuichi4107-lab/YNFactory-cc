# 5つのハーネス設計原則

walkinglabs 方法論に基づく、ハーネス設計の不変原則。
全ての判断に迷ったらこの5原則に立ち戻る。

---

## 原則 1: すべての指示はファイルに書く

### 原則本文
会話に残してはならない。Claude Code はセッション間で会話を忘れるため、指示がファイルにないと消滅する。

### なぜ必要か
Claude Code は新しいセッションを開始すると、前回の会話内容を一切記憶していない。
「前に言ったよね」は通用しない。唯一の永続記憶はファイルシステム上のファイルだけ。
会話で合意した内容がファイルに書かれていなければ、次のセッションでは存在しなかったことと同じになる。

### 違反するとどうなるか
- 次のセッションで同じ指示を繰り返す羽目になる
- 「前回決めたはずの仕様」が無視される
- セッションが進むほど品質が劣化する（記憶喪失の蓄積）

### 具体的な実践方法
- 会話で何かを決めたら、その場で該当ファイルに反映する
- PROGRESS.md にセッションごとの決定事項を記録する
- 「あとで書く」は禁止。決定した瞬間に書く
- 対象ファイル: CLAUDE.md / CONSTRAINTS.md / SRS.md / SDD.md / PROGRESS.md

## 原則 2: 禁止事項を先に書く

### 原則本文
許可より禁止が先。「やってよいこと」より「やってはいけないこと」を先に定義する。
禁止されていないことは全て試みられるという前提で設計する。

### なぜ必要か
AI は「やってよいこと」のリストを渡されると、リストにないことも「禁止されていないから」と解釈して実行する。
人間のチームでも同じだが、AI は特にこの傾向が強い。
「やるな」と明示されていないことは「やってもいい」と判断される。

### 違反するとどうなるか
- テストを通すためにテストコードを書き換える（テスト改ざん）
- SRS にない機能を「便利だから」と勝手に追加する（スコープクリープ）
- 本番データベースに直接クエリを投げる（データ破壊）
- force push で履歴を消す（変更履歴の消失）

### 具体的な実践方法
- CONSTRAINTS.md を SRS.md より先に書く（または同時に書く）
- 新しいプロジェクトでは、過去の failure_patterns.md から禁止事項を自動生成する
- 禁止事項には必ず理由（FP-XXX番号）を付ける
- 「やるなリスト」は CLAUDE.md の PART D に集約する
- 禁止の表現: 「〇〇してはならない」（曖昧な「〇〇に注意する」は禁止の表現として不可）

## 原則 3: スコープを「制約」として定義する

### 原則本文
「やること一覧」ではなく「これ以外はやってはならない境界線」として定義する。
IN SCOPE / OUT OF SCOPE / DEFER の3分類を使う。

### なぜ必要か
「やること一覧」だけだと、一覧にない作業を「暗黙的に含まれている」と拡大解釈される。
「これ以外やるな」という境界線で囲むことで、拡大解釈を物理的に防ぐ。

3分類の意味:
- **IN SCOPE**: 今回のプロジェクトで必ず実装する
- **OUT OF SCOPE**: 今回は絶対に手を付けない（将来もやらない可能性あり）
- **DEFER**: 今回はやらないが、将来やる予定（次フェーズ等）

### 違反するとどうなるか
- スコープクリープ（範囲が際限なく広がる）
- 本来やるべきことが後回しになる
- 「これもやっておきました」が品質劣化の原因になる
- デッドラインを守れなくなる

### 具体的な実践方法
- SRS.md の冒頭に IN SCOPE / OUT OF SCOPE / DEFER セクションを置く
- 各機能要件（FR-XXX）に対して明示的に分類する
- 「あったら便利」は DEFER に入れる（IN SCOPE に入れない）
- セッション中に新しい要件が出たら、まずスコープ分類してから対応を決める

## 原則 4: 完了条件を実装前に書く

### 原則本文
後付けの完了判定は甘くなる。実装前に DoD（Definition of Done）を定義し、全項目チェックされるまで「完了」と言わない。

### なぜ必要か
実装した後に「何をもって完了とするか」を考えると、実装の現状に合わせて基準を緩める心理が働く。
「テストは書いたけどカバレッジは低い」→「まあ動いてるからOK」→ 品質崩壊。
実装前に完了条件を決めておけば、基準を下げる誘惑がない。

### 違反するとどうなるか
- 「動いたから完了」という甘い判定
- テストカバレッジが不十分なままリリース
- セキュリティチェックの漏れ
- スペックドリフト（仕様と実装のずれ）の見落とし

### 具体的な実践方法
- CLAUDE.md の PART B に DoD を定義する（7項目チェックリスト）
- SRS.md の各機能要件に受入条件（Given-When-Then形式）を書く
- TEST_PLAN.md を SRS.md と同時に書く（実装前に）
- 「完了」宣言前に SD-02（実装後検証）を必ず実行する
- DoD の全項目がチェックされていない状態で「完了」と言ってはならない

## 原則 5: 1セッション1フェーズ（欲張らない）

### 原則本文
コンテキスト枯渇を防ぐ。1回のセッションで複数フェーズを進めようとすると品質が落ちる。

### なぜ必要か
Claude Code のセッションには実質的なコンテキスト容量の限界がある（50往復目安）。
1セッションで「SRS作成 → SDD作成 → 実装」と詰め込むと:
- 後半で前半の指示を忘れる（コンテキスト枯渇）
- 設計の一貫性が失われる
- エラーが蓄積して修正コストが増大する

### 違反するとどうなるか
- セッション後半で初期の制約を忘れる
- SRS と実装が矛盾する（スペックドリフト）
- 「さっき言ったはず」が通じなくなる
- 品質の段階的劣化（最後のほうが雑になる）

### 具体的な実践方法
- フェーズ別セッション数の目安:
  | フェーズ | 推奨セッション数 |
  |---|---|
  | Phase 0 (取り込み) | 1 |
  | Phase 1 (リサーチ) | 1-2 |
  | Phase 2 (SRS) | 1-2 |
  | Phase 3 (SDD) | 1-2 |
  | Phase 4 (テスト/ハーネス) | 1 |
  | Phase 5 (レビュー) | 1-2 |
  | Phase 6 (実装) | 2-5 |
  | Phase 7 (検証) | 1 |
  | Phase 8 (移行) | 1 |
- 50往復に達したら強制的にセッション切替（→ session-mgmt.md 参照）
- セッション切替時に必ず PROGRESS.md を更新する
- 「もう少しだから」と50往復を超えない（例外なし）

---

## 5原則の優先順位

迷ったときの判断基準:

1. **原則2（禁止事項優先）** — 最優先。禁止されていることは絶対にやらない
2. **原則4（完了条件先行）** — 基準なしに進めない
3. **原則1（ファイルに書く）** — 口頭合意は無効
4. **原則3（スコープ制約）** — 範囲外に手を出さない
5. **原則5（1セッション1フェーズ）** — 無理に詰め込まない

- [ ] 今回のセッションで扱うフェーズは1つだけか（原則5）
