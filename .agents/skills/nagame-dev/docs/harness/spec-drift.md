# スペックドリフト検出

仕様書（SRS/SDD）と実装の乖離を検出する3つのプロンプト。
ドリフトを放置すると「仕様書は飾り、実装が真実」という状態に陥る。

---

## スペックドリフトとは

仕様書（SRS/SDD）に書かれている内容と、実際の実装が食い違っている状態。
最初は小さなずれだが、放置すると雪だるま式に広がり、最終的に仕様書が信頼できなくなる。

**例え話**: 建築の設計図と実際の建物が違っている状態。「この部屋は3m幅のはず」→ 実際は2.5m。
小さなずれでも積み重なると、最後に家具が入らない、配管が通らない、といった致命的問題になる。

---

## SD-01: 定期チェック（週1回実行）

**目的**: SRS、SDD、CLAUDE.md と実装コードの全体的な整合性を確認する。

**実行タイミング**: 毎週1回（セッション開始時に前回チェックから1週間経っていたら実行）

**チェック項目**:

### 1. SRS の機能要件と実装コードの一致確認
- SRS に記載された全 FR-XXX について:
  - 対応する実装コードが存在するか
  - 実装が要件の意図と合致しているか
  - IN SCOPE の機能が全て実装されているか
  - OUT OF SCOPE / DEFER の機能が実装されていないか（スコープクリープ検出）

### 2. SDD のアーキテクチャと実際のディレクトリ構成の照合
- SDD に記載されたモジュール構成と、実際のディレクトリ・ファイル構成が一致しているか
- SDD に記載された依存関係と、実際の import/require が一致しているか
- SDD に記載されたデータフローと、実際の処理フローが一致しているか

### 3. CLAUDE.md の禁止事項が守られているか
- PART D（絶対禁止事項）の各項目について違反がないか
- CONSTRAINTS.md の全 C-XXX が守られているか

### 4. 技術スタック・バージョンの整合
- SDD に記載された技術スタックと、package.json / requirements.txt 等が一致しているか

**出力形式（ドリフトレポート）**:

```markdown
## SD-01 ドリフトレポート [YYYY-MM-DD]

### 深刻度 HIGH のドリフト
- [DR-001] FR-003 の認証機能が未実装（SRS では Must）
- [DR-002] SDD のモジュール構成と実際のディレクトリが不一致（auth/ が存在しない）

### 深刻度 MEDIUM のドリフト
- [DR-003] FR-007 の実装が SRS の受入条件と部分的に不一致

### 深刻度 LOW のドリフト
- [DR-004] SDD 記載のログレベルと実装のログレベルが異なる

### ドリフトなし
- FR-001, FR-002, FR-004, FR-005, FR-006: 一致確認済
```

**アクション判定**:
| 深刻度 | アクション |
|---|---|
| HIGH | **Red ゲート発動**: 実装を一時停止。ドリフト解消（仕様修正 or 実装修正）を最優先 |
| MEDIUM | **Yellow 警告**: 次セッションまでに解消計画を立てる |
| LOW | **記録のみ**: PROGRESS.md に記載し、適切なタイミングで対処 |

## SD-02: 実装後検証（実装完了時に実行）

**目的**: SRS の受入条件（Acceptance Criteria）を1件ずつ検証する。

**実行タイミング**: 機能実装の完了を宣言する前（DoD チェックの一部）

**チェック手順**:

### 1. 受入条件マトリクスの作成
SRS の全 FR-XXX について、Given-When-Then 形式の受入条件を1件ずつ検証する。

```markdown
## SD-02 受入条件検証マトリクス [YYYY-MM-DD]

| 要件ID | 受入条件 | 検証方法 | 結果 |
|---|---|---|---|
| FR-001-AC1 | Given: ユーザーが未ログイン / When: ログインフォーム送信 / Then: トークン発行 | E2Eテスト auth.test.ts#L12 | PASS |
| FR-001-AC2 | Given: 無効な認証情報 / When: ログインフォーム送信 / Then: エラーメッセージ表示 | E2Eテスト auth.test.ts#L28 | PASS |
| FR-002-AC1 | Given: ログイン済 / When: プロフィール編集 / Then: DB更新 | 単体テスト profile.test.ts#L15 | FAIL |
```

### 2. PASS/FAIL の判定基準
- **PASS**: 受入条件の Given-When-Then が全て実装され、テストが通過している
- **FAIL**: 受入条件が未実装、または実装がテストに失敗している
- **SKIP**: 受入条件が DEFER に分類されている（今回は検証対象外）

### 3. テストとの整合確認
- 受入条件ごとに「どのテストがこの条件を検証しているか」を紐付ける
- テストが存在しない受入条件は自動的に FAIL
- テストが受入条件の意図と異なるものを検証している場合も FAIL

**アクション判定**:
- FAIL が1件でもある → 「完了」宣言不可。FAIL を解消してから再検証
- 全 PASS → DoD の次の項目へ進む

## SD-03: テスト改ざん検出（テスト変更時に実行）

**目的**: テストコードの不正な変更（テストを通すためにテストを変える行為）を検出する。

**実行タイミング**: テストファイルに変更が加えられたとき（git diff で検出）

**検出項目**:

### 1. テストファイルの削除検出
- `tests/` または `__tests__/` 配下のファイルが削除されていないか
- 削除されている場合 → **即座に Red ゲート発動**

### 2. テストの無効化検出
以下のパターンを検出する:
- `@skip` / `@pending` / `.skip()` / `xit(` / `xdescribe(` の追加
- `// TODO: fix later` 等のコメントアウトによる無効化
- テスト関数の中身を空にする（`pass` / `return` だけにする）

### 3. assertion（期待値）の変更検出
特に危険なパターン:
- `expect(result).toBe(200)` → `expect(result).toBe(500)` のような期待値の書き換え
- `assertEqual(count, 10)` → `assertEqual(count, 0)` のような基準の緩和
- assertion の削除（テスト関数はあるが assert がない）

### 4. テストカバレッジの低下検出
- 前回のカバレッジ数値と比較して低下していないか
- 低下している場合 → 原因を特定（テスト削除? コード追加でカバレッジ希釈?）

**出力形式（テスト整合性レポート）**:

```markdown
## SD-03 テスト整合性レポート [YYYY-MM-DD]

### 改ざん検出
- [TI-001] tests/auth.test.ts: assertion 変更（expect(status).toBe(200) → toBe(500)）
- [TI-002] tests/profile.test.ts: @skip 追加（3テスト無効化）

### カバレッジ変動
- 前回: 85% → 今回: 72% (13%低下)
- 原因: tests/profile.test.ts の3テスト無効化

### 結論: 改ざんあり → Red ゲート発動
```

**アクション判定**:
| 検出内容 | アクション |
|---|---|
| テストファイル削除 | **即座に Red ゲート**。削除を revert し、テストが通るよう実装を修正 |
| テスト無効化（skip等） | **即座に Red ゲート**。無効化を revert し、テストが通るよう実装を修正 |
| assertion 変更 | **人間に報告**。正当な理由（仕様変更に伴う期待値更新）があれば許可。理由がなければ Red ゲート |
| カバレッジ低下（5%以上） | **Yellow 警告**。原因を特定し、次セッションまでに回復計画 |
| カバレッジ低下（5%未満） | **記録のみ**。PROGRESS.md に記載 |

## 3プロンプトの実行スケジュール

```
週1回: SD-01（定期チェック）
  ↓
実装完了時: SD-02（受入条件検証）
  ↓
テスト変更時: SD-03（改ざん検出）
```

- SD-01 は週次の定期タスク（セッション開始時に最終実行日を確認）
- SD-02 は DoD チェックの一部として実行
- SD-03 はテストファイルの diff があるたびに実行

---

## ドリフト対処の原則

**仕様と実装が食い違ったとき、どちらを直すか?**

| 状況 | 直す対象 |
|---|---|
| 仕様が正しく、実装が間違っている | 実装を修正する |
| 実装が正しく、仕様が古い | 仕様を更新する（人間の承認後） |
| どちらが正しいか不明 | 人間にエスカレーション。勝手に判断しない |

**重要**: 「仕様を実装に合わせる」のは人間の承認が必要。AI が勝手に仕様を書き換えてはならない。
