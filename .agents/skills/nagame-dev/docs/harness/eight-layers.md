# 8層ハーネスアーキテクチャ

P/G/E（Planner / Generator / Evaluator）を包括する完全なハーネス構造。
8つの層が連携して、AI の出力品質を制御する。

---

## アーキテクチャ全体図

```
┌─────────────────────────────────────────┐
│  Layer 8: Governance（人間の確認点）      │  ← 最上位: 人間が最終判断
├─────────────────────────────────────────┤
│  Layer 7: Memory（状態と履歴）           │
├─────────────────────────────────────────┤
│  Layer 6: Sensor（事後評価 = feedback）   │
├─────────────────────────────────────────┤
│  Layer 5: Tool（実行手段の限定）          │
├─────────────────────────────────────────┤
│  Layer 4: Rule（事前制御 = feedforward）  │
├─────────────────────────────────────────┤
│  Layer 3: Agent（役割分担）              │  ← P/G/E はここ
├─────────────────────────────────────────┤
│  Layer 2: Context（知識の体系化）         │
├─────────────────────────────────────────┤
│  Layer 1: Intent（人間の目的）           │  ← 最下位: 全ての起点
└─────────────────────────────────────────┘
```

---

## 各層の詳細

### Layer 1: Intent層（意図層）

**役割**: 人間の目的を短く明確に伝える。全ての作業の起点。

**代表ファイル**:
- `CLAUDE.md` — プロジェクト固有の指示書（13パート構成）
- `AGENTS.md` — エージェント間の役割分担定義

**設計指針**:
- 1文で目的を表現できること（「〇〇を作る」「〇〇を改善する」）
- 曖昧な表現を避ける（「良い感じに」「適切に」は禁止）
- 技術スタック・対象ユーザー・成功基準を明示する

**ここが壊れると**: 全層が誤った方向に進む。最も致命的な層。

---

### Layer 2: Context層（文脈層）

**役割**: 作業に必要な知識を体系化して提供する。

**代表ファイル**:
- `docs/architecture/` — アーキテクチャドキュメント
- `docs/design-docs/` — 設計ドキュメント
- `docs/SRS.md` — ソフトウェア要求仕様書
- `docs/SDD.md` — ソフトウェア設計文書
- `~/claude-harness/knowledge/` — 過去プロジェクトの知識蓄積

**設計指針**:
- ドキュメントは構造化する（番号付き、セクション分け）
- 「読めば分かる」状態を維持する（暗黙知を残さない）
- 古い情報には日付と「deprecated」マークを付ける

**ここが壊れると**: Claude が誤った前提で実装を進める（スペックドリフトの原因）。

---

### Layer 3: Agent層（役割層）

**役割**: P/G/E の役割分担を定義する。

**代表ファイル**:
- `.claude/agents/planner.md` — Planner の指示書
- `.claude/agents/generator.md` — Generator の指示書
- `.claude/agents/evaluator.md` — Evaluator の指示書

**P/G/E の役割**:
| エージェント | 責務 | 主な成果物 |
|---|---|---|
| **Planner** | 要件整理・設計・計画 | SRS, SDD, TEST_PLAN |
| **Generator** | 実装・コード生成 | src/, tests/ |
| **Evaluator** | 検証・品質評価・ドリフト検出 | evals/, test results, drift reports |

**設計指針**:
- 各エージェントの責務境界を明確にする
- Generator は SRS/SDD に書かれていないものを実装しない
- Evaluator は「テストを通すためにテストを変える」ことをしない

**ここが壊れると**: 役割が混ざり、Generator が勝手に設計変更したり、Evaluator が甘い判定をする。

---

### Layer 4: Rule層（事前制御層）

**役割**: 作業開始前に制約を設定する。フィードフォワード（事前）制御。

**代表ファイル**:
- `.claude/rules/` — Claude Code のルールファイル群
- `CONSTRAINTS.md` — プロジェクト固有の禁止事項（6セクション構成）
- `quality/policies/` — 品質ポリシー定義

**設計指針**:
- 「やってはいけないこと」を先に書く（5原則の第2原則）
- 禁止事項には必ず理由（FP-XXX）を紐付ける
- 制約は具体的に書く（「適切に」ではなく「500行以下」）

**ここが壊れると**: Claude が自由に動きすぎて、過去の失敗を繰り返す。

---

### Layer 5: Tool層（手段層）

**役割**: Claude が使える手段を限定する。

**代表ファイル**:
- `.mcp.json` — MCP サーバー設定
- `.claude/skills/` — カスタムスキル定義
- `.claude/settings.json` — 権限設定

**設計指針**:
- 必要最小限のツールだけ有効にする
- 破壊的操作（rm -rf、DROP TABLE等）は原則禁止
- 外部APIの呼び出しは承認制にする

**ここが壊れると**: 意図しないツール実行で環境を破壊する。

---

### Layer 6: Sensor層（事後評価層）

**役割**: 実行結果を事後評価する。フィードバック制御。

**代表ファイル**:
- `evals/` — 評価スクリプト・結果
- `tests/` — テストスイート
- `quality/checks/` — 品質チェックスクリプト

**設計指針**:
- テストは実装前に書く（Layer 4 の完了条件と連動）
- 評価基準は機械判定可能にする（曖昧な基準禁止）
- テスト改ざんを検出する仕組みを入れる（SD-03）

**ここが壊れると**: 品質が分からないまま「完了」と宣言してしまう。

---

### Layer 7: Memory層（記憶層）

**役割**: セッション間の状態と失敗履歴を保持する。

**代表ファイル**:
- `PROGRESS.md` — セッション間の引き継ぎ記録
- `harness/runs/` — 実行履歴
- `harness/memory/` — セッション別の状態スナップショット
- `~/claude-harness/knowledge/failure_patterns.md` — 失敗パターン蓄積

**設計指針**:
- セッション終了時に必ず PROGRESS.md を更新する
- 失敗は発生直後に記録する（後回しにしない）
- 記録形式を統一する（FP-XXX、SP-XXX）

**ここが壊れると**: セッションが切り替わるたびに記憶喪失が起き、同じ失敗を繰り返す。

---

### Layer 8: Governance層（統治層）

**役割**: 人間の確認点と変更管理。最終意思決定は常に人間が行う。

**代表ファイル**:
- `docs/adr/` — Architecture Decision Records
- `release/` — リリース管理
- `review/` — レビュー記録

**設計指針**:
- RYG ゲート（Red/Yellow/Green）で進行可否を判断する
- 重要な設計判断は ADR として記録する
- リリース前に人間のサインオフを必須にする

**ここが壊れると**: AI が人間の承認なしに本番リリースしてしまう。

---

## P/G/E と 8層のマッピング

```
Planner  → Layer 1 (Intent) + Layer 2 (Context) を入力
           Layer 4 (Rule) を参照
           SRS / SDD / TEST_PLAN を出力

Generator → Layer 2 (Context) + Layer 4 (Rule) を入力
            Layer 5 (Tool) を使用
            src/ / tests/ を出力

Evaluator → Layer 6 (Sensor) を実行
            Layer 7 (Memory) に記録
            Layer 8 (Governance) で人間に報告
```

---

## 層間の依存関係

- Layer 1 → Layer 2: 目的に応じた文脈を用意する
- Layer 2 → Layer 3: 文脈に基づいて役割を割り当てる
- Layer 3 → Layer 4: 役割ごとの制約を設定する
- Layer 4 → Layer 5: 制約に沿ったツールを選定する
- Layer 5 → Layer 6: ツール実行結果を評価する
- Layer 6 → Layer 7: 評価結果を記憶に残す
- Layer 7 → Layer 8: 蓄積された記録から人間が判断する
- Layer 8 → Layer 1: 人間の判断が次の意図になる（循環）

**1つの層を飛ばすと**: 制御が効かなくなる。全8層を順に通すことが品質保証の基本。
