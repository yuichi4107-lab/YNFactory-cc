# コスト・トークン管理ガイド

## 概要

AI駆動開発では「トークン」と「セッション数」が直接コストに影響する。
無計画に進めるとコンテキスト枯渇でセッション切り替えが頻発し、
引き継ぎコスト（情報の再読み込み）だけで予算の大半を消費する。

例え話：タクシーのメーターと同じ。目的地を決めずに走り回ると、
メーターだけが上がって目的地に着かない。事前にルートを決めて最短距離で走る。

---

## 1. リサーチ回数制限

### 同一トピックの再リサーチ上限: 3回

同じトピックについて調べ直すのは最大3回まで。
3回調べても十分な情報が得られない場合は、以下のいずれかを選択する。

| 回数 | アクション |
|---|---|
| 1回目 | 通常リサーチ |
| 2回目 | キーワード・ソースを変えて再リサーチ |
| 3回目 | 異なるリサーチスキルで再リサーチ |
| 3回超 | 社長にエスカレーション（情報が見つからない旨を報告） |

### 理由

リサーチは API 呼び出しコストが高い（1回あたり数百円〜数千円）。
同じトピックを何度も調べるのはコスト効率が悪い。
3回で見つからないなら、そもそも情報が公開されていない可能性が高い。

## 2. フェーズ別セッション数上限

### 通常フェーズ: 最大2セッション

Phase 0（要件定義）〜 Phase 4（テスト設計）は、各フェーズ最大2セッションで完了させる。

| フェーズ | 上限セッション数 | 超過時の対応 |
|---|---|---|
| Phase 0: 要件定義 | 2 | スコープを絞って再開 |
| Phase 1: リサーチ | 2 | 調査範囲を限定 |
| Phase 2: 文書構築 | 2 | 文書を分割して段階的に作成 |
| Phase 3: 設計 | 2 | 設計粒度を粗くして先に進む |
| Phase 4: テスト設計 | 2 | テスト範囲を MVP に限定 |

### 実装フェーズ: プロジェクト規模に応じて可変

Phase 5（実装）はプロジェクト規模で上限が変わる。

| 規模 | ファイル数目安 | 上限セッション数 |
|---|---|---|
| Small | 〜10ファイル | 1〜2 |
| Medium | 11〜30ファイル | 2〜3 |
| Large | 31ファイル〜 | 3〜5 |

### 例外

以下の場合のみセッション数上限を超えてよい。

- 社長が明示的に追加セッションを承認した場合
- Blocker レベルの問題が発見され、解決に追加セッションが必要な場合
- 外部要因（API仕様変更等）で手戻りが発生した場合

## 3. トークン予算配分

### フェーズグループ別の配分比率

プロジェクト全体のトークン消費を以下の比率で管理する。

| フェーズグループ | 含むフェーズ | 配分比率 | 用途 |
|---|---|---|---|
| **設計・準備** | Phase 0〜4 | 30〜50% | 要件定義・リサーチ・文書構築・設計・テスト設計 |
| **実装** | Phase 5 | 10〜20% | コーディング・ユニットテスト |
| **検証・運用** | Phase 6 | 30〜50% | 統合テスト・レビュー・デプロイ・運用設計 |

### 配分の意図

- 設計・準備に多く配分するのは、ここでの品質がプロジェクト全体を決めるため
- 実装は設計が固まっていれば比較的少ないトークンで済む
- 検証・運用はレビューの往復やバグ修正の手戻りを含むため多めに確保

### 配分超過時の対応

配分比率を超過しそうな場合。

1. 現在のトークン使用状況を社長に報告する
2. 超過の原因を分析する（手戻り？スコープ肥大？）
3. 残りフェーズの配分を調整する案を提示する
4. 社長の承認を得て進行する

## 4. コンテキスト使用率の管理

### 70% ルール: セッション切り替え閾値

コンテキストウィンドウの使用率が **70%** に達したら、セッション切り替えを準備する。

| 使用率 | 状態 | アクション |
|---|---|---|
| 〜50% | 正常 | 通常作業を継続 |
| 50〜70% | 注意 | /compact の実行を検討 |
| 70% | 警戒 | セッション切り替えを準備（引き継ぎプロンプト作成開始） |
| 80% | 危険 | 新規タスク着手禁止、引き継ぎプロンプト完成を最優先 |
| 90%〜 | 緊急 | 即座にセッション切り替え |

### 70% で切り替える理由

- 引き継ぎプロンプトの作成自体にトークンを消費する（約5〜10%）
- 最後のタスク完了とプロンプト作成に余裕が必要
- 90% を超えると応答品質が劣化し、引き継ぎ品質も下がる

## 5. コスト削減テクニック

### 5-1: /compact の活用

長い会話履歴を圧縮し、コンテキスト使用率を下げる。

**使うタイミング:**
- コンテキスト使用率が 50% を超えたとき
- 長い議論が一段落して、要点だけ残せばよいとき
- 大きなコードブロックの読み込み後、分析結果だけ残したいとき

**使ってはいけないタイミング:**
- 議論の途中（文脈が失われる）
- 重要な意思決定の直後（決定内容が消える可能性）

### 5-2: 500文字サマリールール

長いドキュメントや調査結果を会話に残す場合、500文字以内のサマリーに圧縮する。

```
## サマリー（500文字以内）
- 結論: ...
- 根拠: ...
- 次のアクション: ...
- 詳細は [ファイルパス] を参照
```

全文をコンテキストに保持するのではなく、サマリー + ファイル参照にする。

### 5-3: Task による処理の隔離

独立したサブタスク（リサーチ、コード生成等）は Task で別コンテキストに隔離する。
メインのコンテキストを消費せずに済む。

**Task に向いている処理:**
- 特定ライブラリの API 調査
- テンプレートコードの生成
- テストデータの作成
- フォーマット変換

**Task に向いていない処理:**
- プロジェクト全体の方針判断
- 複数ファイルにまたがる設計変更
- 社長との対話が必要な判断

### 5-4: Read-on-Demand（必要時読み込み）

ファイルは必要になった時点で読む。セッション開始時に全ファイルを読まない。

- セッション開始時: 引き継ぎプロンプトの [A][B] を最小限で読む
- 議論対象資産 [C]: その議論に着手する時点で読む
- 参照ファイル: 議論中に必要になった時点で読む

## 6. コスト監視のチェックリスト

### セッション開始時

- [ ] 今回のセッションで扱うフェーズを確認
- [ ] トークン予算配分の残りを確認
- [ ] 前セッションの HOLD 項目を確認（追加コストの見積もり）

### セッション中（定期確認）

- [ ] コンテキスト使用率を確認（50% 超えたら /compact 検討）
- [ ] リサーチ回数を確認（同一トピック3回上限）
- [ ] 予定外のタスクが発生していないか確認

### セッション終了時

- [ ] 消費トークンの概算を記録
- [ ] フェーズ進捗とコストの対応を記録
- [ ] 次セッションへの引き継ぎプロンプトを作成
- [ ] HOLD 項目のコスト影響を見積もり

---

## 7. コスト超過の警告サイン

以下のいずれかに該当する場合、コスト管理に問題がある可能性が高い。

| 警告サイン | 原因の可能性 | 対策 |
|---|---|---|
| 同じトピックを4回以上リサーチ | 検索キーワードが不適切 | キーワード再設計、社長に相談 |
| 1フェーズで3セッション以上消費 | スコープ肥大 or 手戻り | スコープ再定義、手戻り原因分析 |
| セッション開始30分でコンテキスト50% | 読み込みファイルが多すぎる | Read-on-Demand に切り替え |
| 引き継ぎプロンプトが毎回1000文字超 | 前セッションの整理不足 | サマリーの圧縮、HOLD項目の整理 |
| /compact を1セッションで3回以上使用 | 会話が冗長 | 回答の簡潔化、タスク分割 |
