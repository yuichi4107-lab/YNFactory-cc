# プロジェクト間の成長曲線

## 概要

nagame-dev は、プロジェクトを重ねるごとに品質と効率が向上する仕組みを持つ。
本文書は、その成長の軌跡を可視化し、成長を加速させるための運用ルールを定義する。

例え話：自動車教習所と同じ。最初は教官（安全装置）がフル介入するが、
運転が上手くなるにつれて介入が減り、最終的には一人で運転できるようになる。
ただし「同じミスを2回する」のは成長していない証拠。

---

## 1. 成長テーブル

| プロジェクト数 | フェーズ | 変化する内容 | Layer 2 蓄積 |
|---|---|---|---|
| **1件目** | 初心者 | 全フェーズをフル手順で実行。全チェックリストを逐一確認。社長の承認を頻繁に取得。 | 初回の失敗パターン・成功パターンを記録開始 |
| **2件目** | 学習期 | 1件目の失敗を CONSTRAINTS に反映。既知パターンはスキップ可能に。 | 失敗パターン 5〜10件、成功パターン 3〜5件 |
| **3〜5件目** | 安定期 | Phase 0〜2 の所要時間が半減。テンプレートが成熟。境界ケースの見落としが減少。 | 失敗パターン 15〜30件、コードスニペット蓄積開始 |
| **6〜8件目** | 効率化期 | セッション数が平均30%削減。レビューの馴れ合い検出が自動化。類似プロジェクトは再利用率が高い。 | 教訓 50件超、プロジェクト横断パターンが見える |
| **9件目以降** | 自律期 | ルーチン判断は AI が自律実行。社長承認は重要判断のみ。新規リスクの予測精度が向上。 | 成長曲線自体のメタ分析が可能に |

## 3. H-REVIEW（定期振り返り）

### H-REVIEW とは

プロジェクト完了後に実施する振り返りセッション。
「何がうまくいったか」「何がうまくいかなかったか」「次にどう改善するか」を記録する。

### 実施タイミング

| タイミング | 目的 | 所要時間目安 |
|---|---|---|
| **プロジェクト完了直後** | 記憶が新鮮なうちに教訓を記録 | 1セッション |
| **3件目完了後** | 初期パターンの安定化確認 | 1セッション |
| **5件目完了後** | 成長テーブルとの乖離確認 | 1セッション |
| **10件目完了後** | 成長曲線のメタ分析 | 1〜2セッション |

### H-REVIEW の構成

```
1. プロジェクト概要（1段落）
2. 成功点（箇条書き3〜5件）
3. 失敗点（箇条書き3〜5件）
4. 各失敗の根本原因分析（5 Whys）
5. CONSTRAINTS への反映事項
6. 次プロジェクトへの具体的改善案
7. 成長指標の更新
```

### H-REVIEW の成果物

| 成果物 | 格納場所 | 内容 |
|---|---|---|
| H-REVIEW レポート | doc/review/h-review/ | 振り返り全文 |
| CONSTRAINTS 更新差分 | プロジェクトルート | 新規制約の追加 |
| 知識ベース更新 | doc/knowledge/ | 5種類の知識タイプ別に分類記録 |

## 4. 5つの知識タイプ

プロジェクトを通じて蓄積される知識を5つに分類する。

### 4-1: failure_patterns（失敗パターン）

過去に発生した失敗とその根本原因。同じ失敗を繰り返さないための記録。

**記録形式:**
```
[FP-001] トークン期限切れによる深夜バッチ停止
- 発生日: 2026-05-15
- プロジェクト: XXXパイプライン
- 根本原因: リフレッシュトークンの有効期限を考慮していなかった
- 対策: BC-2 チェックリストに項目追加済み
- CONSTRAINTS 反映: 済（項目 C-042）
```

**蓄積目標:**
- 1件目完了時: 5〜10件
- 5件目完了時: 30〜50件
- 10件目完了時: 80〜100件

### 4-2: success_patterns（成功パターン）

うまくいったアプローチとその条件。再現性のある成功の記録。

**記録形式:**
```
[SP-001] dry-run → 承認 → 本番の3段階デプロイ
- 初回適用: XXXプロジェクト
- 条件: 自動投稿系の機能全般
- 効果: 誤投稿ゼロを達成
- 再利用回数: 4回（全て成功）
```

### 4-3: lessons_learned（教訓）

失敗パターンから抽出した、より抽象的な学び。プロジェクト横断で適用可能。

**記録形式:**
```
[LL-001] 紙の議論段階で完全実装を目指すと破綻する
- 発見: 壁打ち8回目で12ラウンド議論しても合格に至らなかった
- 一般化: 段階に応じてテスト密度を変える（test-granularity ルール化済み）
- 適用範囲: 全プロジェクトの Phase 2〜4
```

### 4-4: code_snippets（コードスニペット）

再利用可能なコード断片。コピペ可能な形で保存。

**記録形式:**
```
[CS-001] 環境変数存在チェックスクリプト
- 言語: Bash
- 用途: セットアップ時の環境変数確認
- 依存: なし
- コード: (スニペット本体)
```

**蓄積目標:**
- 3件目以降: 認証系、API呼び出し系、エラーハンドリング系が揃い始める
- 5件目以降: プロジェクト初期セットアップがスニペット組み合わせで完了

### 4-5: project_history（プロジェクト履歴）

各プロジェクトのメタ情報。成長曲線の計測に使用。

**記録形式:**
```
[PH-001] XXXパイプライン
- 期間: 2026-05-01 〜 2026-05-20
- セッション数: 12
- フェーズ別所要時間: P0(2h) P1(3h) P2(4h) P3(3h) P4(2h) P5(8h) P6(4h)
- Blocker 数: 3
- 社長エスカレーション数: 5
- H-REVIEW 実施: 済
```

## 5. 成長原則

### 核心ルール: 同じ失敗を2回したら CONSTRAINTS 変換失敗

```
1回目の失敗 = 学習機会（許容される）
2回目の同じ失敗 = CONSTRAINTS への変換が不十分だった証拠（問題あり）
3回目の同じ失敗 = 成長の仕組み自体が壊れている（緊急対応）
```

### このルールの意味

1回目の失敗は避けられない。それは新しい知識を得る機会。
しかし、1回目の失敗を failure_patterns に記録し、CONSTRAINTS に反映したなら、
2回目は防げるはず。防げなかったのは、記録か反映のプロセスに問題がある。

### 3回目の失敗が発生した場合のアクション

1. 過去の failure_patterns 記録を確認する
2. CONSTRAINTS への反映内容を確認する
3. なぜ CONSTRAINTS があっても防げなかったかを分析する
4. CONSTRAINTS の記述方法 or チェックプロセスを改善する
5. H-REVIEW を臨時実施する

## 6. 成長計測チェックリスト

### プロジェクト完了時に計測する指標

- [ ] **セッション効率**: 総セッション数は前回プロジェクトより減ったか
- [ ] **レビュー効率**: 平均レビューラウンド数は減ったか
- [ ] **バグ発見時期**: バグは早期フェーズで発見できたか（左シフト）
- [ ] **スニペット再利用**: コードスニペットの再利用率は上がったか
- [ ] **エスカレーション精度**: 不要なエスカレーション（オオカミ少年）は減ったか
- [ ] **社長満足度**: 社長からの修正指示は減ったか

### 3件ごとに計測する指標

- [ ] **失敗パターン蓄積数**: 目標値に達しているか
- [ ] **同一失敗の再発数**: 2回以上の再発がないか
- [ ] **Phase 0〜2 所要時間**: 前回の3件平均より短縮されたか
- [ ] **CONSTRAINTS の項目数**: 適切に増加しているか（過剰でも不足でもない）

### 成長が停滞している兆候

以下のいずれかに該当する場合、成長の仕組みに問題がある。

| 兆候 | 考えられる原因 | 対策 |
|---|---|---|
| セッション数が減らない | 手戻りが多い or スコープが毎回肥大 | スコープ管理の強化 |
| 同じ失敗が再発する | CONSTRAINTS 反映が不十分 | H-REVIEW の質を上げる |
| スニペット再利用率が上がらない | スニペットの整理不足 | code_snippets の分類見直し |
| 社長エスカレーションが減らない | 判断基準が明確化されていない | Autonomy Boundary Spec の更新 |
| H-REVIEW を実施していない | 「忙しくて振り返れない」 | プロジェクト完了の定義に H-REVIEW を含める |

## 7. 知識ベースのメンテナンス

### 更新タイミング

| トリガー | 更新対象 |
|---|---|
| バグ修正完了時 | failure_patterns |
| フェーズ完了時 | success_patterns, lessons_learned |
| 再利用可能なコード完成時 | code_snippets |
| プロジェクト完了時 | project_history + H-REVIEW |
| CONSTRAINTS 更新時 | 関連する全知識タイプ |

### 陳腐化チェック（半年ごと）

- 6ヶ月以上参照されていない failure_patterns → アーカイブ検討
- 技術変更で無効になった code_snippets → 更新 or 削除
- 外部サービス変更で無効になった success_patterns → 更新
