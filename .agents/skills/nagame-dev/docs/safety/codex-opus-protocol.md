# Codex⇄Opus 非対称レビュープロトコル

## 概要

Codex（実装側AI）と Opus（統括側AI）は対等ではない。
Codex は「技術的に正しいか」を判定し、Opus は「事業的に採用するか」を判定する。
この非対称性を崩さないことが、レビュー品質の生命線である。

---

## 1. 役割テーブル

| 観点 | Codex（実装側） | Opus（統括側） |
|---|---|---|
| **主責任** | 実装 / テスト / CI 破綻検出 | 採否判定 / 運用 / 事業整合 / 安全性 |
| **判断権限** | 技術的 GO/NO-GO の提案 | 最終 ACCEPT/REJECT の決定 |
| **視野** | コード品質・テスト網羅・依存関係 | 事業リスク・コスト・スケジュール・法務 |
| **エスカレーション先** | Opus | 社長 |
| **禁止事項** | 事業判断を勝手に行う | 実装詳細を指示しすぎる |

---

## 2. イテレーションフロー（最大3ラウンド）

```
Round 1-A: Codex → GO / CONDITIONAL GO / NO-GO / ESCALATE を提案
    ↓
Round 1-B: Opus → Finding 単位で ACCEPT / MODIFY / REJECT / HOLD / ESCALATE
    ↓
Round 2-A: Codex → MODIFY/HOLD 項目に対して修正案 or 反論を提示
    ↓
Round 2-B: Opus → 収束判定（全 Finding が ACCEPT or REJECT なら終了）
    ↓
Round 3:   収束しない場合 → 強制 ESCALATE（社長判断へ）
```

### ラウンド制限の理由

3ラウンドを超えるレビューは「論点が整理できていない」証拠。
堂々巡りを防ぐため、Round 3 で未解決の Finding は全て社長エスカレーションとする。

---

## 3. Codex 判定ラベル

| ラベル | 意味 | 次のアクション |
|---|---|---|
| **GO** | 技術的に問題なし、リリース可能 | Opus が事業判断へ進む |
| **CONDITIONAL GO** | 軽微な条件付きで GO | Opus が条件の妥当性を判定 |
| **NO-GO** | 技術的に重大な問題あり | Opus が対応方針を決定 |
| **ESCALATE** | Codex の判断範囲を超える | Opus 経由で社長へ |

---

## 4. Opus Finding 単位の判定ラベル

| ラベル | 意味 | 後続処理 |
|---|---|---|
| **ACCEPT** | Codex の指摘を受け入れる | 修正を実装に反映 |
| **MODIFY** | 指摘は正しいが対応方法を変更 | Codex に修正案を再提示 |
| **REJECT** | 指摘を却下（根拠を明示必須） | Codex に却下理由を通知 |
| **HOLD** | 今回は対応せず、将来課題として記録 | Finding Ledger に登録 |
| **ESCALATE** | Opus の判断範囲を超える | 社長へ Decision Packet 提出 |

---

## 5. Finding 優先度（上から順に対応必須度が高い）

| 優先度 | 定義 | 対応期限 |
|---|---|---|
| **Blocker** | これが未解決ならリリース不可 | 現セッション内 |
| **Must** | リリース前に必ず対応 | 現フェーズ内 |
| **Should** | 対応推奨だが、未対応でもリリース可 | 次フェーズまで |
| **Later** | 将来的に対応 | バックログ登録 |
| **Reject** | 対応不要と判断 | 記録のみ |
| **Escalate** | AI判断範囲外 | 社長判断待ち |

---

## 6. 終了条件

レビューは以下のいずれかを満たしたとき終了する。

- [ ] 全 Blocker が解決済み
- [ ] 全 Must が解決済み or HOLD（HOLD理由が明示されていること）
- [ ] Should 以下は記録されていれば未解決でも可
- [ ] Opus が最終判定（GO / NO-GO）を出した
- [ ] Round 3 到達で未解決項目が社長エスカレーション済み

---

## 7. Review Role Charter（役割憲章）

### Codex の義務

1. 指摘には必ずコード箇所・再現手順・修正案の3点セットを含める
2. 「問題なし」の場合でも、確認した範囲を明示する
3. 推測で GO を出さない。確認できない箇所は ESCALATE する
4. Opus の REJECT に対して反論する場合、一次ソースを根拠にする

### Opus の義務

1. Codex の指摘を形式的に承認しない（内容を検証する）
2. REJECT する場合、技術的根拠 or 事業的根拠を必ず明示する
3. 全 Finding に対して判定ラベルを付与する（放置禁止）
4. 社長への説明責任を常に意識する（高校生説明可能性）

---

## 8. 馴れ合い禁止ルール

AI同士のレビューは「互いに褒め合って終わる」リスクが極めて高い。
以下を厳守する。

### 禁止パターン

| パターン | 例 | なぜ危険か |
|---|---|---|
| **形式的承認** | 「Codex の分析は素晴らしい、ACCEPT」 | 内容を検証していない |
| **根拠なき GO** | 「特に問題なさそうなので GO」 | 確認範囲が不明 |
| **相互譲歩** | 「お互いの指摘を半分ずつ採用」 | 技術的正しさは多数決ではない |
| **ESCALATE 回避** | 「自分たちで何とかしよう」 | 判断範囲を超えている可能性 |

### 検出基準

以下のいずれかに該当する場合、馴れ合いの疑いがある。

- [ ] Round 1 で全 Finding が ACCEPT（1つも異論なし）
- [ ] Codex と Opus の判定が3回連続で一致
- [ ] REJECT が1件もない状態が3セッション以上継続
- [ ] Finding の記述が3行未満（検証の深さが不足）

### 馴れ合い検出時の対応

1. Opus は自己点検を行い、「見落としがないか」を再確認する
2. 再確認でも問題なしなら、その旨を明示して進行（正当な一致もある）
3. 社長への報告時に「馴れ合いチェック済み」と付記する

---

## 9. レビュー記録の保存

| 記録項目 | 保存先 |
|---|---|
| Finding 一覧と判定結果 | Finding Ledger（プロジェクト内 doc/） |
| ラウンドごとのやり取り要約 | Review Log（doc/codex-review/） |
| ESCALATE した項目 | Decision Packet（社長提出用） |
| HOLD した項目 | バックログ（次フェーズ引き継ぎ） |

---

## 10. 運用チェックリスト

レビュー開始前に確認する。

- [ ] Codex と Opus の役割分担が明確か
- [ ] レビュー対象（コード差分・仕様書・テスト結果）が揃っているか
- [ ] 前回レビューの HOLD 項目を引き継いでいるか
- [ ] 馴れ合い防止の意識を持っているか
- [ ] 社長への報告形式（高校生説明）を準備しているか
