# Phase 2: 要件定義 SRS（IEEE 29148 / ISO 25010 準拠）

## 目的

Phase 0（ヒアリング）と Phase 1（リサーチ）の成果を、正式な要件定義書（SRS）に変換する。
IEEE 29148 のフレームワークに沿い、曖昧さゼロ・機械検証可能な要件を定義する。

---

## 1. SRS 章構成

以下の章構成で SRS を作成する。全章必須。

| 章 | タイトル | 内容 |
|---|---|---|
| 0 | **文書管理** | 版数、作成日、変更履歴、承認者 |
| 1 | **はじめに** | 目的、範囲、用語集、参考文書 |
| 2 | **システム概要** | 全体像、コンテキスト図、主要機能の概略 |
| 3 | **ステークホルダー** | 利用者、管理者、外部サービス、それぞれの関心事 |
| 4 | **運用サイクル** | 日次/週次/月次の運用フロー、定期タスク |
| 5 | **フェーズ計画** | MVP→V2→V3 のロードマップ、各フェーズのスコープ |
| 6 | **外部インターフェース** | 外部 API、ファイル入出力、ユーザーインターフェース |
| 7 | **機能要件** | FR-* ID 付きの要件一覧（Given-When-Then） |
| 8 | **画面・操作フロー** | UI がある場合の画面遷移、CLI の場合のコマンド体系 |
| 9 | **データ要件** | データモデル、保存形式、ライフサイクル、バックアップ |
| 10 | **非機能要件** | ISO 25010 の 9 品質特性に基づく要件 |
| 11 | **セキュリティ・監査** | 認証認可、データ保護、監査ログ、インシデント対応 |
| 12 | **制約条件** | 技術的制約、法的制約、運用制約、予算制約 |
| 13 | **トレーサビリティ** | 要件→設計→テスト→実装の追跡マトリクス |
| 14 | **リスク・変更管理** | リスク一覧、変更管理プロセス、エスカレーション基準 |

## 2. MoSCoW 優先度分類

全ての機能要件に MoSCoW 優先度を付与する。

| 優先度 | 意味 | MVP対象 | 目安 |
|---|---|---|---|
| **Must** | これがないとシステムが成立しない | 対象 | 全体の60%以下 |
| **Should** | なくても動くが、強く望まれる | 判断による | 全体の20%程度 |
| **Could** | あると嬉しい | 対象外 | 全体の15%程度 |
| **Won't** | 今回は作らない（将来候補） | 対象外 | 全体の5%程度 |

### 優先度付与ルール

- Must が全体の60%を超えたら、スコープの見直しが必要
- Won't は OUT OF SCOPE として明記（「やらない」と決めたことも記録）
- 社長の承認なしに Must を追加しない

## 3. 要件ID命名規則

```
FR-[カテゴリ]-[連番3桁]
```

### カテゴリ一覧

| カテゴリ | 略称 | 例 |
|---|---|---|
| ユーザー管理 | USR | FR-USR-001 |
| 認証認可 | AUTH | FR-AUTH-001 |
| データ処理 | DATA | FR-DATA-001 |
| 外部連携 | EXT | FR-EXT-001 |
| 通知 | NTF | FR-NTF-001 |
| 管理機能 | ADM | FR-ADM-001 |
| レポート | RPT | FR-RPT-001 |
| システム | SYS | FR-SYS-001 |

### 非機能要件のID

```
NFR-[ISO 25010カテゴリ]-[連番3桁]
```

例: `NFR-PERF-001`（性能要件の1番目）

## 4. Given-When-Then 形式

全ての機能要件は Given-When-Then で記述する。

### テンプレート

```markdown
### FR-DATA-001: 台本テキストから動画を生成する

- **優先度**: Must
- **Given（前提）**: ユーザーが台本テキスト（500文字以上10000文字以下）を用意している
- **When（操作）**: ユーザーがCLIで `generate --input script.txt` を実行する
- **Then（結果）**: 
  - 字幕付きMP4動画ファイルが `output/` ディレクトリに生成される
  - 動画の長さは台本の文字数に応じて 1-30分の範囲
  - 処理完了後、ファイルパスが標準出力に表示される
- **例外**:
  - 台本が500文字未満の場合、エラーメッセージを表示して終了
  - 外部APIがタイムアウトした場合、3回リトライ後にエラー終了
```

### 記述ルール

- **1要件1文**: 1つの FR に複数の独立した機能を詰め込まない
- **検証可能**: Then には具体的な数値・条件を含める（「適切に」「高速に」は禁止）
- **例外を明記**: 異常系・境界条件を必ず書く
- **主語を明確に**: 「システムが」「ユーザーが」を省略しない

## 5. 1要件1文ルール

### NG例

```
FR-DATA-001: ユーザーは台本をアップロードでき、動画が生成され、
完了通知がメールで届き、管理画面で履歴が確認できる。
```

### OK例（4つの独立した要件に分割）

```
FR-DATA-001: ユーザーは台本テキストをアップロードできる
FR-DATA-002: システムは台本テキストから動画を生成する
FR-NTF-001: 動画生成完了時にメールで通知する
FR-RPT-001: 管理画面で動画生成履歴を確認できる
```

## 6. ISO 25010 非機能要件（9品質特性）

| # | 品質特性 | 確認項目 | 記述例 |
|---|---|---|---|
| 1 | **機能適合性** | 機能完全性、正確性、適切性 | 「計算結果の誤差は0.1%以内」 |
| 2 | **性能効率性** | 応答時間、スループット、資源利用 | 「API応答は3秒以内」 |
| 3 | **互換性** | 共存性、相互運用性 | 「Python 3.11/3.12で動作」 |
| 4 | **使用性** | 操作性、学習性、エラー防止 | 「初回利用時の操作手順は5ステップ以内」 |
| 5 | **信頼性** | 成熟性、可用性、回復性 | 「月間稼働率99%以上」 |
| 6 | **セキュリティ** | 機密性、完全性、否認防止 | 「APIキーは環境変数ファイルで管理」 |
| 7 | **保守性** | モジュール性、再利用性、テスト容易性 | 「単体テストカバレッジ80%以上」 |
| 8 | **移植性** | 適応性、設置性、置換性 | 「Docker で環境構築可能」 |
| 9 | **自由度（拡張性）** | 拡張容易性、カスタマイズ性 | 「新APIプロバイダの追加は設定ファイルのみ」 |

### 記述ルール

- 全9特性について記載する（該当なしの場合は「該当なし、理由: ...」と明記）
- 数値目標を含める（「高い」「速い」は禁止）
- 測定方法を併記する（どうやって確認するか）

## 7. 8観点品質チェックリスト

SRS 完成後、以下の8観点でセルフレビューを行う。

| # | 観点 | チェック内容 | 合否 |
|---|---|---|---|
| 1 | **完全性** | 全ての機能がカバーされているか、抜け漏れはないか | |
| 2 | **一貫性** | 要件間に矛盾がないか、用語は統一されているか | |
| 3 | **検証可能性** | 全ての要件がテストで検証できるか | |
| 4 | **追跡可能性** | 全ての要件にIDがあり、設計・テストと紐付くか | |
| 5 | **明確性** | 曖昧な表現がないか（「適切に」「必要に応じて」等） | |
| 6 | **実現可能性** | 技術的・予算的に実現可能か | |
| 7 | **優先順位** | 全要件に MoSCoW 優先度が付いているか | |
| 8 | **変更容易性** | 要件の追加・変更が容易な構造になっているか | |
