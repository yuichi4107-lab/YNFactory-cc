# Phase 1: リサーチ V1→V2

## 目的

Phase 0 で確定したヒアリング内容をもとに、技術的な裏付けを取る。
「作れるか？」「どう作るか？」「何に注意するか？」を調査し、Phase 2（SRS）の入力とする。

**逆算アプローチ**: テンプレート（型）を先に決め、型を埋めるためにリサーチする。
闇雲に調べるのではなく、「SRS に書く項目」を埋めるために必要な情報を狙い撃ちする。

---

## 1. 逆算アプローチの手順

### Step 1: SRS テンプレートの項目を確認

Phase 2 の SRS テンプレート（`02-srs.md`）を参照し、埋める必要がある項目を一覧化する。

### Step 2: 各項目に対して「何を調べれば埋まるか」を特定

```
SRS項目: 外部インターフェース → 調査: 使用APIの仕様、認証方式、レート制限
SRS項目: 非機能要件（性能） → 調査: 類似システムのベンチマーク、APIレスポンス時間
SRS項目: 制約条件 → 調査: 利用規約、法的制約、技術的制約
```

### Step 3: 調査項目をV1/V2に振り分けて実行

---

## 2. V1リサーチ（広く浅く、3観点並列）

### 3観点の並列調査

| 観点 | 調査内容 | ソース例 |
|---|---|---|
| **A. ツール/MCP/OSS** | 使えるツール、MCP サーバー、OSS ライブラリ | GitHub, npm, PyPI, MCP Hub |
| **B. API/ライブラリ/利用規約** | 外部 API の仕様、料金、制約、規約 | 公式ドキュメント, 料金ページ, ToS |
| **C. アーキテクチャ/コミュニティ** | 類似実装の構成、ベストプラクティス | Stack Overflow, Qiita, Zenn, Reddit |

### V1 実行ルール

- 各観点で **2ソース以上** を確認し、URL を記録する
- 調査時間の目安: 各観点 15-30分
- 不確実な情報は `[要V2確認]` マークを付ける
- 3観点は並列実行可能（依存関係なし）

## 3. 7つの必須リサーチカテゴリ

V1/V2 を通じて、以下の7カテゴリは必ず調査する。

| # | カテゴリ | 調査内容 | 必須度 |
|---|---|---|---|
| R1 | **公式API仕様** | エンドポイント、認証、リクエスト/レスポンス形式 | 必須 |
| R2 | **規約・ポリシー** | 利用規約、商用利用可否、データ保持ポリシー | 必須 |
| R3 | **ユーザー・市場** | 類似サービスの利用状況、ユーザーの声 | 推奨 |
| R4 | **競合** | 既存の類似サービス/ツール、差別化ポイント | 推奨 |
| R5 | **技術標準** | 関連する技術標準、ベストプラクティス | 必須 |
| R6 | **OSS/GitHub** | 関連OSSの活発度、スター数、最終更新日 | 必須 |
| R7 | **論文・記事** | 技術的な根拠となる論文や技術記事 | 任意 |

### 各カテゴリの最低要件

- R1: 使用する全外部APIの公式ドキュメントを確認
- R2: 商用利用・自動化に関する規約を確認（違反リスクの排除）
- R5: 採用技術の公式推奨アーキテクチャを確認
- R6: 採用OSSの最終コミット日が6ヶ月以内であることを確認

## 4. 外部API検証チェックリスト

外部APIを使用する場合、以下の項目を全て確認する。

| # | 確認項目 | 確認内容 | 結果 |
|---|---|---|---|
| 1 | **利用可能性** | APIが現在利用可能か、廃止予定はないか | |
| 2 | **認証方式** | APIキー/OAuth/Bearer等、認証の仕組み | |
| 3 | **レート制限** | 1分/1時間/1日あたりのリクエスト上限 | |
| 4 | **料金体系** | 無料枠、従量課金の単価、月額上限の有無 | |
| 5 | **サンドボックス** | テスト用の無料環境があるか | |
| 6 | **利用規約** | 自動化・商用利用・データ保存の可否 | |
| 7 | **SLA** | 稼働率保証、障害時の対応 | |
| 8 | **SDK/ライブラリ** | 公式SDK、コミュニティライブラリの有無 | |

### 検証結果の分類

- **利用可能**: 制約なし、または制約内で運用可能
- **条件付き利用可**: 制約あるが対処法がある（例: レート制限→リトライ実装）
- **利用不可**: 規約違反、廃止予定、コスト超過等

## 5. V2リサーチ（深掘り）

V1 の `[要V2確認]` 項目と、信頼度「低」の項目を深掘りする。

### V2 実行ルール

- V1 で不確実だった項目に集中する
- 公式ドキュメントを最優先ソースとする
- 実際にAPIを叩く、コードを動かす等の実地検証を含む
- 全項目を以下の3段階に分類する

### V2 分類基準

| 分類 | 意味 | 次のアクション |
|---|---|---|
| **確定** | 裏付けが取れた事実 | SRS にそのまま記載 |
| **推奨** | 有力だが他の選択肢もある | SRS に推奨案として記載、代替案も併記 |
| **要注意** | リスクがある、または不確実 | SRS にリスクとして記載、対策を検討 |

### 技術スタック確定

V2 完了時点で、以下の技術スタックを確定させる。

```markdown
## 技術スタック（確定）

| レイヤー | 技術 | バージョン | 選定理由 |
|---|---|---|---|
| 言語 | Python | 3.11+ | 社長の希望 + ライブラリ充実 |
| フレームワーク | FastAPI | 0.100+ | 非同期対応 + 自動ドキュメント |
| DB | SQLite | 3.40+ | 軽量、サーバー不要 |
| 外部API | OpenAI | v1 | 音声合成に使用 |
| ... | ... | ... | ... |
```

## 6. Phase 1 完了条件

### 完了チェックリスト

- [ ] V1: 3観点（ツール/API/アーキテクチャ）全てで2ソース以上確認済み
- [ ] V1: 7必須カテゴリのうち「必須」4カテゴリが調査済み
- [ ] V2: V1の `[要V2確認]` 項目が全て解消済み
- [ ] V2: 全項目が「確定/推奨/要注意」に分類済み
- [ ] 技術スタックが確定している
- [ ] 外部API検証チェックリストが全項目記入済み
- [ ] `research_v1.md` と `research_v2.md` が作成済み

### 完了できない場合

- 重要APIの仕様が不明 → 実地検証（サンドボックスでの試行）を実施
- 規約の解釈が曖昧 → 社長にエスカレーション（法的判断）
- 技術選定で迷い → 2案を比較表にして社長に選択肢提示
