# Phase 6: 実装

## 目的

Phase 5 で GO 判定を受けた SDD（設計書）に基づき、コードを実装する。
設計書に書かれていないコードは書かない。設計書と実装の乖離をゼロにする。

---

## 1. SDD 駆動実装の原則

### 基本ルール

- **設計書に書かれた通りに実装する**: SDD のコンポーネント構成、インターフェース、データモデルに忠実に従う
- **設計書にないものは実装しない**: 「あった方がいい」で機能を追加しない
- **設計変更が必要なら Phase 3 に戻る**: 実装中に設計の問題が見つかったら、コードで回避せず設計を修正する

### 実装順序

```
1. ディレクトリ構成を SDD 通りに作成
2. 各コンポーネントのインターフェース（関数シグネチャ）を先に実装
3. アダプター（外部API連携部分）を DRY_RUN モードで実装
4. コアロジック（内部処理）を実装
5. CLI/エントリポイントを実装
6. 設定管理を実装
7. テストコードを実装
```

## 2. DRY_RUN デフォルト true

### 実装ルール

- 環境変数 `DRY_RUN` のデフォルト値は **true**
- `DRY_RUN=true` の場合、外部APIは呼び出さずモックレスポンスを返す
- `DRY_RUN=false` に切り替えるには明示的な設定が必要
- テスト時は常に `DRY_RUN=true` で実行

### 実装パターン

```python
import os

DRY_RUN = os.environ.get("DRY_RUN", "true").lower() == "true"

def call_external_api(request):
    if DRY_RUN:
        return mock_response(request)
    return real_api_call(request)
```

### DRY_RUN モックの品質基準

- モックレスポンスは実際のAPIレスポンスと同じ構造にする
- モックデータは現実的な値を使う（空文字列やダミー値は避ける）
- モック使用時はログに `[DRY_RUN]` を明記する

## 3. アダプターパターン

### 全ての外部サービスはアダプター経由

```
アプリケーションコード → アダプター → 外部サービス
                          ↓（DRY_RUN時）
                        モック
```

### アダプターの構造

```python
class BaseAdapter:
    """全アダプターの基底クラス"""
    
    def __init__(self):
        self.dry_run = os.environ.get("DRY_RUN", "true").lower() == "true"
    
    def execute(self, request):
        """共通の実行メソッド"""
        self._log_request(request)
        
        if self.dry_run:
            result = self._mock_execute(request)
            self._log_response(result, dry_run=True)
            return result
        
        result = self._real_execute(request)
        self._log_response(result, dry_run=False)
        return result
    
    def _mock_execute(self, request):
        """サブクラスで実装: モックレスポンスを返す"""
        raise NotImplementedError
    
    def _real_execute(self, request):
        """サブクラスで実装: 実際のAPI呼び出し"""
        raise NotImplementedError
```

## 4. 最小依存原則

### 依存追加の判定基準

| 判断 | 条件 |
|---|---|
| **追加OK** | 標準ライブラリでは実現不可能、または実装コストが著しく高い |
| **追加NG** | 標準ライブラリで実現可能、またはコード10行以内で書ける |
| **要検討** | 便利だが必須ではない、代替手段がある |

### 依存追加時の必須記録

```markdown
## 依存追加記録

| パッケージ | バージョン | 追加理由 | 代替案 | ADR |
|---|---|---|---|---|
| requests | 2.31+ | HTTP通信 | urllib(標準)は低レベルすぎ | ADR-005 |
| pydantic | 2.0+ | データバリデーション | dataclass+手動検証は工数大 | ADR-006 |
```

## 5. タスク委譲（大規模実装時）

実装範囲が大きい場合、タスクを分割して委譲する。

### 分割基準

| 規模 | 判断 | 対応 |
|---|---|---|
| **小規模**（ファイル5個以下） | 1人で実装 | 分割不要 |
| **中規模**（ファイル6-15個） | 機能単位で分割 | 2-3タスクに分割 |
| **大規模**（ファイル16個以上） | コンポーネント単位で分割 | コンポーネント毎にタスク化 |

### タスク分割テンプレート

```markdown
## タスク: [タスク名]

- 対象コンポーネント: [C-XX]
- 対応要件: [FR-XXX-001]
- 依存タスク: [なし / タスクY完了後]
- 成果物: [ファイル一覧]
- 完了条件: [テスト PASS + レビュー通過]
```

## 7. 境界値8カテゴリチェック

実装する全ての入力値に対して、以下の8カテゴリで境界値をチェックする。

| # | カテゴリ | 例 | テストケース |
|---|---|---|---|
| 1 | **最小値** | 文字数の下限 | 入力 = 下限値 → 正常処理 |
| 2 | **最小値-1** | 下限未満 | 入力 = 下限-1 → エラー |
| 3 | **最大値** | 文字数の上限 | 入力 = 上限値 → 正常処理 |
| 4 | **最大値+1** | 上限超過 | 入力 = 上限+1 → エラー |
| 5 | **空/null** | 入力なし | 入力 = 空 → エラー |
| 6 | **型不正** | 数値に文字列 | 入力 = "abc" → エラー |
| 7 | **特殊文字** | 絵文字、制御文字 | 入力に絵文字 → 正常 or エラー |
| 8 | **巨大入力** | 想定の10倍 | 入力 = 上限の10倍 → エラー（メモリ溢れしない） |

### 境界値チェック実施記録

```markdown
| 入力項目 | 下限 | 上限 | 空 | 型不正 | 特殊文字 | 巨大 | 結果 |
|---|---|---|---|---|---|---|---|
| 台本テキスト | 500文字 OK | 10000文字 OK | エラー OK | エラー OK | 正常 OK | エラー OK | PASS |
| ファイルパス | 1文字 OK | 255文字 OK | エラー OK | - | スペース OK | エラー OK | PASS |
```

## 8. セキュリティチェックリスト

### 8-1. シークレット管理

- [ ] APIキーをソースコードにハードコードしていない
- [ ] APIキーは環境変数ファイルのみで管理している
- [ ] 環境変数ファイルが `.gitignore` に追加されている
- [ ] ログにAPIキーやパスワードが出力されない
- [ ] エラーメッセージにAPIキーが含まれない
- [ ] テスト用のAPIキーと本番用を分離している

### 8-2. 入力バリデーション

- [ ] 全ての外部入力にバリデーションを実装している
- [ ] SQLインジェクション対策（パラメータバインド）
- [ ] パストラバーサル対策（ファイルパスの正規化）
- [ ] コマンドインジェクション対策（シェル呼び出し回避）
- [ ] 入力サイズの上限チェック

### 8-3. エラーメッセージ

- [ ] エラーメッセージに内部情報（パス、設定値、API応答の詳細）を含めない
- [ ] ユーザー向けエラーメッセージは具体的だが安全
- [ ] デバッグ情報はログファイルのみに出力

### 8-4. 依存関係監査

- [ ] 全依存パッケージのバージョンを固定している（requirements.txt / lock file）
- [ ] 既知の脆弱性がないか確認済み（`pip-audit` / `safety`）
- [ ] 不要な依存パッケージを除去している

### 8-5. APIキー取り扱いルール

```
禁止事項:
  - ソースコードへのハードコード
  - テストコードへの埋め込み
  - コミットメッセージへの記載
  - ログファイルへの出力
  - エラーメッセージへの含有

許可される方法:
  - 環境変数ファイル経由での読み込み（実行時のみ）
  - 環境変数からの読み込み（os.environ）
  - DRY_RUN=true 時はキー不要で動作

テスト時の整合性:
  - テストは DRY_RUN=true で実行（実APIキー不要）
  - APIキーの存在チェックテストは、値を検証しない（set/not set のみ）
  - CI/CD 環境では DRY_RUN=true を強制
```
