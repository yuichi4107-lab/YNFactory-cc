# 開発破綻リスク5層モデル

## 概要

AI駆動開発は従来のソフトウェア開発と異なるポイントで破綻する。
本文書は、破綻リスクを5つの層（レイヤー）に分類し、各層で何を監視し、何を防ぐかを定義する。

例え話：建物の耐震設計と同じ。地盤（Layer A）が緩ければ、どんなに頑丈な柱（Layer C）を立てても倒れる。
各層を順番に固めることが、プロジェクト全体の安定性を決める。

---

## 1. 5層の全体像

```
Layer E: 運用後リスク（規約変更・API変更・復旧不能）
Layer D: 検証リスク（AI過信・完了誤認・回帰未実施）
Layer C: 実装リスク（本番破壊・自動投稿暴走・コスト暴走）
Layer B: 文書構築リスク（根拠なし・テスト不能・コンテキスト枯渇）
Layer A: 設計前リスク（曖昧入力・実現不可能・スコープ肥大）
```

下の層ほど基盤的。上の層の問題は下の層の不備から生じることが多い。

---

## 2. Layer A: 設計前リスク

プロジェクト開始前、要件定義の段階で発生するリスク。

| リスク | 説明 | 検出方法 | 対策 |
|---|---|---|---|
| **曖昧入力** | 社長の要件が抽象的すぎて仕様に落とせない | P-00 要件定義プロンプトで具体化 | 5W1H チェック、具体例3つ以上 |
| **実現不可能** | 技術的・法的に実現できない要件 | Layer 2 文書構築時の調査 | 事前 PoC、法務チェック |
| **スコープ肥大** | 「ついでにこれも」で際限なく膨らむ | Phase 0 完了時のスコープ確認 | MoSCoW 優先度、MVP 定義 |
| **前提知識不足** | 対象ドメインの理解が浅い | リサーチフェーズの品質 | research-system 等で事前調査 |

### Layer A の完了判定

- [ ] 要件が 5W1H で記述されている
- [ ] 技術的実現可能性が確認済み
- [ ] スコープが MoSCoW で優先度付けされている
- [ ] MVP（最小実行可能プロダクト）が定義されている

---

## 3. Layer B: 文書構築リスク

仕様書・設計書を作成する段階で発生するリスク。

| リスク | 説明 | 検出方法 | 対策 |
|---|---|---|---|
| **根拠なし仕様** | 調査せずに書いた仕様 | レビュー時に一次ソース要求 | 全仕様に根拠リンク必須 |
| **テスト不能仕様** | 合格基準が曖昧で検証できない | テスト設計時に発覚 | 機械判定可能な閾値を必須化 |
| **コンテキスト枯渇** | AIのコンテキスト上限に到達 | トークン使用率監視 | セッション分割、/compact |
| **文書間矛盾** | SRS と SDD で異なる仕様記述 | クロスリファレンスチェック | SSoT 原則、変更履歴管理 |
| **過剰設計** | 紙の上で完璧を目指しすぎる | ラウンド数の監視 | test-granularity ルール準拠 |

### Layer B の完了判定

- [ ] 全仕様に根拠（一次ソース or 調査結果）がある
- [ ] 全仕様にテスト可能な合格基準がある
- [ ] 文書間の矛盾がクロスチェック済み
- [ ] コンテキスト使用率が 70% 未満

---

## 4. Layer C: 実装リスク

コードを書いて動かす段階で発生するリスク。最も直接的な被害が出る層。

| リスク | 説明 | 検出方法 | 対策 |
|---|---|---|---|
| **本番破壊** | 本番環境のデータ・設定を破壊 | 環境分離の確認 | dev/staging/prod 完全分離 |
| **自動投稿暴走** | 自動投稿が止まらない、誤投稿 | dry-run テスト | 必ず dry-run → 承認 → 本番の3段階 |
| **コスト暴走** | API呼び出しの無限ループ等 | コスト上限設定 | rate limit、月次予算アラート |
| **秘密情報漏洩** | APIキー・パスワードのコミット | git hook、レビュー | 環境変数ファイル管理、ATM方式 |
| **依存関係破壊** | ライブラリ更新で既存機能が壊れる | CI/CD テスト | lock ファイル管理、更新テスト |

### Layer C の完了判定

- [ ] 本番環境と開発環境が完全分離されている
- [ ] 自動投稿系は dry-run が実装されている
- [ ] API呼び出しに rate limit が設定されている
- [ ] 秘密情報がコードにハードコードされていない
- [ ] 依存関係の lock ファイルが管理されている

---

## 5. Layer D: 検証リスク

テスト・レビュー段階で発生するリスク。

| リスク | 説明 | 検出方法 | 対策 |
|---|---|---|---|
| **AI過信** | AIの出力を無条件に信頼 | 馴れ合いチェック | Codex⇄Opus 非対称レビュー |
| **完了誤認** | 未完了なのに「完了」と報告 | 完了チェックリスト照合 | 機械判定可能な完了条件 |
| **回帰未実施** | 修正後に既存機能のテストをしない | CI/CD パイプライン | 回帰テストスイート必須 |
| **テストの偏り** | 正常系のみテスト、異常系が抜け | boundary-checklist 照合 | 8カテゴリ境界ケース必須 |
| **統計的誤判定** | サンプル数不足で合格判定 | 統計的検定 | 最低サンプル数の事前定義 |

### Layer D の完了判定

- [ ] Codex⇄Opus レビューが完了している
- [ ] 完了チェックリストが全項目クリア
- [ ] 回帰テストが実行済み
- [ ] 境界ケース8カテゴリが網羅されている

---

## 6. Layer E: 運用後リスク

リリース後に発生するリスク。開発時には予見しにくい。

| リスク | 説明 | 検出方法 | 対策 |
|---|---|---|---|
| **規約変更** | 外部サービスの利用規約が変わる | 定期的な規約確認 | 規約変更監視、代替サービス準備 |
| **API変更** | 外部APIの仕様変更・廃止 | バージョン監視 | API抽象化層、移行計画 |
| **復旧不能** | 障害発生時にデータを復元できない | 復旧訓練 | バックアップ、リストア手順書 |
| **スケール問題** | ユーザー増加で性能劣化 | 負荷テスト | 事前のスケール設計 |
| **ドリフト** | 運用中に仕様と実態が乖離 | 定期 H-REVIEW | P-13 ドリフト検出プロンプト |

### Layer E の完了判定

- [ ] 外部サービスの規約確認が完了している
- [ ] API変更時の移行手順が文書化されている
- [ ] バックアップ・リストア手順が検証済み
- [ ] ドリフト検出の仕組みが稼働している

---

## 7. 3つの致命的ギャップ（Critical Gaps）

5層モデルの中で、特に見落とされやすい3つのギャップ。

### Gap 1: Layer A → B のギャップ（要件→仕様の翻訳ミス）

社長の意図と仕様書の記述がずれる。最も頻度が高く、最も発見が遅い。
対策：仕様書完成時に社長へ「高校生説明」で確認を取る。

### Gap 2: Layer B → C のギャップ（仕様→実装の解釈ミス）

仕様書は正しいが、実装が仕様と異なる。AIが仕様を「解釈」して独自実装する。
対策：実装後に仕様書との差分チェックを行う。

### Gap 3: Layer D → E のギャップ（テスト→運用の環境差）

テスト環境では動くが、本番環境では動かない。環境変数、権限、ネットワーク構成の差異。
対策：staging 環境を本番と同一構成にする。

## 9. 層別の対応優先度

リスクが複数の層で同時に検出された場合、下の層から順に対応する。

```
対応順: A → B → C → D → E
```

Layer A の問題が残っている状態で Layer C を修正しても、根本原因が解消されないため無駄になる。
「地盤を固めてから柱を立てる」の原則を守る。
