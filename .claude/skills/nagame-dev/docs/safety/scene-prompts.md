# シーン別プロンプトカタログ P-00〜P-16

## 概要

nagame-dev の各フェーズ・シーンで使用するプロンプトのカタログ。
各プロンプトは「いつ使うか」「何をするか」「注意点」を明示する。

例え話：料理のレシピ集と同じ。「カレーを作りたい」ならカレーのページを開く。
全レシピを暗記する必要はなく、必要な時に必要なページを参照する。

## 2. 各プロンプト詳細

### P-00: 要件定義

**いつ使うか:** プロジェクト開始時。社長から「こういうの作りたい」と言われた時。

**何をするか:**
- 社長の要望を 5W1H で構造化する
- MoSCoW 優先度（Must/Should/Could/Won't）で分類する
- MVP（最小実行可能プロダクト）の範囲を定義する
- 技術的実現可能性の初期判定を行う

**注意点:**
- 社長の言葉を勝手に解釈しない。不明点は質問する
- 「ついでにこれも」のスコープ肥大を防ぐ
- 実現不可能な要件は根拠を示して早期にフィードバック

---

### P-01-A: セッション開始

**いつ使うか:** 新しいセッション（壁打ち）の開始時。

**何をするか:**
- 引き継ぎプロンプトの [A][B][C] を読了する
- 読了完了報告を社長に提出する
- 今回の着手タスクを提示し、社長の承認を得る

**注意点:**
- handover-template.md に準拠する
- 議論対象資産 [C] は全行読了必須（ls や grep だけでは読了とみなさない）
- harness 自動投入済みファイルは二重ロード不要（§3-bis 例外A）

---

### P-01-B: セッション中断

**いつ使うか:** 緊急事態でセッションを中断する時。

**何をするか:**
- 現在の作業状態を最小限で記録する
- 未保存の変更点を列挙する
- 中断理由を記録する

**注意点:**
- 中断は緊急時のみ。通常は P-01-C（正常終了）を使う
- 最低限「何をしていたか」「何が未完了か」を記録する

---

### P-01-C: セッション終了

**いつ使うか:** セッションを正常終了する時。

**何をするか:**
- セッションの成果をサマリーにまとめる
- HOLD 項目を整理する
- 次セッション向けの引き継ぎプロンプトを作成する

**注意点:**
- コンテキスト 70% に達する前に開始する
- 引き継ぎプロンプトは handover-template.md に準拠
- 議論対象資産 [C] を必ず明示する（空欄禁止）

---

### P-02-A: バグ報告

**いつ使うか:** バグが発見された時の初期報告。

**何をするか:**
- 症状を構造化して記述する（再現手順・期待動作・実際の動作）
- 影響範囲を判定する（Blocker/Must/Should/Later）
- スクリーンショット・ログを添付する

**注意点:**
- 推測で原因を書かない。事実のみ記述する
- 「動かない」だけでは不十分。再現手順を必ず含める

---

### P-02-B: バグ分析

**いつ使うか:** P-02-A の報告を受けて、根本原因を分析する時。

**何をするか:**
- 再現手順を実行して症状を確認する
- 根本原因（Root Cause）を特定する
- 影響範囲を調査する（他の機能への波及）

**注意点:**
- 表面的な原因ではなく根本原因まで掘り下げる
- 「なぜ5回」（5 Whys）で深掘りする
- 分析結果に推測が含まれる場合は明示する

---

### P-03-A: 修正計画

**いつ使うか:** バグの根本原因が特定され、修正方法を計画する時。

**何をするか:**
- 修正案を複数提示する（最低2案）
- 各案のリスク・工数・影響範囲を比較する
- 推奨案を根拠付きで提示する
- 回帰テストの範囲を定義する

**注意点:**
- codex-review.md に従い、修正前に Codex レビューを実施する
- 修正が他の機能に影響しないか、boundary-checklist で確認する

---

### P-04-A: コードレビュー

**いつ使うか:** 実装完了後、Codex⇄Opus 非対称レビューを実行する時。

**何をするか:**
- Codex が技術的観点で GO/NO-GO を判定する
- Opus が事業的観点で ACCEPT/REJECT を判定する
- 最大3ラウンドで収束させる

**注意点:**
- codex-opus-protocol.md に完全準拠する
- 馴れ合い禁止ルールを意識する
- 社長への報告は高校生説明で行う

---

### P-05-A: テスト実行

**いつ使うか:** テストスイートを実行し、結果を分析する時。

**何をするか:**
- テストスイートを実行する
- 失敗したテストの原因を分析する
- テストカバレッジを確認する
- 結果を構造化して報告する

**注意点:**
- 全テスト PASS でも、境界ケースの漏れがないか確認する
- テスト結果の「偽の成功」（テスト自体が不十分）に注意する

---

### P-05-C: テスト設計

**いつ使うか:** Phase 4 でテストケースを設計する時。

**何をするか:**
- 正常系・異常系・境界ケースを網羅的に設計する
- boundary-checklist.md の8カテゴリを参照する
- 合格基準を機械判定可能な形で定義する

**注意点:**
- test-granularity.md に従い、段階に応じたテスト密度にする
- 紙の段階で完全実装しない（仕様だけ書く）

---

### P-07-A: セッション切替（送信側）

**いつ使うか:** コンテキスト 70% に達し、セッション切り替えを行う時（現セッション側）。

**何をするか:**
- 引き継ぎプロンプトを handover-template.md 形式で作成する
- [A][B][C] の必読ファイルを明示する
- 未完了タスクと HOLD 項目を整理する

**注意点:**
- [C] 議論対象資産は空欄禁止
- 引き継ぎプロンプトは500文字サマリーではなく、必要な詳細を含める

---

### P-07-B: セッション切替（受信側）

**いつ使うか:** 新セッションで引き継ぎプロンプトを受領した時。

**何をするか:**
- P-01-A と同様の読了・報告・着手伺いを行う
- 前セッションの HOLD 項目を確認する
- 不明点があれば社長に質問する

**注意点:**
- P-01-A と同じ注意点に加え、前セッションの文脈を正確に引き継ぐ

---

### P-08-A: Phase移行（完了判定）

**いつ使うか:** 現フェーズの完了判定を行う時。

**何をするか:**
- 現フェーズの全成果物が揃っているか確認する
- 完了チェックリスト（risk-5layers.md）を照合する
- 未解決の HOLD 項目を次フェーズに引き継ぐ

**注意点:**
- 「だいたいできた」は完了ではない。機械判定可能な基準で判定する
- HOLD 項目が Blocker レベルなら Phase 移行不可

---

### P-08-B: Phase移行（開始準備）

**いつ使うか:** 次フェーズの開始準備を行う時。

**何をするか:**
- 次フェーズの前提条件が満たされているか確認する
- 必要なリソース（ファイル・環境・権限）を準備する
- 次フェーズの目標とスコープを確認する

**注意点:**
- 前フェーズの完了判定（P-08-A）が済んでいること
- 前提条件が欠けている場合は Phase 移行を保留する

---

### P-13: ドリフト検出

**いつ使うか:** 運用中に仕様と実態の乖離が疑われる時。

**何をするか:**
- 仕様書と実際の動作を比較する
- 乖離箇所を特定し、原因を分析する
- 仕様を更新するか、実装を修正するか判断する

**注意点:**
- ドリフトは徐々に進行するため、定期的な実行を推奨
- 仕様側が古い場合と実装側が間違っている場合の両方を考慮する

---

### P-14: ハーネス更新

**いつ使うか:** CONSTRAINTS ファイルや成果物テンプレートを更新する時。

**何をするか:**
- 変更内容を明確にする
- 既存プロジェクトへの影響を評価する
- 更新後のバリデーションを実行する

**注意点:**
- CONSTRAINTS の変更は全プロジェクトに影響する可能性がある
- 変更履歴を必ず記録する

---

### P-15: SRS生成

**いつ使うか:** Phase 2 でソフトウェア要件仕様書を生成する時。

**何をするか:**
- P-00 の要件定義結果をベースに SRS を構造化する
- 機能要件・非機能要件を網羅する
- 各要件にテスト可能な合格基準を付与する

**注意点:**
- 全要件に根拠を付与する（根拠なし仕様は Layer B リスク）
- 合格基準は機械判定可能な形式にする

---

### P-16: SDD生成

**いつ使うか:** Phase 3 でソフトウェア設計文書を生成する時。

**何をするか:**
- SRS をベースにアーキテクチャ設計を行う
- コンポーネント図・データフロー図を作成する
- API 設計・データモデルを定義する

**注意点:**
- SRS との整合性を保つ（Gap 2 防止）
- 過剰設計を避ける（MVP に必要な範囲に絞る）

---

## 3. プロンプト選択フローチャート

```
何をしたい？
  ├─ プロジェクトを始めたい → P-00
  ├─ セッションを開始/終了したい
  │   ├─ 開始 → P-01-A or P-07-B
  │   ├─ 中断 → P-01-B
  │   └─ 終了 → P-01-C or P-07-A
  ├─ バグを報告/修正したい
  │   ├─ 報告 → P-02-A
  │   ├─ 分析 → P-02-B
  │   └─ 修正 → P-03-A
  ├─ レビュー/テストしたい
  │   ├─ コードレビュー → P-04-A
  │   ├─ テスト設計 → P-05-C
  │   └─ テスト実行 → P-05-A
  ├─ Phase を移行したい
  │   ├─ 完了判定 → P-08-A
  │   └─ 開始準備 → P-08-B
  ├─ 仕様書を作りたい
  │   ├─ SRS → P-15
  │   └─ SDD → P-16
  └─ 運用/保守
      ├─ ドリフト検出 → P-13
      └─ ハーネス更新 → P-14
```
