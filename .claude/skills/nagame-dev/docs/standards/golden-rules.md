# 7つの黄金ルール

本ドキュメントは nagame-dev の全フェーズに適用される絶対ルールである。
フェーズ固有のルールと矛盾した場合、本ドキュメントが優先する。

---

## ルール一覧

### 1. 根拠IDがないMust要件は作らない

**ルール本文**: 全てのMust要件には、一次ソースに接続する Evidence ID を付与すること。Evidence ID のないMust要件の作成を禁止する。

**なぜ必要か**: 根拠のないMust要件は「それっぽいが検証不能な要件」を生む。見た目が整っているだけに、レビューで通過しやすく、実装後に「実は不要だった」「前提が間違っていた」と判明する。

**違反した場合**: 実装後に要件の正当性を証明できず、手戻りが発生する。最悪の場合、不要な機能を本番リリースしてしまい、保守コストだけが残る。

**適用タイミング**: Phase 2（リサーチ）完了時、Phase 3（SRS作成）全体、Phase 5（レビュー）全ラウンド

---

### 2. テストIDがないMust要件は実装へ進めない

**ルール本文**: 全てのMust要件には TC-* （テストケースID）を接続すること。TC-* が未接続のMust要件が1件でもある状態で実装フェーズへ進むことを禁止する。

**なぜ必要か**: 「作れる・試せる・止められる」の3条件を満たさない要件は、実装しても合否判定ができない。合否判定できない要件は永遠に「完了」にならない。

**違反した場合**: 実装完了の判定基準がなくなり、「動いているように見えるが正しいか不明」な状態でリリースされる。受入テストが形骸化する。

**適用タイミング**: Phase 3（SRS作成）完了時、Phase 5（レビュー）のGO判定時

---

### 3. dry-runがない破壊的操作はRedにする

**ルール本文**: 本番DB直接操作、自動投稿（SNS/メール/課金）、データ削除、外部サービスへの書き込み等の破壊的操作は、dry-run / sandbox / 承認ゲートのいずれかが設計されていない限り、RYGゲートでRed判定とする。

**なぜ必要か**: 不可逆操作を安全装置なしで実行すると、1回のバグで取り返しのつかない損害が発生する。課金事故、誤投稿、データ消失は事後修復が極めて困難。

**違反した場合**: 本番環境で意図しない課金・投稿・削除が実行される。顧客データの消失、規約違反、金銭的損害が発生する可能性がある。

**適用タイミング**: Phase 4（SDD/ハーネス設計）、Phase 5（レビュー）、Phase 6（実装）全体

---

### 4. Yellowは本番禁止、隔離PoCのみ許可

**ルール本文**: RYGゲートでYellow判定の項目は、sandbox / PoC / 追加調査のみ許可する。本番投入および不可逆操作を禁止する。Yellowを「ほぼGreen」と解釈することを禁止する。

**なぜ必要か**: Yellowは「条件を満たせばGreenになり得る」状態であり、「たぶん大丈夫」ではない。条件未達のまま進めると、未検証のリスクを本番に持ち込む。

**違反した場合**: 未検証のリスクが本番環境に入り込み、問題発覚時には既に不可逆な状態になっている。「Yellowだったが問題なかった」は結果論であり、プロセスとしては失敗。

**適用タイミング**: Phase 5（レビュー）のRYG判定時、Phase 6（実装）のデプロイ判断時

---

### 5. レビュー指摘は必ず再リサーチIDへ変換する

**ルール本文**: レビューで発見された問題は、コード修正だけで閉じず、必ず再リサーチID（re-research-triggers.md 参照）に変換すること。調査結果を要件・仕様・テスト・リスク台帳のいずれかに反映する。

**なぜ必要か**: コード修正だけで閉じると、「なぜその問題が起きたのか」「他に同種の問題がないか」が検証されない。根本原因を放置したまま表面的な修正を繰り返すことになる。

**違反した場合**: 同種の問題が別の箇所で再発する。修正の妥当性を検証する根拠がないため、修正自体が新たなバグを生む可能性がある。

**適用タイミング**: Phase 5（レビュー）の全ラウンド、Phase 6（実装）中のコードレビュー

---

### 6. コード修正だけで閉じず仕様・テスト・リスク台帳も更新する

**ルール本文**: コードを修正した場合、その修正が影響する仕様書（SRS/SDD）、テスト計画（TEST_PLAN）、リスク台帳（RISK_REGISTER）を必ず確認し、必要に応じて更新すること。

**なぜ必要か**: コードと文書が乖離すると、次回のレビューやメンテナンスで「文書と実装が違う」状態が発生する。文書が信頼できなくなると、文書ベースの品質管理が崩壊する。

**違反した場合**: 仕様書と実装の乖離が蓄積し、どちらが正しいか判断できなくなる。新規メンバーや将来の自分が、古い仕様書を信じて誤った判断を下す。

**適用タイミング**: Phase 5（レビュー）での修正時、Phase 6（実装）でのコード変更時

---

### 7. Redは「壊れる前に止められた成功」として扱う

**ルール本文**: RYGゲートでRed判定を出すことは失敗ではなく、破綻防止の証拠として扱う。Red判定を出したことを理由に、担当者やプロセスを否定してはならない。

**なぜ必要か**: Red判定を「失敗」と扱うと、判定者がRedを出すことを躊躇し、本来Redであるべき項目がYellowやGreenに甘くなる。これは品質ゲートの形骸化を招く。

**違反した場合**: Red判定が出にくくなり、未検証のリスクがGreen扱いで本番に入る。品質ゲートが機能しなくなり、本番障害が増加する。

**適用タイミング**: Phase 5（レビュー）全体、チーム運営・振り返り全般

---

## 黄金ルール適用チェックリスト

各フェーズ完了時に以下を確認する。1つでもNGがあればフェーズ完了を宣言できない。

| # | チェック項目 | 確認方法 |
|---|---|---|
| 1 | 全Must要件にEvidence IDが接続されているか | SRS の Evidence Matrix を検索 |
| 2 | 全Must要件にTC-*が接続されているか | Traceability Matrix で未接続を検索 |
| 3 | 破壊的操作に全てdry-run/sandbox/承認ゲートがあるか | SDD の HARNESS セクションを確認 |
| 4 | Yellow判定の項目が本番操作に含まれていないか | RYG判定表を確認 |
| 5 | レビュー指摘が全て再リサーチIDに変換されているか | reproposal_log.md を確認 |
| 6 | コード修正に伴う文書更新が完了しているか | 変更履歴と差分を確認 |
| 7 | Red判定が適切に記録・対処されているか | PROGRESS.md を確認 |

---

## 例外

- 社長が明示的に「このルールは今回適用しない」と指示した場合のみ、該当ルールをスキップできる
- スキップした場合、その判断と理由を PROGRESS.md に記録すること
- 黄金ルール全体の無効化は不可（個別ルール単位でのみスキップ可能）
