# ID接続体系

本ドキュメントは nagame-dev で使用する全ID体系を定義する。
全ての成果物はIDで相互接続され、追跡可能性（トレーサビリティ）を担保する。

---

## 1. ID接頭辞一覧（14種）

| 接頭辞 | 分類 | 命名規則 | 例 | 用途 |
|---|---|---|---|---|
| OBJ | 目的 | OBJ-NNN | OBJ-001 | プロジェクトの目的・ゴール定義 |
| USR | 利用者 | USR-NNN | USR-001 | ペルソナ・利用者分類 |
| FLOW | 業務フロー | FLOW-NNN | FLOW-001 | 業務フロー・ユースケース |
| FUNC / FR | 機能要件 | FR-{機能群}-NNN | FR-AUTH-001 | 機能要件の定義 |
| DATA | データ | DATA-NNN | DATA-001 | データモデル・スキーマ定義 |
| API | 外部連携 | API-{サービス名}-NNN | API-STRIPE-001 | 外部API連携の定義 |
| NFR | 非機能 | NFR-{区分}-NNN | NFR-PERF-001 | 非機能要件（性能・可用性等） |
| SEC | セキュリティ | SEC-NNN | SEC-001 | セキュリティ要件 |
| OPS | 運用 | OPS-NNN | OPS-001 | 運用・保守要件 |
| TEST / TC | テスト | TC-{対象要件ID} | TC-FR-AUTH-001 | テストケース定義 |
| ACC | 受入基準 | ACC-{対象要件ID} | ACC-FR-AUTH-001 | 受入基準の定義 |
| RISK | リスク | RISK-NNN | RISK-001 | リスク台帳エントリ |

## 2. 要件ID台帳（Requirements ID Ledger）の必須フィールド

全ての要件IDは以下のフィールドを持つ。空欄は許容しない（該当なしの場合は「N/A」と明記）。

| # | フィールド名 | 説明 | 必須/任意 |
|---|---|---|---|
| 1 | 要件ID | 一意の識別子（上記命名規則に従う） | 必須 |
| 2 | 分類 | 機能/非機能/セキュリティ/運用 等 | 必須 |
| 3 | 要件名 | 要件の短縮名（30文字以内推奨） | 必須 |
| 4 | 要件本文 | 要件の詳細記述 | 必須 |
| 5 | 背景理由 | なぜこの要件が必要か | 必須 |
| 6 | 優先度 | MoSCoW（Must/Should/Could/Won't） | 必須 |
| 7 | 対象フェーズ | V1/V2/Later | 必須 |
| 8 | 関連画面 | 対応する画面ID（該当なしはN/A） | 必須 |
| 9 | 関連データ | 対応するDATA-*ID | 必須 |
| 10 | 受入基準 | ACC-*ID（機械判定可能な合格基準） | 必須 |
| 11 | 検証方法 | TC-*ID（テストケースへの接続） | 必須 |
| 12 | 例外条件 | 想定される例外とその処理 | 必須 |
| 13 | 責任者 | 要件のオーナー | 必須 |
| 14 | 状態 | Draft/Approved/Implemented/Verified | 必須 |
| 15 | 変更履歴 | 変更日・変更者・変更内容 | 必須 |

## 3. ID接続ルール（優先度別）

### Must要件（最も厳格）

Must要件は以下の全てが接続されていなければ実装フェーズへ進めない。

```
Must要件 ──→ Evidence ID（根拠）   ... 黄金ルール#1
Must要件 ──→ ACC-*（受入基準）     ... 合否判定可能性
Must要件 ──→ TC-*（テストケース）  ... 黄金ルール#2
Must要件 ──→ RISK-*（リスク）      ... リスク認識
```

### Should要件

```
Should要件 ──→ ACC-*（受入基準）    ... 必須
Should要件 ──→ TC-*（テストケース） ... 必須
Should要件 ──→ Evidence ID          ... 推奨（なくてもブロックしない）
```

### Could/Won't要件

```
Could要件 ──→ ACC-*（受入基準）     ... 推奨
Won't要件 ──→ 除外理由の記録       ... 必須
```

## 4. トレーサビリティマトリクス

全IDの接続関係を以下のマトリクス形式で管理する。

```
要件ID → 根拠ID → テストID → リスクID → 実装計画ID
```

### マトリクスの維持ルール

| ルール | 説明 |
|---|---|
| 孤立ID警告 | どのIDにも接続されていないIDは警告として報告する |
| 双方向接続 | 要件→テストだけでなく、テスト→要件の逆引きも維持する |
| 変更時の波及確認 | 1つのIDを変更したら、接続先の全IDへの影響を確認する |
| 削除時の理由記録 | IDを削除する場合、削除理由と影響範囲を記録する |

### マトリクス例

| 要件ID | 根拠ID | ACC-* | TC-* | RISK-* | PLAN-* | 状態 |
|---|---|---|---|---|---|---|
| FR-AUTH-001 | EV-API-001 | ACC-FR-AUTH-001 | TC-FR-AUTH-001 | RISK-003 | PLAN-002 | Approved |
| FR-PAY-001 | EV-STRIPE-001 | ACC-FR-PAY-001 | TC-FR-PAY-001 | RISK-001 | PLAN-005 | Draft |
| NFR-PERF-001 | EV-BENCH-001 | ACC-NFR-PERF-001 | TC-NFR-PERF-001 | RISK-007 | PLAN-010 | Approved |

---

## 5. ID採番ルール

| ルール | 説明 |
|---|---|
| 連番は3桁ゼロ埋め | 001, 002, ... 999 |
| 欠番は許容する | 削除されたIDの番号は再利用しない |
| 機能群名は英大文字 | AUTH, PAY, NOTIF, ADMIN 等 |
| サービス名は公式名準拠 | STRIPE, OPENAI, SLACK 等（全大文字） |
| ラウンド番号はR+数字 | R1, R2, R3 |

## 6. 接続不備の検出と対処

### 自動検出すべきパターン

| パターン | 検出方法 | 対処 |
|---|---|---|
| Must要件にEvidence IDなし | SRSの全Must要件をスキャン | Phase進行禁止、再リサーチ |
| Must要件にTC-*なし | Traceability Matrixで未接続検索 | Phase進行禁止、テスト設計 |
| 孤立テストケース | TC-*から要件IDへの逆引き不可 | 対応要件の確認または削除 |
| 孤立リスク | RISK-*から要件IDへの逆引き不可 | 対応要件の確認または削除 |
| 重複ID | 同一IDが2箇所以上で定義 | 即座に統合・一意性を回復 |

### 対処の優先順位

1. **重複ID** → 即座に修正（データ整合性の破壊）
2. **Must要件の接続不備** → Phase進行前に必ず修正
3. **Should要件の接続不備** → 同一Phase内で修正
4. **孤立ID** → 警告として記録、次回レビューで対処

---

## 7. 変更管理

IDに変更が発生した場合の手順:

1. 変更対象IDの変更履歴フィールドを更新
2. トレーサビリティマトリクスで接続先を確認
3. 接続先の各IDへの影響を評価
4. 影響があるIDの状態を「要確認」に変更
5. 影響範囲の修正が完了したら状態を戻す

**禁止事項**: IDの意味を変えて番号を使い回すこと（例: FR-AUTH-001 の内容を全く別の要件に書き換える）
