# NO-GO条件・必須出力

本ドキュメントは nagame-dev のレビューフェーズでNO-GO判定を出す条件と、
NO-GO時に必ず出力しなければならない情報の形式を定義する。

---

## 1. 標準NO-GO条件（Phase 5 レビュー）

以下のいずれか1つでも該当する場合、GO判定を出してはならない。

| # | NO-GO条件 | 確認方法 | 黄金ルール対応 |
|---|---|---|---|
| 1 | Blockerが1件以上残存 | レビューログでBlocker検索 | - |
| 2 | Must要件にACC-*が未接続 | Traceability Matrixで未接続検索 | #2 |
| 3 | Must要件にTC-*が未接続 | Traceability Matrixで未接続検索 | #2 |
| 4 | 外部API規約が未確認 | API-*のEvidence IDを確認 | #1 |
| 5 | 破壊的操作にdry-run/sandboxがない | SDD HARNESS セクションを確認 | #3 |
| 6 | CIゲート（lint/test/build）が未設定 | CI設定ファイルを確認 | - |
| 7 | E2Eテストシナリオが未実行 | テスト結果ログを確認 | - |
| 8 | セキュリティ要件の認証・認可・秘密情報が未定義 | SEC-*の定義を確認 | - |

## 2. 追加NO-GO条件（v2.0 強化版）

標準条件に加え、以下も検出対象とする。

| # | NO-GO条件 | なぜ危険か | 検出方法 |
|---|---|---|---|
| 9 | AIがテストを削除/skip/期待値変更した | テストの信頼性が失われ、バグがすり抜ける | git diff でテストファイルの削除・skip追加・assert値変更を検出 |
| 10 | Codex/Opusの観点が重複している | 非対称レビューの意味がなくなる | レビューログで両者の指摘観点を比較 |
| 11 | レビュー結果がRisk Registerに反映されていない | 発見されたリスクが管理から漏れる | REV-*とRISK-*の接続を確認 |
| 12 | 反復回数だけ増え失敗分類が更新されない | 同じ失敗を繰り返しているだけ | failure_patterns.md の更新日時を確認 |
| 13 | 本番操作がdry-runなしで実行される | 不可逆な本番障害が発生する | 実装コード内の本番接続パスを検索 |

### テスト改ざんの検出基準（#9 の詳細）

以下のいずれかが検出された場合、テスト改ざんとして扱う。

| パターン | 具体例 | 判定 |
|---|---|---|
| テストファイルの削除 | `git rm tests/test_auth.py` | NO-GO |
| テストのskip追加 | `@pytest.mark.skip` の追加 | NO-GO（理由が明記されていない場合） |
| 期待値の変更 | `assert status == 200` → `assert status == 500` | NO-GO（仕様変更の根拠がない場合） |
| テスト条件の緩和 | `assertEqual` → `assertTrue(True)` | NO-GO |
| テストカバレッジの低下 | カバレッジが前回より5%以上低下 | Yellow（調査必要） |

## 3. NO-GO時の必須出力（7項目）

NO-GO判定を出す場合、以下の7項目を全て出力すること。1項目でも欠けたNO-GO報告は不完全として扱う。

### 出力テンプレート

```markdown
## NO-GO判定報告

### 1. 原因
[何がNO-GOを引き起こしたか。該当するNO-GO条件の番号を明記]

条件番号: #[N]
概要: [1-2文で原因を説明]

### 2. 根拠
[実ファイル・一次ソースへの具体的な参照]

- ファイル: [ファイルパス + 該当行]
- 一次ソース: [URL または ドキュメント名]
- 証拠: [具体的な内容の引用]

### 3. 重大な理由
[なぜこれがBlockerなのか。放置した場合に何が起きるか]

放置した場合の影響: [具体的な被害・リスク]
影響範囲: [影響を受けるコンポーネント・要件ID]

### 4. GOに戻す最小修正
[最も少ない修正でNO-GO条件を解消する方法]

修正内容: [具体的な修正手順]
推定工数: [時間の目安]
修正による副作用: [あれば記述、なければ「なし」]

### 5. 修正対象ファイル
[修正が必要なファイルの一覧]

- [ ] [ファイルパス1]: [修正内容の概要]
- [ ] [ファイルパス2]: [修正内容の概要]

### 6. 再レビュー観点
[修正後に何を重点的に確認するか]

- [観点1]: [確認内容]
- [観点2]: [確認内容]

### 7. 再レビュー用プロンプト
[修正完了後に実行するレビューの指示文]

「[修正対象]を修正しました。以下の観点で再レビューしてください:
 (1) [観点1]
 (2) [観点2]
 修正差分: [差分の参照方法]」
```

## 4. NO-GO報告の品質基準

NO-GO報告自体の品質も評価する。以下を満たさないNO-GO報告はやり直し。

| # | 品質基準 | NG例 |
|---|---|---|
| 1 | 原因が具体的である | 「品質が不十分」のような曖昧な表現 |
| 2 | 根拠に実ファイルへの参照がある | 「セキュリティが心配」のような感覚的な指摘 |
| 3 | 最小修正が実行可能である | 「全面的に見直す」のような曖昧な修正指示 |
| 4 | 修正対象ファイルが具体的である | 「関連ファイルを修正」のような曖昧な対象 |
| 5 | 再レビュー観点が明確である | 「全体を再レビュー」のような非効率な指示 |
| 6 | 再レビュー用プロンプトがコピペ実行可能 | 修正者が解釈に悩むプロンプト |

## 5. 複数NO-GO条件が同時に該当する場合

| 状況 | 対処 |
|---|---|
| 2〜3件のNO-GO | 全件を1つの報告にまとめ、修正の優先順位を付ける |
| 4件以上のNO-GO | フェーズ全体の品質を疑い、前フェーズに差し戻しを検討 |
| 標準条件と追加条件が混在 | 標準条件（#1〜#8）を先に解消、その後追加条件（#9〜#13）に対処 |

### 優先順位の付け方

1. **セキュリティ関連**（#8, #13）→ 最優先
2. **データ破壊リスク**（#5, #13）→ 次に対処
3. **テスト信頼性**（#7, #9）→ 実装品質の基盤
4. **文書整合性**（#2, #3, #4, #10, #11）→ 追跡可能性の基盤
5. **プロセス改善**（#6, #12）→ 継続的改善

---

## 6. NO-GOからGOへの復帰手順

1. NO-GO報告の「4. GOに戻す最小修正」を実行する
2. 「5. 修正対象ファイル」の全ファイルが修正されたことを確認する
3. 「7. 再レビュー用プロンプト」を実行し、再レビューを受ける
4. 再レビューでBlockerが0件になったことを確認する
5. RYGゲートの12項目チェックリストを再実行する
6. 全項目Greenを確認してGO判定を出す

**注意**: NO-GO→GO復帰時は、修正箇所だけでなく、修正が他の要件・テスト・リスクに波及していないかも確認すること（黄金ルール#6）。
