# Phase 4: テスト / ハーネス / E2E

## 目的

Phase 2（SRS）の受入基準と Phase 3（SDD）の設計に基づき、テスト計画・安全装置・E2Eシナリオを策定する。
「動いているように見える」ではなく「証拠をもって動作を証明する」ための仕組みを構築する。

---

## 1. テスト計画（IEEE 829 準拠 12セクション）

| # | セクション | 内容 |
|---|---|---|
| 1 | **テスト計画ID** | `TP-[プロジェクト名]-[版数]` |
| 2 | **目的** | このテスト計画で検証する範囲と目標 |
| 3 | **テスト対象** | テスト対象のコンポーネント/機能一覧 |
| 4 | **テスト対象外** | 明示的にテストしない範囲と理由 |
| 5 | **テストアプローチ** | テストピラミッドのどの層で何をテストするか |
| 6 | **Entry Criteria（開始条件）** | テスト開始前に満たすべき条件 |
| 7 | **Exit Criteria（終了条件）** | テスト完了と判定する条件 |
| 8 | **Suspension Criteria（中断条件）** | テストを中断する条件 |
| 9 | **テスト環境** | OS、ランタイム、依存ツール、テストデータ |
| 10 | **テストスケジュール** | いつ、何を、誰がテストするか |
| 11 | **リスクと対策** | テストに関するリスクとその対策 |
| 12 | **成果物** | テスト計画書、テストケース、テスト結果レポート |

### Entry / Exit / Suspension Criteria テンプレート

```markdown
### Entry Criteria（テスト開始条件）
- [ ] SDD の設計が社長承認済み
- [ ] テスト対象コードがビルド可能
- [ ] テスト環境が構築済み
- [ ] テストデータが準備済み

### Exit Criteria（テスト終了条件）
- [ ] 全 Must 要件のテストが PASS
- [ ] コードカバレッジ 80% 以上
- [ ] Blocker / Must の不具合がゼロ
- [ ] E2E テストが全シナリオ PASS

### Suspension Criteria（テスト中断条件）
- Blocker 不具合が 3件以上同時発生
- テスト環境が利用不能
- 外部 API が長時間ダウン
```

## 2. テストピラミッド

| 層 | テスト種別 | 対象 | 数の目安 | 実行頻度 |
|---|---|---|---|---|
| 1 | **Unit（単体）** | 関数・メソッド単位の動作 | 最多 | コミット毎 |
| 2 | **Integration（結合）** | コンポーネント間の連携 | 中程度 | PR毎 |
| 3 | **E2E（エンドツーエンド）** | ユーザーシナリオ全体 | 最少 | デプロイ前 |
| 4 | **Acceptance（受入）** | SRS 受入基準の検証 | 要件数分 | リリース前 |
| 5 | **Security（セキュリティ）** | 脆弱性、権限、データ保護 | 主要攻撃面分 | リリース前 |
| 6 | **Regression（回帰）** | 既存機能が壊れていないか | 蓄積 | リリース前 |
| 7 | **Smoke（煙テスト）** | 最低限動くか | 3-5件 | デプロイ直後 |

### カバレッジ目標

- Unit: 行カバレッジ **80%以上**
- Integration: 主要フロー **100%**
- E2E: 後述の6シナリオ **100%**

## 3. P/G/E 3エージェント体制

テスト工程を3つの役割に分割し、品質を担保する。

### Planner（計画者）

| 責務 | 成果物 |
|---|---|
| テスト契約（何をテストするか）の定義 | テスト計画書 |
| 合格基準の設定 | Exit Criteria |
| リスクの洗い出し | リスク一覧 |
| テストケースの設計（実装はしない） | テストケース仕様書 |

### Generator（生成者）

| 責務 | 成果物 |
|---|---|
| テストコードの実装 | テストファイル群 |
| テスト実行とログ記録 | テスト実行ログ |
| カバレッジ計測 | カバレッジレポート |
| テスト結果の整理 | チェックリスト記入済み |

### Evaluator（評価者）

| 責務 | 成果物 |
|---|---|
| テスト結果の評価 | 評価レポート |
| 品質スコアの算出 | スコアカード |
| ブロッカーの特定 | ブロッカー一覧 |
| GO/NO-GO 判定の提案 | 判定結果 |

## 4. 決定論的センサー（Deterministic Sensors）

AIの自己申告を信頼せず、機械的に検証可能なセンサーを設置する。

| # | センサー | コマンド例 | 合格基準 |
|---|---|---|---|
| S1 | **テスト** | `pytest --tb=short` | 全テスト PASS |
| S2 | **型チェック** | `mypy src/` | エラー 0件 |
| S3 | **リント** | `ruff check src/` | エラー 0件（警告は許容） |
| S4 | **ビルド** | `python -m build` | 正常終了 |
| S5 | **E2E** | `pytest tests/e2e/` | 全シナリオ PASS |
| S6 | **セキュリティ** | `bandit -r src/` | HIGH 0件 |

### センサー実行ルール

- 全センサーは **自動実行** する（手動確認に依存しない）
- センサーの結果は **ログファイルに記録** する
- 1つでも FAIL なら **次フェーズに進めない**

## 5. 安全ハーネス（Safety Harness）

外部サービスへの意図しない影響を防ぐための安全装置。

| # | ハーネス | 内容 | 実装方法 |
|---|---|---|---|
| H1 | **DRY_RUN** | デフォルトで外部APIを呼ばない | 環境変数 `DRY_RUN=true` がデフォルト |
| H2 | **承認ゲート** | 課金APIの呼び出し前に確認プロンプト | `--approve` フラグが必要 |
| H3 | **冪等性** | 同じ操作を2回実行しても結果が変わらない | 状態チェック → 既存なら スキップ |
| H4 | **キルスイッチ** | 暴走時に即停止できる | Ctrl+C でグレースフル停止 |
| H5 | **監査ログ** | 全ての外部API呼び出しをログに記録 | `audit.log` に書き込み |

### DRY_RUN の動作仕様

```
DRY_RUN=true（デフォルト）:
  - 外部APIは呼び出さない
  - モックレスポンスを返す
  - ファイルは生成するが、ダミーデータ
  - ログに [DRY_RUN] と明記

DRY_RUN=false:
  - 実際の外部APIを呼び出す
  - 課金が発生する可能性がある
  - 明示的に設定しない限り false にならない
```

### CONSTRAINTS.md テンプレート

```markdown
# CONSTRAINTS（制約条件）

## 実行制約
- DRY_RUN はデフォルト true。false にするには明示的な設定が必要
- 課金APIの呼び出しは --approve フラグが必要
- 1回の実行で呼び出せるAPI回数の上限: [N回]

## データ制約
- 入力テキストの上限: [N文字]
- 出力ファイルの上限: [N MB]
- 同時処理数の上限: [N件]

## セキュリティ制約
- APIキーはハードコード禁止
- 機密情報はログに出力しない
- 外部入力は必ずバリデーション
```

### HARNESS.md テンプレート

```markdown
# HARNESS（安全ハーネス仕様）

## H1: DRY_RUN
- 環境変数: DRY_RUN
- デフォルト: true
- 切り替え: export DRY_RUN=false

## H2: 承認ゲート
- フラグ: --approve
- 対象: 課金APIの呼び出し
- 未承認時の動作: エラーメッセージ表示 + 終了

## H3: 冪等性
- 対象: 全データ書き込み操作
- 実装: 既存チェック → スキップ or 上書き確認

## H4: キルスイッチ
- トリガー: SIGINT (Ctrl+C)
- 動作: 進行中の処理を完了 → クリーンアップ → 終了

## H5: 監査ログ
- ファイル: audit.log
- 形式: [timestamp] [level] [component] [action] [result]
- ローテーション: 日次、7日保持
```

## 6. E2E シナリオ設計

### 必須6シナリオ

| # | 種別 | シナリオ | 期待結果 |
|---|---|---|---|
| E2E-01 | **正常系1** | 標準的な入力で正常処理 | 正常完了、期待通りの出力 |
| E2E-02 | **正常系2** | 最小入力で正常処理 | 正常完了、最小出力 |
| E2E-03 | **正常系3** | 最大入力で正常処理 | 正常完了、最大出力 |
| E2E-04 | **異常系1（外部障害）** | 外部APIがダウン | リトライ後エラー終了、ログ記録 |
| E2E-05 | **異常系2** | 不正な入力 | バリデーションエラー、ユーザーへ案内 |
| E2E-06 | **境界値** | 入力の上限/下限ぴったり | 正常処理（境界を含む） |

### E2E シナリオ 7項目テンプレート

各シナリオは以下の7項目を記述する。

```markdown
### E2E-01: 標準的な入力で正常処理

1. **前提条件**: DRY_RUN=true、テストデータ準備済み
2. **入力データ**: 1000文字の台本テキスト
3. **実行手順**: `python -m src.main generate --input test_script.txt`
4. **期待結果**: output/ に MP4 ファイルが生成される
5. **検証方法**: ファイル存在確認 + ファイルサイズ > 0 + メタデータ検証
6. **タイムアウト**: 60秒
7. **クリーンアップ**: output/ のテストファイルを削除
```

## 7. RYG（Red/Yellow/Green）判定基準

E2E テスト結果を3段階で判定する。

| 色 | 条件 | 次のアクション |
|---|---|---|
| **Green** | 全6シナリオ PASS | Phase 5（レビュー）へ進む |
| **Yellow** | 境界値（E2E-06）のみ FAIL | 修正して再テスト、Phase 5 へは進める |
| **Red** | 正常系（E2E-01〜03）または異常系（E2E-04〜05）が FAIL | 修正必須、Phase 5 へ進めない |

### RYG 記録テンプレート

```markdown
## E2E テスト結果

| 実行日時 | シナリオ | 結果 | 備考 |
|---|---|---|---|
| YYYY-MM-DD HH:MM | E2E-01 正常系1 | PASS | - |
| YYYY-MM-DD HH:MM | E2E-02 正常系2 | PASS | - |
| YYYY-MM-DD HH:MM | E2E-03 正常系3 | PASS | - |
| YYYY-MM-DD HH:MM | E2E-04 異常系1 | PASS | - |
| YYYY-MM-DD HH:MM | E2E-05 異常系2 | PASS | - |
| YYYY-MM-DD HH:MM | E2E-06 境界値 | FAIL | 上限ぴったりで例外発生 |

### 総合判定: Yellow
### 理由: E2E-06 のみ FAIL、境界値の off-by-one エラー
### 次のアクション: 修正して再テスト
```
