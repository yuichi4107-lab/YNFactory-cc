## 1. プロジェクト概要

### ゴール

東証グロース市場の小型・材料銘柄を対象に、寄り前気配（8:45-8:59）の板状況と複合フィルターで買い優勢銘柄を自動検知し、Phase 0（2ヶ月検証）で勝率60%以上・プロフィットファクター1.5以上を確認したうえで、Phase 2以降のkabu API自動発注に移行する日本株デイトレシステムを構築すること。

### 戦略サマリー

| 項目 | 内容 |
|------|------|
| 戦略名 | JP-DAYTRADE-v1（寄り前気配×板厚み戦略） |
| 対象市場 | 東証グロース中心（プライム小型も対象） |
| ユニバース除外 | 株価 > 3,000円 または 単元代金 > 30万円、特別気配銘柄 |
| スクリーニング時刻 | 8:45-8:59（確定気配フェーズ） |
| コアシグナル | 買気配累積株数 > 売気配累積株数（比率0.8以下）+ 板厚み確認 |
| 複合フィルター | GAP率 +3〜+8%、前日出来高 ≥ 100万株、時価総額100〜1,000億円、直近5日値幅率 ≥ 5%、材料フラグ（加点） |
| エントリー | 8:59 寄り成り注文（Phase 2以降自動） |
| 資金配分 | リスク等化（損切-2%時の損失額を揃える） |
| 同時保有 | Phase 0: 3銘柄、Phase 2: 5銘柄 |
| 利確 | +5〜10%（+3%で半分利確→残り追随の分割も検討） |
| 損切 | -1〜-2% |
| 大引けクローズ | 15:25 成行 |
| 停止ルール | 日次ドローダウン -5% または 3連敗で当日取引停止 |
| 取引種別 | 現物のみ（Phase 0はSBI手動、Phase 2以降は三菱eスマートAPI自動） |

## 2. スコープ

### やること

- J-Quants API（無料/Lightプラン）による日足データ取得とバックテスト母集団構築
- kabu API（PUSH/REST）による8:00-9:00の寄り前気配データのリアルタイム取得と自前保存
- 7フィルター組合せスクリーニングロジックの実装とバックテスト
- Walk-Forward検証によるパラメータ最適化（過学習防止）
- Telegramによる朝8:59のシグナル通知（既存Telegramインフラ流用）
- Phase 0: SBI証券での手動発注・記録・週次レビュー（3銘柄）
- Phase 2: kabu API自動発注・ポジション管理・エラー処理（5銘柄）
- 本番監視ダッシュボード・アラート・定期レポート

### やらないこと

- SBI証券へのAPI自動発注（公式API個人向け非公開、利用規約上不可）
- Seleniumによるブラウザ操作での自動発注（利用規約違反リスク）
- 信用取引・空売り・レバレッジ取引（Phase 0は現物のみ）
- FX/Coincheck等の既存システムへの変更・影響（完全別系統）
- 有料データベンダー（Bloomberg・Refinitiv等）の使用
- 東証プライム大型株（値嵩株）・マザーズ以外の地方市場専用銘柄
- 高頻度取引（HFT）・アービトラージ・統計的アービトラージ
- Windows VPS（Phase 0〜2はSurface据置で対応、Phase 3移行は別判断）
- 複数口座の同時運用（三菱eスマート一本化はPhase 2以降）

## 工程1: バックテストエンジン

### 目的

確定した7フィルタースクリーニング条件と寄り成り戦略ロジックを実装し、過去2年分のデータでバックテストを実行。期待値・勝率・PF・最大DDを算出し、戦略の有効性を統計的に検証する。

### 中間成果物

| 成果物 | パス | 内容 |
|--------|------|------|
| スクリーニングエンジン | `jp-daytrade/strategy/screener.py` | 7フィルター実装 |
| バックテストエンジン | `jp-daytrade/backtest/engine.py` | 寄り成り→利確/損切/大引けクローズ |
| パフォーマンスレポート | `jp-daytrade/backtest/results/bt_report_v1.md` | 全指標集計 |
| 取引ログCSV | `jp-daytrade/backtest/results/trades_v1.csv` | 全取引の詳細記録 |

### バックテスト設計仕様

**スクリーニング条件（初期パラメータ）**:
```
AND条件:
  1. 株価 ≤ 3,000円 かつ 単元代金 ≤ 30万円
  2. 時価総額 100〜1,000億円
  3. 直近5日日中値幅率 ≥ 5%
  4. 前日出来高 ≥ 100万株
  5. GAP率（8:59時点の買気配 / 前日終値 - 1）≥ +3%
  6. 寄り前売買比率: 売気配累積 / 買気配累積 ≤ 0.8（買い優勢）
  7. 板厚み（上下10本累積）≥ 10,000株

加点（合計2点以上でエントリー優先）:
  + 当日/前日夜の適時開示（業績予想修正 or 上方サプライズ）: +1点
  + 特別気配フラグ（AskSign = "0103" = 特別買い気配）: +1点
  + 前日出来高前週同日比 ≥ 200%: +1点
```

**エントリー/エグジット仕様**:
- エントリー: 寄り付き価格（始値）で約定とみなす
- 利確: +5%到達で50%利確、残り50%は+10%または大引け
- 損切: -2%（SL固定）
- 大引けクローズ: 15:25 成行（残ポジション全クローズ）
- 同時保有上限: 3銘柄（Phase 0設定）
- スリッページ想定: 0.1%（保守的設定）
- 手数料: 0円（三菱eスマートAPI信用想定、Phase 0はSBI手数料別途補正）

**合格基準（バックテスト）**:
- 勝率 ≥ 55%
- プロフィットファクター ≥ 1.3
- シャープレシオ ≥ 0.8
- 最大ドローダウン ≤ 20%

## 技術的決定事項

### コードベース配置: `ai-trade-system/` 拡張 vs 新規プロジェクト

**判断結果: 新規プロジェクト `jp-daytrade/` を作成推奨**

| 観点 | ai-trade-system/拡張 | jp-daytrade/（新規） |
|------|---------------------|---------------------|
| データソース | Saxo API（FX/先物）/ Coincheck API | kabu API（日本株）/ J-Quants |
| 実行環境 | Linux VPS（ConoHa） | Surface Windows |
| 取引時間 | 24時間（FX）・一部 | 8:00-15:30（東証営業日のみ） |
| 依存ライブラリ | saxo_api, ccxt 等 | kabusapi, jquants 等 |
| スケジューラ | Linux cron | Windows タスクスケジューラ |
| 将来の保守 | 混在で複雑化 | 独立で明確 |

理由: 実行環境（Linux VPS vs Windows Surface）、データソース、取引時間が根本的に異なるため、混在させると保守性が著しく低下する。ディレクトリ構造の規約（例: `config/`・`data/`・`strategy/`・`trading/`・`notify/`）はai-trade-systemを参考に統一することで一貫性を確保。

### データストレージ

**判断結果: SQLite推奨（Phase 0〜2）**

| 比較軸 | SQLite | PostgreSQL | CSV/Parquet |
|--------|--------|------------|-------------|
| セットアップ | ファイルのみ、ゼロ設定 | サーバー構築必要 | ゼロ設定 |
| クエリ | SQL完全対応 | SQL完全対応 | pandas/polars依存 |
| 同時アクセス | 制限あり（単一書込） | 完全対応 | 制限あり |
| Surface/ConoHa移植 | ファイルコピーのみ | DB移行作業必要 | ファイルコピーのみ |
| スケーリング | 〜10GB程度で十分 | 無制限 | 分析向き、更新苦手 |

結論: 日々の取引量（最大5件/日）と気配データ保存量（数十銘柄×1分足×数時間）はSQLiteで十分。Phase 3以降で本格的な高頻度分析が必要になった場合にPostgreSQLへ移行を検討。

### バックテスト対象期間

**推奨: 過去2年分（2024-04〜2026-04）**

理由:
- 2024/11のクロージング・オークション導入後の相場を含む（制度変更の影響を検証できる）
- 2024/11の三菱UFJ eスマート証券ブランド変更前後を含む（API仕様の継続性確認）
- 2年 × 東証営業日 ≒ 500日 → 統計的に十分なサンプル数
- J-Quants Lightプラン（無料）で取得可能な範囲内

### kabu API認証フロー（Windows/Surface）

工程3に詳述。kabuステーション起動 → ログイン → API有効化 → Pythonからlocalhost:18080へアクセス。2要素認証の自動化はPhase 2以降の課題。

### Linux VPS vs Windows の役割分担

| 処理 | 実行環境 | 理由 |
|------|---------|------|
| kabu PUSH API接続・気配取得 | Surface（Windows） | kabuステーション必須（Windowsアプリ） |
| リアルタイムシグナル検知 | Surface（Windows） | 同上 |

| 6 | kabuステーション自動ログイン（2要素認証の自動化） | 中 | Phase 0は手動ログイン。Phase 2移行時に対処 |

### 想定ブロッカー

| ブロッカー | 影響工程 | 回避策 |
|-----------|---------|--------|
| 信用口座審査遅延（7営業日超） | 工程3・5 | 工程0・1・2はモックで開発継続、審査期間中に前倒し実施 |
| Professional適用が条件を満たせない | 工程3以降全て | 信用口座開設で自動適用されるはずだが、非適用の場合はSBI証券でのフルハンドル運用を検討 |
| kabuステーション接続不安定 | 工程3・6 | 接続断の自動リカバリー実装、1日1再起動で安定化 |
| バックテスト結果が合格基準未達（PF < 1.3等） | 工程2 | パラメータ再調整・フィルター条件の見直し。最悪の場合、戦略設計から再検討 |
| Surface障害（停電・Windows Update強制再起動） | 工程3・5・6 | UPS導入、アクティブ時間設定、アラート監視 |

### 代替案（kabuステーション動作不良時）

1. **J-Quants + 株探スクレイプのみでシグナル生成**: 寄り前気配（リアルタイム板）は使えないが、前日データ＋材料フラグでスクリーニングは可能。精度は落ちるがシステムが止まらない
2. **楽天証券 MarketSpeed RSS（Excel経由）**: 寄り前気配の板情報がExcelで取得可能。自動化難度は高いがkabuステーション代替として検討可
3. **Windows VPS（KAGOYA 3GB・月2,420円）への移行**: Surface障害が頻発する場合のインフラ代替
