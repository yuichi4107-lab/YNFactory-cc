## 2. テストアプローチ（テストピラミッド）

4層構成とする。件数の目安は自動テスト関数の数であり、受入テストケース（TC-*）は各層に配置された50件が正である。

| 層 | 目的 | 対象 | TC件数 | 自動テスト件数の目安 |
|---|---|---|---:|---:|
| **Unit** | 各コンポーネントの公開関数が仕様どおりの入出力・例外を返すこと | C-01〜C-14 の公開関数（SDD §1.3） | 17 | 120件（全公開関数に1件以上） |
| **Integration** | モック取引所・モックデータ提供元と結合した主要経路が仕様どおり動くこと | データ取得経路／発注経路／記録経路 の3経路 | 16 | 40件 |
| **E2E** | データ取得→シグナル→リスク→発注→記録→通知 の1サイクルが完走すること | `docs/E2E_SCENARIOS.md` の6本（正常3・異常2・境界1） | 2（TC-P01, P03） | 6本 |
| **異常注入** | 安全装置が例外なく発動すること（発動しないことが最大の欠陥） | RiskGate・OrderRouter・Notifier・Reconciler | 15 | 30件 |

- 異常注入層は「注入した異常に対して、定義された停止・拒否・通知が**発生した**こと」を判定する。発生しなければFAILである（FP-005・FP-006の再発防止）。
- 全テストはAPIキーなしで実行できる（§8 テスト環境）。

## 4. 重点テストケースの詳細手順

旧システムが実際に失敗した箇所（FP-002, FP-005, FP-006, FP-008）に対応する7件は、手順を実装可能な粒度まで詳細化する。

### 4.1 TC-E01: 実残高に基づく発注数量の決定（FP-005 の直接対策）

- **前提**:
  1. モック取引所の instruments: symbol=BTC_JPY, qty_step=0.00000001（ケースA）／qty_step=0.0001（ケースB）
  2. positions（記録上）: BTC 0.00133
  3. モック取引所の fetch_balance("BTC") 応答: 0.00132648（手数料控除により記録より小さい。FP-005 と同じ差分）
- **手順**:
  1. 決済シグナルを投入し、OrderRouter.submit まで実行する
  2. モックが受信した place の数量を取得する
  3. fetch_balance の呼び出し回数を取得する
- **期待結果**:
  - ケースA（qty_step=0.00000001）: 発注数量 == 0.00132648（記録上の0.00133と異なる値であることが直接判定できる）
  - ケースB（qty_step=0.0001）: 発注数量 == 0.0013
  - 両ケースで fetch_balance 呼び出し回数 == 1（発注前に照会している）
- **判定方法**: 上記3値のassert。加えて 発注数量 ≤ 0.00132648 をassertし、記録値0.00133がそのまま使われた場合（残高超過）を検出する
- **補足**: ACC-E01 は qty_step を規定していない。qty_step=0.0001 のみでは 0.00133 も 0.0013 に丸まり「記録値が使われていない」ことを区別できないため、ケースAを併置して判定を成立させる（§9 のSRSフィードバック参照）

### 4.2 TC-E06: 同一拒絶3回連続での戦略停止（FP-005: 21日間ループの再発防止）

- **前提**:
  1. モック取引所が place に対し常に拒絶応答「残高不足」を返す設定
  2. 決済シグナルを発生させる戦略が1件稼働中。strategy_state.consecutive_failures == 0
- **手順**:
  1. サイクル1回目を実行 → 拒絶1回目。consecutive_failures と alerts を記録
  2. サイクル2回目を実行 → 拒絶2回目
  3. サイクル3回目を実行 → 拒絶3回目
  4. **サイクル4回目を実行**（停止後の再送が起きないことの検証。この手順を省略しない）
- **期待結果**:
  1. 1回目の拒絶で通知が送信される（TC-M01 と同一事象）
  2. 3回目の拒絶で strategy_state.status=STOPPED、stop_reason に拒絶理由「残高不足」を含む
  3. 停止通知が送信され、本文に拒絶理由を含む
  4. **4回目のサイクルで place は呼ばれない**
- **判定方法**:
  - モックの place 呼び出し回数 == 3（4回目のサイクル実行後に検査。4なら FAIL）
  - strategy_state.status == STOPPED、consecutive_failures == 3
  - alerts に拒絶理由文字列を含む行が存在
  - 業務エラーに対する同一サイクル内リトライが0回であること（SDD §2.4: 業務エラーはリトライしない）

### 4.3 TC-M01: 最初のエラーから60秒以内の通知（FP-006: 無言の故障の再発防止）

- **前提**:
  1. モック取引所が place にエラーを返す設定
  2. 模擬時計を使用（実時間待機なし）。Telegramモックが受信時刻を記録
- **手順**:
  1. 発注を含むサイクルを実行し、モックがエラーを返した時刻 T0 を記録する
  2. Telegramモックが通知を受信した時刻 T1 を記録する
- **期待結果**: 最初の1回のエラーで通知が送信される（3回目を待たない）。T1 − T0 ≤ 60秒
- **判定方法**:
  - alerts に1件追加され、sent == true
  - T1 − T0 ≤ 60秒（模擬時計の値でassert）
  - エラー1回の時点で判定する（エラー回数カウンタ == 1 の状態で通知が存在する）

### 4.4 TC-R05: DD 25%での全停止（ACC-R05 をそのまま実行）

- **前提**:
  1. 期初資金500,000円。pnl_daily 上の資産評価額の最高値 == 520,000円
  2. 戦略3件が稼働中（暗号資産2・FX1）
- **手順**:
  1. 資産評価額を390,000円に設定する（(520,000 − 390,000) ÷ 520,000 = 25.0%）
  2. サイクルを実行する
  3. 新規シグナルを投入し、次のサイクルを実行する
  4. オーナーの再開指示を投入せずに、さらに1サイクル実行する
- **期待結果**:
  1. 全戦略（3件）が停止する
  2. 通知が送信される
  3. 再開指示があるまで発注が行われない
- **判定方法**:
  - strategy_state: 3件全てが status == STOPPED
  - alerts に DD 25% 到達を示す1件が追加
  - 手順3・4のサイクルで place 呼び出し回数 == 0
  - 対照ケース: 評価額390,520円（下落率24.9%）では全戦略 ACTIVE のまま（E2E-B01 と共通のデータで実施）

### 4.5 TC-B02: HOLDOUT 2回目アクセスの拒否（FP-002: データスヌーピングの防止）

- **前提**:
  1. 戦略X の backtest_runs に holdout_accessed_at == "2026-08-21T10:00:00Z" が記録済み
- **手順**:
  1. 戦略X で HOLDOUT 区間の検証を再度実行する
  2. 送出された例外の型とメッセージを取得する
  3. backtest_runs.holdout_accessed_at を再照会する
- **期待結果**: アクセスが拒否され、前回のアクセス日時が表示される
- **判定方法**:
  - 拒否例外が送出される（HOLDOUT データは返らない）
  - 例外メッセージに "2026-08-21T10:00:00Z" を含む（文字列照合）
  - holdout_accessed_at の値が "2026-08-21T10:00:00Z" のまま不変（2回目の日時で上書きされない）
  - 対照ケース: 別戦略Y の初回アクセスは成功し、holdout_accessed_at が新規に記録される

### 4.6 TC-B08: ギャップ時の始値約定（BP§2 B6: 約定の楽観の排除）

- **前提**:
  1. Day1 終値105円で損切り価格100円のロングポジションを保有するテストデータ
  2. Day2 の始値 == 95円（損切り価格を5円下抜くギャップ）
- **手順**:
  1. Day1〜Day2 を含む期間でバックテストを実行する
  2. 決済 fill の約定価格と実現損益を取得する
- **期待結果**: 約定価格は100円ではなく95円として計算される
- **判定方法**:
  - fill 価格 == 95（100 なら FAIL）
  - 実現損益が95円基準で計算されている（取得単価110円・数量1の場合: 実現損益 == −15円。−10円なら FAIL）
  - 対照ケース: Day2 始値が101円（ギャップなし・日中に100円到達）の場合は fill 価格 == 100

### 4.7 TC-D03: 同期フォルダ配下の格納先で起動中止（FP-008: Drive上のDB破損の再発防止）

- **前提**:
  1. 設定ファイルのデータ格納先に、同期フォルダを示すパスを設定する。判定対象: Google Drive / OneDrive / Dropbox（ACC-D03）
  2. テストケース: (a) パス文字列による判定（例: "G:/マイドライブ/data"、"~/Google Drive/data"、"~/OneDrive/data"、"~/Dropbox/data"） (b) 同期クライアントのマーカー（`.tmp.drivedownload` 等の検出ファイル）を置いたディレクトリ
- **手順**:
  1. 各ケースでシステムを起動する
  2. 終了コードと標準エラー出力を取得する
  3. 対照ケース: 非同期フォルダ（`/var/lib/mmat/data`）で起動する
- **期待結果**: 同期フォルダ配下では、エラーメッセージを出力し終了コード1で停止する。非同期フォルダでは起動が継続する
- **判定方法**:
  - 同期フォルダの全ケースで exit code == 1 AND stderr に設定されたパス文字列を含む
  - 起動中止時、データファイル（Parquet/SQLite）が1件も作成されていない
  - 対照ケースで exit code != 1（起動フェーズを通過する）

### 8.2 モック取引所アダプタ（MockExchangeAdapter）が再現する挙動

モックは ExecutionAdapter インターフェース（SDD §1.3）を実装し、以下の11挙動を設定で切り替えられること。P3 Entry の条件として、モック自体のテストを全PASSさせる。

| 1 | 残高照会が記録上の数量より小さい実残高を返す（手数料控除誤差。例: 0.00133 に対し 0.00132648） | TC-E01 |
| 2 | 数量刻み（qty_step）・最小注文数量（0.0001 BTC）の適用と、刻み未満の注文の拒絶 | TC-E01, E02 |
| 3 | 拒絶応答3種の区別（残高不足／レート制限／パラメータ不正）と拒絶理由文字列の返却 | TC-E06, R系 |
