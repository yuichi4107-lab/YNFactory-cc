## E2E-N01（正常系1）: シグナル生成から発注・記録までの1サイクル完走

### 1. 目的
定時起動→設定検証→データ取得→品質チェック→シグナル生成→リスク審査→発注→約定→記録 の1サイクル（SRS §4.1）が、人手の介入なしに完走することを確認する。

### 2. 前提条件
- 市場: 暗号資産（BTC_JPY）。instruments: qty_step=0.0001、min_qty=0.0001
- モックデータ: 確定済み日足5年分。最終確定バーで買いシグナルが1件発生するよう設計した系列
- モック取引所: fetch_balance("JPY")=300,000円。place は全量約定（FILLED）を返し、約定価格・手数料（Taker 0.05%）を応答に含める
- 戦略: 1件（ST-01）稼働中。リスク設定値は全て投入済み（1トレード1.0%＝5,000円、市場3・合計6、DD上限25%）

### 3. 手順
1. 模擬時計を定時起動時刻に設定し、Scheduler のサイクルを1回起動する
2. サイクル終了後、signals・orders・order_events・fills・positions・pnl_daily の各テーブルを照会する
3. RiskGate の Decision 記録を照会する
4. シグナル生成開始時刻と place 送信時刻を取得する

### 4. 期待結果
- シグナル1件が入力値つきで記録される
- RiskGate が承認（approved=true）し、注文1件が送信・約定する
- fills の実績値（約定数量・価格・手数料）で positions と pnl_daily が更新される
- サイクル全体でエラー通知が0件

### 5. 確認方法
- テーブル: signals（1行・inputs非空）、orders（1行・冪等キーあり）、order_events（NEW→SUBMITTED→FILLED の遷移）、fills（1行・fee>0）、positions（1行）
- ログ: サイクル開始・終了の記録。ERROR レベル0件
- 通知: alerts に異常通知が追加されていないこと

### 6. 合否基準（機械判定）
- [ ] signals 追加行数 == 1 かつ inputs（JSON）が空でない
- [ ] orders 追加行数 == 1、state == FILLED、冪等キー == sha256(strategy_id+symbol+as_of+side) の再計算値
- [ ] 発注数量 ≤ fetch_balance 応答から計算した最大数量、かつ qty_step=0.0001 の整数倍
- [ ] fills 1行の qty・price・fee がモック応答値と一致
- [ ] positions.avg_price が fills の実績値から計算した値と一致
- [ ] pnl_daily に当日行が存在し market == 暗号資産
- [ ] place 送信時刻 − シグナル生成開始時刻 ≤ 60秒（TC-P01）
- [ ] alerts の ERROR 追加件数 == 0

### 7. FAIL時の記録先
`harness/failure_patterns.md` へ FP-*（連番）として追記する。記載項目: シナリオID／事象／観測したテーブル・ログの値／原因／変換先（要件・設計・テストのどれを直すか）。

## E2E-N02（正常系2）: ポジションの保有と決済

### 1. 目的
建玉の保有→決済シグナル→実残高照会→決済発注→ポジション消滅→実現損益計上 の経路が、記録と実残高の差（FP-005 の状況）があっても完走することを確認する。

### 2. 前提条件
- 保有ポジション: BTC 0.00133（記録上）、平均取得価格 5,000,000円/BTC、strategy_id=ST-01
- モック取引所: fetch_balance("BTC")=0.00132648（手数料控除で記録より小さい）。qty_step=0.0001
- モックデータ: 決済シグナル（売り）が1件発生する系列。売り約定価格 5,200,000円/BTC、手数料 Taker 0.05%
- 当日実現損益 0円、DD 0%

### 3. 手順
1. サイクルを1回起動する（決済シグナルが発生する）
2. モックが受信した place の数量と、fetch_balance の呼び出し記録を取得する
3. サイクル終了後、positions・fills・pnl_daily を照会する

### 4. 期待結果
- 発注前に実残高が照会され、発注数量は 0.00132648 を刻み0.0001で切り捨てた 0.0013 になる（記録上の0.00133は使われない）
- 決済が約定し、positions から当該行が消える
- 実現損益が実績値（約定価格・手数料）から計算されて pnl_daily に計上される

### 5. 確認方法
- テーブル: positions（当該symbol行の消滅）、fills（決済1行）、pnl_daily（realized 更新）、orders（決済注文1行・FILLED）
- モック記録: fetch_balance("BTC") 呼び出し1回、place 受信数量
- ログ: 残高不足拒絶が0件であること

### 6. 合否基準（機械判定）
- [ ] fetch_balance("BTC") 呼び出し回数 == 1（place より前の時刻）
- [ ] place 受信数量 == 0.0013（0.00133 なら FAIL）
- [ ] 残高不足による拒絶件数 == 0
- [ ] positions で symbol=BTC_JPY の行数 == 0（サイクル後）
- [ ] pnl_daily.realized == (5,200,000 − 5,000,000) × 0.0013 − 手数料合計（誤差0円。打消しや概算を認めない）
- [ ] orders の決済注文 state == FILLED

### 7. FAIL時の記録先
`harness/failure_patterns.md` へ FP-*（連番）として追記する（記載項目は E2E-N01 §7 と同じ）。特に place 受信数量が 0.00133 だった場合は FP-005 の再発として明記する。

## E2E-N03（正常系3）: 日次通知の送信

### 1. 目的
日次1回の定期通知が、SRS §6.6 の6項目を1通で伝え、異常通知と区別できることを確認する。

### 2. 前提条件
- 状態を既知の値に設定: 稼働状態=稼働中3戦略、保有ポジション=BTC_JPY 0.0013（暗号資産）と USD_JPY 100通貨（FX）、当日実現損益=+1,200円、累計損益=+8,500円、現在DD=3.0%、停止中の戦略=ST-03（停止理由: E3 同一エラー3回連続）
- Telegramモック: 受信本文・受信時刻・メッセージ分割を記録する。送信は成功応答

### 3. 手順
1. 模擬時計を日次通知時刻に進め、通知タスクを起動する
2. Telegramモックの受信記録を取得する
3. 対照として異常通知1件（任意のエラー）を発生させ、接頭辞を比較する

### 4. 期待結果
- 日次通知が1回送信され、6項目（稼働状態／市場ごとの保有ポジション／当日の実現損益／累計損益／現在のDD／停止中の戦略とその理由）を全て含む
- 接頭辞が異常通知と異なる
- 各メッセージは2,000文字以内（超える場合は分割される）

### 5. 確認方法
- 通知: Telegramモックの受信本文（文字列照合）
- テーブル: alerts に日次通知1件が sent=true で記録される
- ログ: 通知タスクの実行記録

### 6. 合否基準（機械判定）
- [ ] 日次通知の送信回数 == 1（当日内）
- [ ] 本文に設定した6項目の値が全て含まれる: 「3」（稼働戦略数）／「BTC_JPY 0.0013」／「USD_JPY 100」／「+1,200」／「+8,500」／「3.0%」／「ST-03」と停止理由「E3」（文字列照合で8要素全一致）
- [ ] 日次通知の接頭辞 != 異常通知の接頭辞（先頭トークンの比較）
- [ ] 受信した各メッセージの文字数 ≤ 2,000
- [ ] alerts の当該行 sent == true

### 7. FAIL時の記録先
`harness/failure_patterns.md` へ FP-*（連番）として追記する（記載項目は E2E-N01 §7 と同じ）。

## E2E-A01（異常系1）: 外部API障害 — 発注APIの連続エラーで戦略停止・通知

### 1. 目的
発注APIが連続でエラーを返したとき、初回60秒以内の通知（FR-MON-001）→3回連続で戦略停止（FR-EXEC-006）→4回目の再送なし、が全て起きることを確認する。旧システムの21日間ループ（FP-005）と無言の故障（FP-006）の再発防止を、単体ではなく通し経路で検証する。

### 2. 前提条件
- 保有ポジション: BTC 0.0013（決済対象）。戦略 ST-01 稼働中、consecutive_failures=0
- モック取引所: place に対して常に拒絶応答「残高不足」を返す設定。応答時刻を記録
- Telegramモック: 受信時刻を記録。送信は成功応答
- 模擬時計を使用（サイクル間隔は模擬時計で進める）

### 3. 手順
1. サイクル1回目を起動する。拒絶発生時刻 T0 と通知受信時刻 T1 を記録する
2. サイクル2回目を起動する
3. サイクル3回目を起動する。strategy_state と alerts を照会する
4. サイクル4回目を起動する（停止後の再送検証。省略しない）
5. モックの place 呼び出し履歴（回数・時刻）を取得する

### 4. 期待結果
- 1回目の拒絶から60秒以内に異常通知が送信される
- 3回目の拒絶で ST-01 が停止し、拒絶理由を含む停止通知が送信される
- 4回目のサイクルでは place が呼ばれない（同じ注文の再送なし）
- 業務エラーへの同一サイクル内リトライが発生しない（SDD §2.4）

### 5. 確認方法
- テーブル: strategy_state（status・stop_reason・consecutive_failures）、alerts（件数・本文・時刻）、orders／order_events（REJECTED 遷移3件）
- モック記録: place 呼び出し回数と各時刻
- 通知: Telegramモックの受信本文に拒絶理由「残高不足」を含むこと

### 6. 合否基準（機械判定）
- [ ] T1 − T0 ≤ 60秒（TC-M01）
- [ ] 1回目の拒絶時点で alerts 追加件数 ≥ 1（3回目まで無言なら FAIL）
- [ ] サイクル3回目終了時: strategy_state.status == STOPPED、consecutive_failures == 3、stop_reason に「残高不足」を含む
- [ ] 停止通知の本文に拒絶理由を含む（文字列照合）
- [ ] place 呼び出し回数 == 3（サイクル4回目終了時に検査。4以上なら FAIL）
- [ ] 同一サイクル内の place 再試行 == 0回（各サイクルの呼び出しが1回ずつであること）

### 7. FAIL時の記録先
`harness/failure_patterns.md` へ FP-*（連番）として追記する（記載項目は E2E-N01 §7 と同じ）。place 呼び出しが4回以上の場合は FP-005 の再発、通知が3回目まで出ない場合は FP-006 の再発として明記する。

## E2E-A02（異常系2）: データ取得の失敗 — 品質チェック不合格で当該市場のサイクル中止・通知

### 1. 目的
データ品質チェック（BP§1.2）の不合格時に、当該市場のシグナル生成が中止され、不合格項目が通知され、前回データでの発注が行われず、他市場のサイクルは継続することを確認する（SRS §4.2）。

### 2. 前提条件
- 市場: 暗号資産とFXの2市場が稼働対象
- モックデータ: 暗号資産側は欠損バー20%（BP§1.2 項目1「欠損バーの割合」に不合格）の系列。FX側は全項目合格の系列で、シグナルが1件発生する設計
- 前回サイクルの暗号資産データ（正常）が DataStore に残っている
- 戦略: 暗号資産1件・FX1件が稼働中

### 3. 手順
1. 両市場のサイクルを起動する
2. 暗号資産市場の signals・orders と alerts を照会する
3. FX市場の signals・orders を照会する
4. DataQualityChecker の結果記録を照会する

### 4. 期待結果
- 暗号資産: 品質チェックが passed=false となり、シグナル生成・発注が行われない。前回の正常データを使った発注も行われない。不合格項目「欠損バー」を含む通知が送信される
- FX: サイクルが継続し、シグナル生成・発注が行われる
- 暗号資産の戦略は停止しない（データ復旧後の次サイクルで再開できる状態を保つ）

### 5. 確認方法
- テーブル: 品質チェック結果記録（passed=false・不合格項目名）、signals・orders（市場別の追加件数）、alerts（本文）、strategy_state
- 通知: 本文に市場名と不合格項目名を含むこと
- ログ: 暗号資産サイクルの中止記録

### 6. 合否基準（機械判定）
- [ ] 品質チェック結果: 暗号資産 passed == false かつ items に「欠損バー」を含む／FX passed == true
- [ ] signals 追加件数: 暗号資産 == 0、FX == 1
- [ ] orders 追加件数: 暗号資産 == 0（前回データでの発注が0件であること）、FX == 1
- [ ] alerts に1件追加され、本文が市場名（暗号資産）と不合格項目名（欠損バー）を含む
- [ ] strategy_state: 暗号資産戦略の status == ACTIVE（停止ではなくサイクル中止であること）

### 7. FAIL時の記録先
`harness/failure_patterns.md` へ FP-*（連番）として追記する（記載項目は E2E-N01 §7 と同じ）。前回データで発注が行われた場合は「古いデータでの発注」として独立のFP番号を起票する。

## E2E-B01（境界系）: リスク上限の境界 — DD 24.9%では継続、25.0%で全停止

### 1. 目的
全停止のしきい値 DD 25%（FR-RISK-005・ACC-R05）の境界1点で挙動が切り替わること、および 25%未到達側では DD 15%超による数量50%縮小（FR-RISK-004）が働いていることを確認する。

### 2. 前提条件
- 期初資金500,000円。資産評価額の最高値 == 520,000円（pnl_daily に記録済み）
- 戦略3件が稼働中（暗号資産2・FX1）。新規シグナルが毎サイクル1件発生する設計
- しきい値の座標: 24.9%下落 → 評価額 390,520円／25.0%下落 → 評価額 390,000円（520,000 × 0.750 = 390,000）
- ケースAとケースBは独立した環境で実行する（状態を持ち越さない）

### 3. 手順
- **ケースA（24.9%・継続側）**
  1. 資産評価額を390,520円に設定し、サイクルを起動する
  2. strategy_state・RiskGate の Decision・place 受信数量を照会する
- **ケースB（25.0%・停止側）**
  1. 資産評価額を390,000円に設定し、サイクルを起動する
  2. strategy_state・alerts を照会する
  3. 新規シグナルを投入してもう1サイクル起動する（再開指示なし）
  4. オーナーの再開指示を投入し、さらに1サイクル起動する

### 4. 期待結果
- ケースA: 全戦略が稼働を継続する。DD 24.9% > 15% のため、発注数量は50%に縮小される（全停止はしない）
- ケースB: 全戦略が停止し、通知が送信される。再開指示があるまで発注が行われず、再開指示後に発注が再開される

### 5. 確認方法
- テーブル: strategy_state（3件のstatus）、alerts（DD到達通知）、pnl_daily（DD値）、orders
- モック記録: place の呼び出し回数と受信数量
- RiskGate の Decision 記録（adjusted_size・reason）

### 6. 合否基準（機械判定）
- ケースA（評価額390,520円）:
  - [ ] 記録された DD == 24.9%（小数1桁で照合）
  - [ ] strategy_state: 3件全て status == ACTIVE
  - [ ] Decision.approved == true かつ adjusted_size == 原数量 × 0.5（DD15%超の縮小が適用されている）
  - [ ] place 呼び出し回数 ≥ 1
- ケースB（評価額390,000円）:
  - [ ] 記録された DD == 25.0%
  - [ ] サイクル1回目終了時: strategy_state 3件全て status == STOPPED
  - [ ] alerts に DD 25% 到達を示す1件が追加され sent == true
  - [ ] 手順3のサイクルで place 呼び出し回数 == 0
  - [ ] 手順4（再開指示後）のサイクルで place 呼び出し回数 ≥ 1、strategy_state == ACTIVE
- 境界の非対称性: 24.9%側で停止した場合・25.0%側で継続した場合は、いずれも FAIL とする（「25%到達で停止」＝以上、が正）

### 7. FAIL時の記録先
`harness/failure_patterns.md` へ FP-*（連番）として追記する（記載項目は E2E-N01 §7 と同じ）。しきい値の比較演算子の誤り（> と ≥ の取り違え）が原因の場合はその旨を明記する。
