# HARNESS.md — 開発ハーネス設計

本ファイルは MMAT を**実装するときの安全装置**を定義する。
`CONSTRAINTS.md` が「何をしてはならないか」を宣言するのに対し、
本ファイルは**それを機械的に検出・強制する仕組み**を定義する。

宣言だけでは守られない。旧システムも「バックテストは慎重に行う」と決めていたが、
上昇相場だけのデータで合格判定を出した（FP-001）。**検出する仕組みがなかったからである。**

---

## 1. 8層構成

| 層 | 本プロジェクトでの中身 |
|---|---|
| L1 Intent（意図） | `docs/SRS.md` §1.3 の成功指標。年率10〜15%・DD25%以内 |
| L2 Context（文脈） | `docs/SRS.md` / `docs/SDD.md` / `BACKTEST_PROTOCOL.md` / `harness/failure_patterns.md` |
| L3 Agent（役割） | requirements-definer → executor → quality-checker の3役（`02_設定/docs/quality-loop.md`） |
| L4 Rule（事前制御） | `CONSTRAINTS.md` の INV-01〜40。実装前にこれを読む |
| L5 Tool（手段） | pytest / ruff / mypy / coverage / git |
| L6 Sensor（事後評価） | §3 の決定論センサー |
| L7 Memory（記憶） | `harness/failure_patterns.md`（FP-*）、`PROGRESS.md` の状態ログ |
| L8 Governance（統治） | RYGゲート、GO判定基準、`docs/SRS.md` §13 の変更管理 |

## 2. Planner / Generator / Evaluator

| 役割 | 担当 | 入力 | 出力 | 合格条件 |
|---|---|---|---|---|
| **Planner** | requirements-definer | SRS の該当要件 | 工程の要件定義書（ゴール・完了条件・品質基準） | 対応するTC-*が特定されている |
| **Generator** | executor | 要件定義書 + SDD | 実装コード + テスト | 該当TC-*が緑 |
| **Evaluator** | quality-checker | 実装物 + 要件定義書 | 100点満点の採点 | **85点以上**。未満なら具体的な改善指示を出して差し戻す |

**Evaluator が測るのは実装の品質であり、戦略の有効性ではない。**
旧システムは品質スコア88〜100点を取りながら、戦略が有効かは一度も測らなかった（FP-012）。
戦略の有効性は `BACKTEST_PROTOCOL.md` §6〜§7 のゲートが測る。**この2つを混同しない。**

## 5. テスト改ざん検査（週次）

| # | 検査 | 閾値 |
|---|---|---|
| T-01 | テスト件数が前週より減っていないか | 減少0件 |
| T-02 | `@pytest.mark.skip` / `xfail` が増えていないか | 増加0件 |
| T-03 | アサーションのないテスト関数がないか | 0件 |
| T-04 | カバレッジが前週より低下していないか | 低下0% |

**テストを緑にするためにテストを変えるのは、最も検出しにくい失敗である。**
実装が進んでいるように見えて、実際には検証が消えていく。

## 7. 失敗 → 禁止事項への昇格ループ

失敗が起きたら、5ステップで処理する。**修正して終わりにしない。**

1. **記録**: `harness/failure_patterns.md` に FP-* として追記する（事実・原因・なぜ起きたか）
2. **変換**: その失敗を防ぐ制約を `CONSTRAINTS.md` に INV-* として追加する
3. **強制**: 可能なら §4 の禁止パターン検査に検出ルールを追加する
4. **検証**: その失敗を再現するテストを追加し、修正後に緑になることを確認する
5. **波及**: 同種の問題が他の箇所にないかを探す（コード修正だけで閉じない）

**同じ失敗を3回繰り返したら、対処ではなくアプローチそのものを変える。**

## 8. RYG ゲートと GO 判定

| 判定 | 条件 | 許可される行動 |
|---|---|---|
| **Green** | Blocker 0件 / 全Must要件にACC・TCが接続 / 決定論センサー全緑 / カバレッジ80%以上 / E2E全PASS | 次フェーズへ進む |
| **Yellow** | 未達1〜2件、原因が特定されている | **ペーパー・PoCのみ。実弾禁止** |
| **Red** | 未達3件以上、またはバイアス未解消、または安全装置の未実装 | 停止・再設計 |

**GO判定（Phase 5）の条件**: 上記Greenの全条件に加え、
外部依存の規約確認が完了していること（U1〜U3）、
破壊的操作がDRY_RUN・冪等・停止機構で制御されていること、
`BACKTEST_PROTOCOL.md` §7 のフォワードゲートを通過していること。

**Red を出すことは失敗ではない。壊れる前に止められた証拠として扱う。**
