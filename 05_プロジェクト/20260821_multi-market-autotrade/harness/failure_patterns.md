# 失敗パターン台帳（FP-*）— 旧自動売買システムからの回収

- 作成日: 2026-08-21
- 回収元: `20260606_ai-trade-system`、`20260418_jp-daytrade`、`.company/secretary/handoff-log/`（2026-04〜08）、HANDOFF.md
- 位置づけ: **ゼロベースで作り直すのはコードだけであり、ここに記録した失敗は引き継ぐ。**
  各FPは Phase 2（SRS）で要件またはスクリーニング基準に変換すること。変換先を「→」で示す。

---

## A. 戦略の検証プロセスに起因する失敗

### FP-001: 上昇相場だけのバックテストで合格判定を出した
- **事実**: ショート戦略 Phase 1 のバックテストは、レポート自身が対象期間を「上昇相場優位期間」と明記したまま合否判定を行った。ショート戦略を上昇相場で検証すれば不利に出るのは当然で、逆にロング戦略を同じ期間で検証すれば過大評価される。
- **なぜ起きたか**: 期間の選定基準が事前に決まっておらず、手元にあるデータをそのまま使った。
- **→ 変換先**: バックテストプロトコル（相場レジーム分割の必須化）／SRS 非機能要件

### FP-002: 792通りのグリッドサーチで1通貨だけ突出した結果を採用候補にした
- **事実**: TP/SL/Hold の総当たり792通りを探索し、XRP の double_top が PF 4.89・Calmar 3.895 という突出値を出した。4通貨中3通貨は PF 1.0前後で、XRP だけが極端に良い。にもかかわらず「XRP単独採用」の候補として残された。
- **なぜ起きたか**: 探索回数に対する多重比較の補正がなく、Out-of-Sample 検証もなかった。**探索を増やせば偶然の勝ち組は必ず現れる**という前提が設計に入っていなかった。
- **→ 変換先**: バックテストプロトコル（IS/OOS分割・ウォークフォワード・パラメータ感度の平坦性チェック）／スクリーニング基準 S1

### FP-003: 板情報が必要な戦略を日足データで検証し、当然のように失敗した
- **事実**: jp-daytrade の「寄り前気配×板厚み戦略」は、要件定義まで通したうえでバックテストの結果が 勝率13.88% / PF 0.49 / シャープ -5.36 / 最大DD -95.9%。原因は戦略の欠陥ではなく、**エッジの源泉である板情報（F6/F7）が日足データでは再現できなかった**こと。
- **なぜ起きたか**: 戦略採用時に「その戦略を検証できるデータが手元にあるか」を確認していなかった。
- **→ 変換先**: スクリーニング基準 S3（データ入手性）を**採用の前提条件**に格上げ。検証不能な戦略は、どれだけ理屈が良くても採用しない

### FP-004: バックテスト可能期間が2年しかない状態で長期戦略を検討した
- **事実**: J-Quants 無料プランのデータ範囲は 2024-01-24〜2026-01-24 の2年間。この期間には日本株の大きな下落局面がほとんど含まれない。
- **→ 変換先**: バックテストプロトコル（最低検証期間と、含むべき相場イベントの明示）

## B. 発注・約定まわりの失敗（完全自動発注では致命傷になる）

### FP-005: 決済APIが残高不足で拒絶され続け、21日間ループした
- **事実**: 保有期限（Day 15）超過の判定は毎4時間サイクルで正しく発火していたが、`market_sell` が毎回 `Amount has insufficient BTC balance` で拒絶され、21日間ループしていた。原因は**記録上の数量 0.00133 に対し実残高が 0.00132648**（手数料控除分の差）。ポジションは手動決済するまで残り続けた。
- **なぜ致命的か**: 「シグナルは正しい・ロジックも正しい・それでも決済されない」という、ログを見ないと気づけない故障。**完全自動発注ではこれが最も怖い故障形態**。
- **→ 変換先**: SRS 機能要件（発注前の実残高照会・数量丸め・約定後の記録同期）＋ SRS 機能要件（**同一エラーがN回連続したら自動停止して通知**）

### FP-006: エラーが握りつぶされ、異常が「無言で」継続した
- **事実**: 上記のエラーは docker logs には ERROR として連続出力されていたが、通知にも停止にも繋がらず、オーナーが成績確認を依頼するまで21日間発覚しなかった。
- **→ 変換先**: SRS 非機能要件（監視・アラート）。**通知は「成功時」ではなく「異常時」に確実に出ることを受入基準にする**

### FP-007: 販売所APIを使い、手数料が実質0.5%かかっていた
- **事実**: Coincheck の販売所経由の実質コストは約0.5%。板（現物取引）へ切り替えて 0.02% になり、**年間84%の手数料削減**と記録されている。売買が頻繁なほど、この差が戦略の生死を分ける。
- **→ 変換先**: スクリーニング基準 S4（コスト後生存）／SRS 外部インターフェース要件（板APIの使用を必須とする）

## C. 運用・インフラの失敗

### FP-008: SQLite DBを Google Drive 配下に置いて破損させた
- **事実**: 同期の書込干渉で `database disk image is malformed` が発生し、608銘柄中483銘柄まで取得した時点でDBが壊れた。ローカルディスクへ移管して解決。
- **→ 変換先**: CONSTRAINTS.md の禁止事項（**データ格納先を同期フォルダ配下に置かない**）

### FP-009: 外部APIの仕様変更でクライアントが全損した
- **事実**: J-Quants が V1（email+password → refresh_token）を廃止し V2（x-api-key ヘッダー直接認証）へ移行。既存クライアントは 400 を返し続け、全面書き直しになった。
- **→ 変換先**: SDD（外部APIはアダプタ層で隔離し、仕様変更の影響をアダプタ内に閉じる）／SRS（APIバージョン変更の検知）

### FP-010: VPSへローカルの新版を丸ごと置いて依存不足で起動不能にした
- **事実**: ローカルの新 `trader.py` を VPS に丸ごとコピーしたところ、oanda/saxo/httpx の依存が足りず Restarting ループ。ロールバックし、**VPS側の旧ベースに最小diffだけ当てる**方式に転換して復旧した。
- **→ 変換先**: SDD デプロイ設計（デプロイは全置換ではなくビルド成果物単位・ロールバック手順を必須）

---

## D. 戦略ポートフォリオ設計の失敗

### FP-011: ロング戦略のみで構成し、下落相場に一方的に弱かった
- **事実**: 初期構成は BTC/ETH/SOL/XRP の3ロング戦略のみ。下落相場に弱いことが判明してからショート戦略の追加を検討し始めた。後付けで方向性を足したため、戦略間の相関設計が最後まで行われなかった。
- **→ 変換先**: スクリーニング基準 S8（戦略間の相関）／SRS（採用戦略の収益源が偏っていないことを受入基準にする）

### FP-012: 「実装完了」と「収益が出る」を混同した
- **事実**: ショート戦略 Phase 2 は工程1〜6まで実装・テスト（品質スコア88〜100点）を完走し「本番投入準備完了状態」と記録されたが、実弾検証には至らず、その後の戦略変更（RSI(2)＋CMEベーシスへ）で丸ごと使われなくなった。**品質スコアは実装の品質を測っていたが、戦略の有効性は測っていなかった**。
- **→ 変換先**: SRS 受入基準（**フォワード（ペーパー）検証の通過を、実装完了とは別のゲートとして定義する**）／PROGRESS の Exit Criteria

## E. 意思決定プロセスの失敗

### FP-013: 戦略が短期間で二転三転し、どれも検証を完了しなかった
- **事実**: 2026-04 チャートパターン（ロング3種）→ 2026-04 ショート戦略追加 → 2026-07 RSI(2)平均回帰＋CMEベーシス（quant-bot）へ全面変更 → 2026-08 全停止。**4か月で3回、戦略の土台が変わった**。そのたびに実装は進んだが、どの戦略も実弾での検証を完了していない。
- **なぜ起きたか**: 「次に調べた戦略の方が良さそうに見える」という理由で乗り換えられる状態だった。乗り換えの是非を判定する基準がなかった。
- **→ 変換先**: SRS 変更管理（**採用戦略の変更には、既存戦略が事前に定めた撤退基準に触れたという根拠を要する**）。新しく良さそうな戦略が見つかったことは、既存戦略を止める理由にならない

### FP-014: ブロッカーの記述が古いまま4か月放置された
- **事実**: HANDOFF の「ブロック中」に載っていた `Binance Futures API Key 未発行` は、戦略変更によりとっくに無効化されていたが、2026-08-16 の棚卸しまで4か月間そのまま残り、意思決定を止め続けた。
- **→ 変換先**: PROGRESS.md の状態ログ運用（ブロッカーには必ず「いつ・何を確認したか」を書く）
