## 2. Blocker 一覧（重複を除いて9件）

### B-01 損切り価格が存在しない（I-01 / RV-05）
FR-RISK-001 は「1トレードの想定損失が口座残高の1.0%を超える発注をしない」と定めるが、
**「想定損失」の定義がどの文書にもなく**、SDD §1.3 の `Signal` にも `orders` にも `positions` にも
損切り価格の項目がない。RiskGate は想定損失を算出できない。FR-BT-008（ギャップ時の始値約定）も同様に実装できない。

**これは安全装置の筆頭が実装不能ということである。** 完全自動発注を選んだ以上、ここが空いていると
残りの安全装置は意味をなさない。

### B-02 冪等キーが FP-005 に逆経路で到達する（実装側 穴1）
**最も危険な指摘。** ADR-006 の冪等キー `sha256(strategy_id + symbol + as_of + side)` は
同一シグナルの再送を弾く。ところが FR-EXEC-006 は「同一の発注エラーが3回連続したら停止」を求める。

拒絶された注文を再試行しようとしても**冪等キーが同一なので発注自体が行われず**、
`consecutive_failures` が増えない。したがって3回に到達せず、**停止も通知も起きない**。

旧システムは「再送し続けて21日間ループした」。今回の設計は「再送されず、無言で止まる」。
**症状は逆だが、結果は同じ——誰も気づかないまま機能停止する。** FP-005 と FP-006 の再発である。

### B-03 ドローダウンが約定駆動でしか更新されない（実装側 穴2）
資産評価額とDDの更新契機が約定に紐づいているため、**約定が発生しない含み損の拡大局面で
DD15%（ロット半減）もDD25%（全停止）も発火しない**。相場が一方向に動いてポジションを抱えたまま
沈んでいく、まさに安全装置が必要な場面で動かない。

### B-04 失敗カウンタが原理的に3回に到達しない（実装側 穴3）
失敗カウンタが戦略単位で、別注文の成功でリセットされる。さらに「同一エラー」の判定を
**理由の文字列**で行うため、残高の実数値が含まれるエラーメッセージ（例:「insufficient balance: 0.00132648」）は
毎回別の文字列になる。**3回連続という条件が永久に成立しない。**

### B-05 kill switch の入力経路が存在しない（I-02）
FR-RISK-006 は「外部から60秒以内に全停止」を求めるが、GUIはなく、Notifier は送信専用で受信機能がない。
**停止指示をどこから入れるのかが設計されていない。** TC-R06 と E2E-B01 の手順が書けない。
「オーナーの明示的な再開指示」も同様。

### B-06 追記のみの記録と状態遷移が両立しない（I-03）
`orders.state` を持ちながら INV-22 で「追記のみ・更新禁止」としている。
一方 E2E-N01 は `state == FILLED` を確認せよと求める。**TC-C01 と E2E-N01 が同時に成立しない。**

### B-07 「口座残高」「口座全体のDD」が未定義（I-04）
INV-23 は「損益を市場ごとに分離し、合算した損益を確定値として扱わない」と定める。
一方 FR-RISK-004/005 は「**口座全体の**ドローダウン」で発火する。**両者が衝突している。**
`account_state` の型定義もない。

### B-08 DD25%が採用候補の想定DDの内側にある（RV-02）
安全装置の全停止水準（DD25%）が、採用候補の想定DD（暗号資産の中核戦略で30〜40%）**より内側**にある。
**戦略が正常に機能している下落局面で恒久停止する。**
DD15%のロット半減も、トレンドの回復局面で損失を固定する方向に働く。

オーナー回答の「DD25%以内」をそのまま安全装置の閾値に写し、**戦略側の想定DDと突き合わせていなかった**
ことが原因である。目標としてのDDと、停止閾値としてのDDを混同した。

### B-09 フォワード検証ゲートに到達できない（RV-03）
`BACKTEST_PROTOCOL.md` §7 のゲートは「最低3か月かつ30トレード」。
中核候補 CR-01（時系列モメンタム）は**年2〜10回**しか売買しない。30トレードには数年かかる。
**Phase 5 に到達する経路が存在しない。** SRS 自身が R4 で「検証期間中に一度もエントリーが
発生しない可能性」を認めており、矛盾が文書内で閉じている。

## 5. 私（設計者）の総括

指摘の多くは**私が作り込んだ問題**である。弁解せずに記す。

1. **オーナーの回答を、意味を確認せずに数値として写した。** 「DD25%以内」は目標の表明であって、
   安全装置の発火水準ではない。両者を突き合わせていれば B-08 は起きなかった
2. **安全装置を個別に設計し、相互作用を検証しなかった。** 冪等キー（ADR-006）と失敗カウンタ
   （FR-EXEC-006）は、単体ではどちらも正しい。組み合わせると B-02 になる
3. **「構造で防ぐ」と宣言しながら、その構造自体を検証しなかった。** ADR-007 も ADR-012 も
   考え方としては正しいが、実装可能性を詰めていない
4. **文書の量を進捗と取り違えた。** 7,392行を書いて実装は0行。事業側レビューの
   「文書を作ることが目的化していないか」という問いに、**私は明確に反論できない**

FP-012（実装完了と収益を混同した）を台帳に書きながら、**私は FP-012 の変種をやっていた**——
文書完成と進捗を混同していた。

## 6. RYG 判定

**Red。** 根拠は次のとおり。

- Blocker 9件。うち B-01〜B-04 は**安全装置が機能しないことを意味する**
- FP-005・FP-006 の再発経路が、対策したはずの設計の中に残っている
- 同時に合格し得ないテストの組が4組ある
- Phase 5 への到達経路が存在しない（B-09）
- 期待値に対する工数が、どちらの見積りでも成立しない

**nagame-dev の黄金ルール7に従い、この Red は失敗ではなく「壊れる前に止められた」ものとして扱う。**
実装に入っていれば、これらは実弾を動かす段階まで発見されなかった可能性が高い。
