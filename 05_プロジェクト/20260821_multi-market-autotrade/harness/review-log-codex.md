## 2. 安全装置の穴（詳細・発生シナリオつき）

### 穴1: 冪等キーが「拒絶後の再試行」を潰し、決済不能ポジションが放置される（I-05, S-04）

**シナリオ**
1. 日足戦略 ST-01 が 2026-09-01 のバーで BTC の決済シグナルを出す。冪等キー K = `sha256("ST-01"+"BTC_JPY"+"2026-09-01T00:00:00Z"+"SELL")`。
2. 実残高不足で拒絶される（FP-005 と同じ状況）。`consecutive_failures = 1`。
3. 次のサイクル（4時間後）。同じバーが最新の確定バーなので `as_of` は変わらず、**冪等キーは K のまま**。
4. OrderRouter は FR-EXEC-004（同一キーの二重送信禁止）に従い、`place` を呼ばずに弾く。
5. **`consecutive_failures` は 1 のまま増えない。** FR-EXEC-006 の「3回連続で停止」は永久に発火しない。
6. 通知も出ない（FR-MON-001 は発注APIのエラーに反応するが、送信自体が行われていない）。
7. ポジションは決済されないまま残り続ける。**FP-005（21日間ループ）と同じ結果に、逆の経路で到達する。**

**なぜ文書から検出されるか**: TC-E04（place 呼び出し 1回）と TC-E06／E2E-A01（place 呼び出し 3回）が同一の入力条件で両立しないため。

**修正**: I-05 のとおり冪等キーに attempt_no を含め、S-04 のとおり失敗カウンタを注文系列単位・エラーコード単位で持つ。

---

### 穴2: DD の評価額が約定駆動でしか更新されず、最も必要な場面で全停止が発火しない（S-03）

**シナリオ**
1. BTC ロングを1件保有。ST-01 はエントリー条件を満たさなくなり、以後シグナルを出さない（SRS R4 が想定する「現金退避が続く」局面の逆で、建玉を持ったままの局面）。
2. BTC が数日で 30% 下落する。約定は1件も発生しない。
3. SDD §2.1 手順9「約定結果を Ledger に追記し、PositionManager が損益とDDを更新」しか評価額の更新経路がないため、**pnl_daily の評価損益と DD が更新されない**。
4. RiskGate が参照する DD は古いまま。DD 15%（数量半減）も DD 25%（全停止）も発火しない。
5. 実際の口座は DD 30% を超えている。§1.3 の最大DD25%は既に破られているが、システムは何も検知していない。

**修正**: サイクル開始時にマーク価格を取得して評価額と DD を必ず更新する手順を追加し（S-03）、TC-R05 の前提条件に「約定0件のサイクルで DD が更新されること」を加える。

---

### 穴3: 「同一エラー3回連続」が成立せず、FP-005 の21日ループが再発する（S-04）

**シナリオA（別注文の成功でリセット）**
1. ST-01 が BTC と ETH の2銘柄を扱う。BTC の決済が残高不足で拒絶される（失敗1）。
2. 同サイクルで ETH の新規建てが成功する。`strategy_state.consecutive_failures` は戦略単位の単一カウンタなので **0 にリセットされる**。
3. 以後、BTC の失敗と ETH の成功が交互に続く限り、カウンタは 1 を超えない。BTC のポジションは永久に決済されない。

**シナリオB（エラーメッセージの揺らぎ）**
1. 取引所が返す拒絶理由が `Amount 0.00133 has insufficient BTC balance (available 0.00132648)` のように**数量を含む**。
2. 残高は約定手数料でわずかに動くため、毎回わずかに違う文字列が返る。
3. 「同一の」拒絶を文字列一致で判定していると、3回連続が永久に成立しない。

いずれも FP-005 の実害（決済されないまま21日）を再現する。TC-E06 は「常に同一の拒絶応答を返すモック」でしかテストしていないため、**どちらのシナリオも検出できない**。

**修正**: カウンタのスコープを `(strategy_id, symbol, side)`（または冪等キー系列）に、比較対象をエラーコードに変える。TC-E06 に両シナリオのケースを追加する。

---

### 穴4: 同一サイクルの複数シグナルが同時保有上限をすり抜ける（S-02）

**シナリオ**
1. 暗号資産市場のサイクルで、ST-01・ST-02・ST-03 が同時に新規シグナルを出す。既存ポジションは 2 件（上限は市場3）。
2. RiskGate は1件ずつ `evaluate(signal, account_state)` を評価する。`account_state` の生成タイミングが未定義であるため、サイクル開始時にスナップショットを取る実装だと3件とも「現在2件 < 3」で承認される。
3. 3件とも発注され、同時保有が 5 件になる。**市場上限3をすり抜ける。**
4. 同じ経路で、合計6件（INV-16）、1戦略配分40%（INV-19）、日次損失上限（INV-15）もすり抜ける。

**なぜ文書から検出されるか**: TC-R03 が「事前に3ポジション保有した状態で4本目を審査する」という直列前提でしか書かれておらず、1サイクル複数シグナルのケースを持たないため。SDD §2.2 の「逐次」は市場間・発注間の逐次であって、`account_state` の再取得を意味していない。

---

### 穴5: 切り捨て丸めが min_qty 未満のダストを生み、記録と実残高が乖離する（I-10, I-11）

**シナリオ**
1. 記録上 0.00133 BTC 保有、実残高 0.00132648、`qty_step = min_qty = 0.0001`。
2. FR-EXEC-001/002 に従い、実残高を切り捨てた 0.0013 を決済する。
3. **0.00003 BTC が残る。min_qty 未満なので二度と単独では決済できない。**
4. E2E-N02 の合格条件は「positions の行数 == 0」なので、実装は positions 行を削除する。以後、**記録では 0、実残高では 0.00003** という乖離が恒久化する。
5. 次に同じ銘柄を建てるとき、FR-EXEC-001（実残高照会）で 0.00003 が加算され、想定より大きい建玉になる。1トレード上限の計算がずれる。

これは FP-005 が生まれたのと同じ「記録と実残高の乖離」であり、テスト計画自身がそれを合格条件として要求している。

---

### 穴6: DD25% 全停止がポジションを放置し、DD が上限の外へ拡大する（S-06）

**シナリオ**
1. 評価額が HWM から 25% 下落。FR-RISK-005 で全戦略が停止する。
2. E2E-B01 ケースB の合格条件は「その後の place 呼び出し == 0」。決済注文も送れない。
3. 相場がさらに下落し、DD は 35%、45% と拡大する。システムは何もしない。
4. オーナーが再開指示を出しても、S-05 のとおり HWM が 520,000円のままなので DD は 25% 以上であり、RiskGate が即座に再停止する。**手動決済以外に出口がない。**

「最大DD25%以内」（§1.3）を守るための装置が、25%を超えた損失の拡大を止められない構造になっている。

---

### 穴7: プロセス落下時に孤児注文が残る（S-08, S-09）

**シナリオ**
1. OrderRouter が `place` を送信する。取引所は受理する。
2. 応答を受け取る前にプロセスが落ちる（VPS の OOM、デプロイ、電源）。
3. `orders` への追記が送信の**後**に設計されていれば、システムには注文の記録がない。
4. 再起動時、Reconciler は「記録にある UNKNOWN 注文」を照会するが、**記録が存在しないため照会対象にならない**。
5. 取引所側では約定してポジションが立つ。RiskGate はそのポジションを知らないまま、同時保有数を1件少なく数え続ける。

TC-P04 は「UNKNOWN の注文が1件ある状態で SIGKILL」しかテストしておらず、このケースを検出しない。

---

### 穴8: 日次損失上限の日境界が未定義で、実質2倍使える（S-07）

**シナリオ**
1. 内部時刻は UTC（ADR-011）。日次損失カウンタが UTC 00:00 でリセットされる実装になる。
2. JST では 09:00 のリセット。JST の 1営業日（09:00〜翌09:00）は UTC の2日にまたがる。
3. JST 08:00 までに 3.0%（15,000円）の実現損失を出して当日停止 → JST 09:00 に UTC 日付が変わってカウンタがリセット → 同じ JST の日にさらに 3.0% を失える。
4. **日次損失上限が実質 6.0% になる。** DD 25% までの到達が想定の半分の日数で起こる。

さらに「日をまたぐ注文」（前日に送信、翌日に約定）の損益をどちらの日に帰属させるかが未定義であるため、境界付近では意図的でなくても上限をまたげる。

### 最も工数を食う箇所

1. **バックテストエンジンの自作（ADR-003）＋ ベクトル化二重実装（FR-BT-006）— 単独で 80〜120時間。**

### 価値との対比

SRS §15 R6 が明記する期待値は**税引後 年3.5〜4万円**。実作業 435〜600時間に対して、**時給換算で 60〜90円**である。1年目で回収できるのは投下時間の1%に満たない。

この事実は SRS 自身が R6 として認識しているが、再評価のタイミングが P4 終了時（＝工数の85%投下後）に置かれている。**E-01 の Phase 0 を挿入し、「Green 戦略が1件も出ない」場合に 40時間で撤退できる分岐を作ることを強く推奨する。** それをしないなら、本プロジェクトの正当化理由は収益ではなく学習であると SRS §1.1 に明記すべきで、その場合は P3〜P5 のスコープ（実弾投入）を落とす選択肢も検討対象になる。

## 4. 総合判定

### **Red**

`harness/HARNESS.md` §8 の RYG 基準（Red = 未達3件以上、またはバイアス未解消、**または安全装置の未実装**）に照らして Red とする。

**理由**

1. **Blocker 5件が未解決である。** うち3件（I-01 損切り価格の不在、I-04 口座残高・DDの定義不在、I-05 冪等キーと再試行の衝突）は、安全装置の中核（RiskGate と OrderRouter）が**そもそも実装できない**ことを意味する。I-03（orders.state の自己矛盾）はデータモデルの根幹であり、Ledger・OrderRouter・Reconciler の3コンポーネントが着手できない。

2. **安全装置に、FP-005 と FP-006 の再発経路が残っている。** 穴1・穴3 は「決済されないポジションが放置され、通知も停止も起きない」という旧システムの故障形態を、別の経路で再現する。本プロジェクトの存在理由がその再発防止である以上、これは致命的である。穴2（DD が約定駆動でしか更新されない）は、最大の安全装置が最も必要な局面で動かないことを意味する。

3. **文書間に、テストが同時に合格し得ない矛盾が3組ある。** TC-E04 対 TC-E06/E2E-A01（穴1）、TC-C01 対 E2E-N01（I-03）、E2E-N02 の「0.0013 を発注して positions を0行にする」（穴5）、E2E-B01 手順4（S-05）。これらは実装以前に文書側で解決する必要がある。

4. **CI の中核（G-01〜G-03）が、宣言された手段（AST 走査）では実装できない。** G-03 はデータフロー解析であり、G-01/G-02 は DI を前提とする本設計では原理的に呼び出し先を特定できない。「機械的に強制している」という前提が成立しないまま緑が出続ける状態は、規律に依存していた旧システムより危険である（検査があると信じてしまうため）。

5. **トレーサビリティの「未接続0件」という主張が2箇所で誤っている。** SDD §7 に FR-DATA-007〜010 がない（I-12）。BP§3.3・§4 C3〜C6 に対応する要件も TC もない（I-13）。REL-01 はこの表を根拠に判定されるため、判定基準そのものが機能していない。

**Green へ向かうための最短経路**

1. Blocker 5件を SRS/SDD の改版で解消する（見積り 12〜16時間）。特に I-04（口座残高と DD の定義）と I-05（冪等キー）は、他の指摘の前提になるため最初に決める。
2. 安全装置の穴1〜8 を SRS §6.5 と SDD §2.1〜2.3 に反映し、対応する TC を追加する（見積り 10〜14時間）。
3. HARNESS §4 の G-01〜G-04 を、静的検査から**型検査＋実行時ガード**へ書き換える（見積り 4〜6時間）。
4. I-13（BP §3.3・C3〜C6 の要件化）と I-12（SDD §7 の補完）でトレーサビリティを閉じる（見積り 6〜8時間）。
5. **その後、実装（P1）ではなく Phase 0（E-01）から入る。**

上記1〜4を終えれば Yellow、Phase 0 で Green 戦略が1件以上出た時点で P1 着手の判断材料が揃う。
