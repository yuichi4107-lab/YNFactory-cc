- 開始日: 2026-08-21
- 進行方式: nagame-dev v2.0（IEEE 29148 / ISO 25010 / IEEE 1016 / IEEE 829 / Google SRE PRR 準拠）

- **ユーザー判断ポイント: Phase 2（要件定義 SRS）完了時点で「実装するか否か」を決める。→ 2026-08-21 に「進む」を受領。実装は Phase 5（レビューGO判定）通過後に開始する**

## 工程分解

### Phase 0 — ヒアリング（★現在ここ）
- 初期4問（資金 / 運用スタイル / 自動化レベル / リスク許容度）＋口座・API保有状況の確認
- 成果物: `docs/00_intake_sheet.md`（ヒアリングシート＋スコープ表 IN/OUT/DEFER）
- 完了条件: 仮置き★が5個以下、矛盾ゼロ、スコープ確定
- 使用モデル: Opus（判断の分岐が大きいため）

### Phase 1a — 戦略カタログ収集（100件）
- 世界中の投資戦略を **仮想通貨40 / FX30 / 日本株30 = 100件** 収集
- 1件あたり記録項目: 戦略名 / 市場 / 保有期間 / ロジック要旨 / 主張されるエッジの理由 / 出典URL / 信頼度(A〜D) / 必要データ / 概算キャパシティ
- 出典は学術論文（SSRN・arXiv・Journal of Portfolio Management等）、取引所公式、著名OSS、実運用レポートを優先。個人ブログは信頼度C以下として扱い、単独では採用根拠にしない
- 成果物: `research/strategy_catalog_100.md`
- 使用モデル: **Fable**（広く浅い収集は並列数を稼ぐ方が効く）。市場別に3エージェント並列

### Phase 1b — 絞り込み（100 → 20 → 5〜8）
- 9基準スクリーニング（下表）でスコアリングし、二段階で絞る
- 落とした戦略も「なぜ落としたか」を必ず残す（後で復活検討できるように）
- 成果物: `research/strategy_screening.md` + `research/research_v1.md`
- 使用モデル: **Opus**（採否判断・エッジの真贋判定は難度が高い）

| # | 基準 | 落とす条件の例 |
|---|---|---|
| S1 | エビデンスの質 | 出典が信頼度C以下のみ / 再現研究なし |
| S2 | 個人資金で執行可能か | 最低ロット・証拠金が想定資金を超える |
| S3 | データ入手性 | 有料データ月数万円が必須 |
| S4 | コスト後生存 | 手数料・スプレッド・スリッページ控除で優位性が消える |
| S5 | キャパシティ | 板が薄く想定ロットで滑る |
| S6 | 実装難度 | 低遅延インフラ（HFT）が前提 |
| S7 | 税制・規制 | 日本の課税区分・金商法・取引所規約に抵触 |
| S8 | 戦略間の相関 | 既採用戦略と収益源が同じ |
| S9 | 失敗の再現 | 旧システムが同じ理由で失敗している |

### Phase 1c — 技術リサーチ V2（実行可能性の裏取り）
- ブローカー/取引所API（発注・レート制限・規約）、データソース、税制、VPS構成、バックテスト基盤（vectorbt / backtrader / nautilus_trader 等）を一次ソースで確認
- 「絞り込んだ戦略が本当にこの環境で回せるか」を戦略ごとに突き合わせる
- 成果物: `research/research_v2.md`（確定 / 推奨 / 要注意 の3分類）
- 使用モデル: Opus（規約・税制の読み取り）＋ Fable（API仕様の機械的な収集）

### Phase 1d — バックテスト設計の妥当性検証
- 過剰最適化を防ぐ手順を先に決める: In-Sample / Out-of-Sample 分割、ウォークフォワード、複数期間・複数銘柄での頑健性、取引コストモデル、生存バイアス・先読みバイアスの排除
- **旧システムの最大の失点はここ**（上昇相場のみのバックテストで合格判定していた）ので、要件として明文化する
- 成果物: `docs/BACKTEST_PROTOCOL.md`
- 使用モデル: Opus

### Phase 2 — 要件定義 SRS ★ユーザー判断ポイント
- IEEE 29148 準拠。全Must要件に Evidence ID（Phase 1の出典）と TC-*（テストID）を接続
- ISO 25010 の9品質特性で非機能要件を定量化
- リスク管理要件（1トレード上限・日次損失上限・最大DD・kill switch・二重発注防止・約定不整合検知）を機能要件として明記
- 成果物: `docs/SRS.md` + 100点18項目の自己採点
- 使用モデル: Opus
- **→ ここでユーザーが実装可否を判断する。GOが出るまで Phase 3 以降へ進まない**

## 安全側の不変条件（Phase 0 時点で確定・以後変更不可）

1. **実弾発注は Phase 8 まで一切行わない**。Phase 6-7 はペーパートレード / DRY_RUN のみ
2. 稼働中・停止中を問わず、既存の `/opt/ai-trader/` および旧FXデーモンには触らない
3. APIキーはリポジトリに置かない。`.env` は commit しない
4. 実弾移行時も、初回は最小ロット1件のみ → 段階拡大
5. 「バックテストが良い」だけでは Green にしない。フォワード（ペーパー）で規定期間の検証を通すこと
