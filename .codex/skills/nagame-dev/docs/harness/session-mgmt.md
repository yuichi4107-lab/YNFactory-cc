# セッション管理（50往復ルール）

Claude Code のセッション間記憶喪失に対処するための運用ルール。
PROGRESS.md を「外部記憶」として使い、セッション切替時の情報損失をゼロにする。

---

## 50往復ルール

**会話が50往復を超えたら、必ずセッションを切り替える。例外なし。**

### なぜ50往復か

Claude Code はセッションが長くなると「コンテキスト枯渇」が起きる。
コンテキスト枯渇とは、会話の初期に与えた指示（CLAUDE.md の禁止事項、SRS の要件等）の優先度が下がり、守られなくなる現象。

例え話で言うと、机の上に書類を積み上げていくイメージ。最初に置いた重要な書類（設計書）が、後から積んだ書類（実装の議論）に埋もれて見えなくなる。50枚目あたりで限界が来る。

50往復は安全限界の目安であり、プロジェクトの複雑さによっては30-40往復で兆候が出ることもある。

---

## セッション終了手順

50往復に達した場合、または1フェーズが完了した場合に実行する。

### Step 1: git commit（該当する場合）

```
git add [変更ファイル]
git commit -m "type: [変更内容の要約]"
```

- コミットメッセージは変更内容を正確に反映する
- 未完了の作業がある場合も中間コミットする（作業状態の保全）

### Step 2: PROGRESS.md を更新

以下の形式でセッション記録を追記する:

```markdown
## セッション [N] 完了 — [YYYY-MM-DD]

### フェーズ: Phase [N] — [フェーズ名]

### 完了タスク
- [具体的に何を完了したか]
- [具体的に何を完了したか]

### 次のアクション（次セッションで最初にやること）
- [ ] [具体的なタスク]
- [ ] [具体的なタスク]

### 未解決問題（持ち越し）
- [解決できなかった問題と、その状況]
- [試した対処法と、なぜうまくいかなかったか]

### 学んだこと（knowledge候補）
- [このセッションで得た知見]
- [次回以降に役立つ情報]

### RYGステータス
- Phase [N]: [Green / Yellow / Red] — [理由]

### ファイル変更一覧
- [変更したファイルのパスと変更概要]
```

### Step 3: セッション引き継ぎメモ（複雑な状態の場合）

未解決問題が複雑な場合、PROGRESS.md に加えて引き継ぎメモを作成する:
- 現在のコードの状態（何が動いて何が動いていないか）
- デバッグ途中の場合: 何を試して何が分かっているか
- 設計判断の途中の場合: どの選択肢を検討中か

### Step 4: 社長への報告

```
50往復に達したため、セッションを切り替えます。
PROGRESS.md に状態を保存しました。

今回の成果: [1-2行で要約]
次回の予定: [1-2行で要約]
```

## 新セッション開始手順

### Step 1: 必読ファイルの読了

以下の順序で読む:

1. **CLAUDE.md** — プロジェクト全体の指示書（13パート構成）
2. **CONSTRAINTS.md** — 禁止事項・制約（6セクション構成）
3. **PROGRESS.md** — 最新のセッション記録（直近のエントリを重点的に）

### Step 2: 前回の続きを把握

PROGRESS.md の「次のアクション」と「未解決問題」を確認する。

### Step 3: 作業再開

前回のセッションで中断した箇所から再開する。
新しいことを始める前に、必ず中断した作業を片付ける。

## コンテキスト枯渇の緊急対応

### 兆候の検出

以下の兆候が1つでも現れたら、コンテキスト枯渇が発生している可能性がある:

| 兆候 | 具体例 |
|---|---|
| **制約忘れ** | CONSTRAINTS.md の禁止事項を破る |
| **反復ミス** | 同じ間違いを2回以上繰り返す |
| **要件忘れ** | SRS に書かれた要件を無視した実装をする |
| **文脈喪失** | セッション前半の決定事項と矛盾する発言をする |
| **品質低下** | コードの品質が明らかに後半で落ちる |

### 緊急対応手順

**劣化した状態で作業を続けてはならない。即座に停止する。**

1. **即座に作業を停止する**
   - 中途半端な状態でも止める
   - 「もう少しだから」と続けない

2. **PROGRESS.md に状態を保存する**
   - 通常のセッション終了手順と同じ形式で記録
   - 追記: 「コンテキスト枯渇により緊急切替」と明記

3. **git commit する**
   - 作業途中でもコミット（状態保全が目的）
   - メッセージ: `chore: セッション緊急切替（コンテキスト枯渇）`

4. **社長へ報告**
   ```
   コンテキスト枯渇の兆候があります。セッションを切り替えます。
   PROGRESS.md に状態を保存しました。
   次のセッションで [タスク名] の続きから再開します。
   ```

## フェーズ別セッション数の目安

| フェーズ | 推奨セッション数 | 上限 | 備考 |
|---|---|---|---|
| Phase 0 (取り込み) | 1 | 1 | 要件ヒアリング |
| Phase 1 (リサーチ) | 1-2 | 2 | 技術調査 |
| Phase 2 (SRS) | 1-2 | 2 | 要件定義 |
| Phase 3 (SDD) | 1-2 | 2 | 設計 |
| Phase 4 (テスト/ハーネス) | 1 | 2 | テスト計画・ハーネス設定 |
| Phase 5 (レビュー) | 1-2 | 2 | 設計レビュー |
| Phase 6 (実装) | 2-5 | 制限なし | スコープに依存 |
| Phase 7 (検証) | 1 | 2 | 受入検証 |
| Phase 8 (移行) | 1 | 2 | デプロイ・移行 |

**実装フェーズ以外は最大2セッション**: 2セッションで終わらない場合、スコープが大きすぎる可能性がある。スコープの見直しを検討する。

## PROGRESS.md の運用ルール

### 書く内容
- セッション番号（連番）
- フェーズと日付
- 完了タスク・次のアクション・未解決問題・学んだこと
- RYG ステータス
- ファイル変更一覧

### 書かない内容
- コードの全文コピー（ファイルパスと変更概要のみ）
- 議論の逐語録（結論のみ）
- 感情や主観的な評価

### サイズ管理
- 1セッション分の記録は20-40行を目安にする
- 10セッションを超えたら、古いセッション記録をアーカイブセクションに移動する
- アーカイブしても削除はしない

### 読み方の優先度
- 新セッション開始時: 最新の1-2セッション分を詳細に読む
- 過去のセッション: 「次のアクション」と「未解決問題」だけ確認
