# 再リサーチトリガー（8条件）

本ドキュメントは、レビューや実装で問題が発見された際に「すぐ修正」ではなく
「まず根拠調査に戻す」ための判定条件と運用ルールを定義する。

---

## 原則

レビューで問題が見つかった時の正しい対処は:

1. **まず根拠調査に戻す**（再リサーチ）
2. 調査結果を要件・仕様・テスト・ハーネス・リスク台帳のいずれかに反映する
3. 反映先が更新された状態で修正を実施する

**禁止されるパターン**: 問題を見つけた → すぐコード修正 → 閉じる（黄金ルール#5, #6違反）

反映先のない調査はプロジェクトを安全にしない。調査結果は必ずプロジェクト文書に還元する。

---

## 8つのトリガー条件

### トリガー1: API制限で不安定

| 項目 | 内容 |
|---|---|
| **発火条件** | 外部APIのRate Limit超過、タイムアウト、断続的な接続失敗が発生 |
| **再リサーチの焦点** | 公式推奨のリトライ戦略、バックオフ設計、キュー設計、代替エンドポイント |
| **調査の信頼度要件** | 信頼度A必須（公式APIドキュメントのRate Limitページ） |
| **反映先** | SDD（リトライ設計）+ HARNESS（サーキットブレーカー、フォールバック） |
| **完了条件** | 公式推奨に基づくリトライ設計がSDDに記載され、dry-runで動作確認済み |

### トリガー2: E2Eが不安定

| 項目 | 内容 |
|---|---|
| **発火条件** | E2Eテストが同一条件で成功/失敗を繰り返す（フレーキーテスト） |
| **再リサーチの焦点** | 非同期処理のタイミング問題、テストfixture、環境差分、外部依存 |
| **調査の信頼度要件** | 信頼度B以上（テストフレームワーク公式ドキュメント、著名なCI/CDベストプラクティス） |
| **反映先** | TEST_PLAN（テスト安定化戦略）+ E2Eシナリオ（待機戦略・リトライ設計） |
| **完了条件** | 同一テストが10回連続で同一結果を返すことを確認 |

### トリガー3: 規約リスク発見

| 項目 | 内容 |
|---|---|
| **発火条件** | 使用中のAPIや外部サービスの利用規約に抵触する可能性が判明 |
| **再リサーチの焦点** | 公式規約原文、禁止事項一覧、代替API、類似サービスの規約比較 |
| **調査の信頼度要件** | 信頼度Aのみ（公式Terms of Service） |
| **反映先** | SRS（規約制約の要件追加）+ RISK（規約違反リスクの登録） |
| **完了条件** | 規約準拠が確認されるか、代替手段への切り替え計画が策定される |

### トリガー4: 誤操作リスク

| 項目 | 内容 |
|---|---|
| **発火条件** | ユーザーまたはシステムの誤操作で不可逆な被害が発生し得る箇所が判明 |
| **再リサーチの焦点** | 権限設計のベストプラクティス、承認フロー、undo機能、kill switch設計 |
| **調査の信頼度要件** | 信頼度B以上 |
| **反映先** | HARNESS（安全装置設計）+ CONSTRAINTS（操作制約定義） |
| **完了条件** | 全ての不可逆操作にdry-run/承認ゲート/kill switchのいずれかが設計済み |

### トリガー5: 根拠不足

| 項目 | 内容 |
|---|---|
| **発火条件** | Must要件の根拠となるEvidence IDが存在しない、または信頼度C/D以下のみ |
| **再リサーチの焦点** | Must判断の公式根拠（一次ソース） |
| **調査の信頼度要件** | 信頼度A必須（Must要件の根拠は黄金ルール#1） |
| **反映先** | SRS（Evidence Matrix の更新） |
| **完了条件** | 該当Must要件に信頼度AのEvidence IDが接続されるか、Must→Shouldに降格 |

### トリガー6: 原因不明

| 項目 | 内容 |
|---|---|
| **発火条件** | CIが不安定だが、実装のバグかAPI制限か環境問題か原因が特定できない |
| **再リサーチの焦点** | エラーログの分類、類似事例の調査、環境差分の特定 |
| **調査の信頼度要件** | 信頼度B以上（類似事例）+ 自環境のログ（一次情報） |
| **反映先** | failure_patterns.md（失敗パターンの記録）+ SDD（設計見直しが必要な場合） |
| **完了条件** | 原因が特定され、failure_patterns.md に分類・対策が記録される |

### トリガー7: 運用不安

| 項目 | 内容 |
|---|---|
| **発火条件** | 非エンジニア（社長等）が運用手順を実行できない可能性がある |
| **再リサーチの焦点** | ユーザビリティのベストプラクティス、運用自動化手法、簡潔な手順書設計 |
| **調査の信頼度要件** | 信頼度B以上 |
| **反映先** | SRS（OPS要件の見直し）+ 運用手順書（手順の簡潔化・自動化） |
| **完了条件** | 運用手順が非エンジニアでも実行可能なレベルに簡潔化される |

### トリガー8: テスト不能

| 項目 | 内容 |
|---|---|
| **発火条件** | 受入基準（ACC-*）が曖昧でテストケース（TC-*）に変換できない |
| **再リサーチの焦点** | 受入基準のベストプラクティス、SMART基準、Given-When-Then形式 |
| **調査の信頼度要件** | 信頼度B以上 |
| **反映先** | SRS（ACC-*の具体化）+ TEST_PLAN（テストケースの追加） |
| **完了条件** | ACC-*が機械判定可能な形に具体化され、TC-*が作成される |

## 再リサーチの実行ルール

### 調査手段

| 手段 | 用途 | 信頼度 |
|---|---|---|
| WebSearch | 一般的な検索、初期調査 | 結果に応じてA〜D |
| WebFetch | 特定URLの内容取得、公式ドキュメント読み込み | 取得先に応じてA〜D |
| 公式ドキュメント直接参照 | API仕様・規約・Rate Limit確認 | A |
| OSSリポジトリ参照 | 実装例・設定例の確認 | B |

### 最大回数制限

- 同一論点につき再リサーチは **最大3回** まで
- 3回で解決しない場合は **社長にESCALATE** する
- ESCALATEの形式はescalation.mdに従う

### 記録ルール

- 全ての再リサーチ結果は **reproposal_log.md** に記録する
- 「調べたが見つからなかった」も否定的根拠として記録する
- 記録形式:

```markdown
### 再リサーチ: [トリガー番号] [概要]

- **発火日**: YYYY-MM-DD
- **トリガー条件**: #[N] [条件名]
- **調査内容**: [何を調べたか]
- **調査結果**: [何が分かったか / 分からなかったか]
- **信頼度**: A / B / C / D
- **反映先**: [どのファイルのどのセクションを更新したか]
- **完了判定**: 完了 / 未完了 / ESCALATE
- **残回数**: [N] / 3
```

## トリガー発火の判定フロー

```
レビューまたは実装中に問題が見つかった
  │
  ├── 8つのトリガー条件のいずれかに該当するか？
  │     ├── Yes → 再リサーチを実行（コード修正の前に）
  │     └── No  → 通常のバグ修正フローで対処
  │
  ├── 再リサーチの結果、反映先が特定されたか？
  │     ├── Yes → 反映先を更新してからコード修正
  │     └── No  → 追加調査またはESCALATE
  │
  └── 3回目の再リサーチか？
        ├── No  → 再リサーチを続行
        └── Yes → 社長にESCALATE
```

## 再リサーチとコード修正の順序

**正しい順序**:
1. 問題を発見する
2. トリガー条件を判定する
3. 再リサーチを実行する
4. 調査結果を文書（SRS/SDD/TEST_PLAN/HARNESS/RISK等）に反映する
5. 文書の更新に基づいてコードを修正する
6. 修正後のテストを実行する

**禁止される順序**:
1. 問題を発見する
2. すぐにコードを修正する ← **禁止**
3. テストが通ることを確認して閉じる ← **文書が更新されていない**
