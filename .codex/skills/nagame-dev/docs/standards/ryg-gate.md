# RYGゲート詳細定義

RYG（Red / Yellow / Green）は nagame-dev の全フェーズで使用するGO/NO-GO判定システムである。
全ての判定はこの3色のいずれかに分類され、曖昧な中間状態を許容しない。

---

## 1. 各色の定義

| 判定 | 意味 | 許可すること | 禁止すること |
|---|---|---|---|
| **Green** | 進めてよい | 次フェーズへの移行、限定リリース、本番接続 | 未記録の前提で進むこと、文書化されていない口頭合意での進行 |
| **Yellow** | 条件付き保留 | sandbox実行、PoC実施、追加調査、隔離環境でのテスト | 本番投入、不可逆操作、ユーザー影響のある変更、Yellow項目の放置 |
| **Red** | 停止 | 再リサーチ、設計変更、スコープ縮小、社長へのエスカレーション | 実装継続、本番接続、「後で直す」前提での進行、Red判定の無視 |

### 判定の原則

- **迷ったらYellow**: GreenかYellowか迷う場合はYellowにする
- **迷ったらRed**: YellowかRedか迷う場合はRedにする
- **格上げは根拠必須**: Red→Yellow、Yellow→Greenへの格上げには、根拠となる調査結果・修正内容を明示する
- **格下げは即時**: 新しいリスクが発見された場合、Green→Yellow→Redへの格下げは即時実行する

## 2. Green判定の12項目完了チェックリスト

全項目がチェック済みでなければGreen判定を出せない。1項目でも未チェックならYellow以下。

| # | 確認項目 | 確認内容 | 確認方法 |
|---|---|---|---|
| 1 | 目的 | 対象者・成功定義・失敗定義が明確か | OBJ-*の本文を確認 |
| 2 | 根拠 | Must判断が一次ソース（信頼度A）に接続されているか | Evidence Matrixを確認 |
| 3 | 要件 | 全要件がACC-*・TC-*・RISK-*に接続されているか | Traceability Matrixを確認 |
| 4 | 仕様 | 入力・処理・出力・例外が全て定義されているか | SDDの各コンポーネントを確認 |
| 5 | 技術 | 代替案と採否理由が記録されているか | SDDのTechnology Decisionを確認 |
| 6 | 外部API | 公式Docs・利用規約・Rate Limit・料金が確認済みか | API-*の調査結果を確認 |
| 7 | セキュリティ | 認証・認可・秘密情報管理・監査ログがあるか | SEC-*の定義を確認 |
| 8 | ハーネス | dry-run・mock・sandbox・kill switchが設計済みか | HARNESS設計書を確認 |
| 9 | テスト | Unit〜Acceptance全レベルのテストが設計済みか | TEST_PLANを確認 |
| 10 | CI | lint・test・build・secret scanがパイプラインに含まれるか | CI設定ファイルを確認 |
| 11 | 運用 | 監視・alert・rollback手順が定義されているか | OPS-*の定義を確認 |
| 12 | レビュー | Codex/Opus双方のBlockerが0件か | レビューログを確認 |

## 3. ループ停止条件

レビューの反復（ループ）を止めてよい条件。以下のいずれかを満たした場合にループを停止する。

| # | 停止条件 | 説明 |
|---|---|---|
| 1 | GO一致 | Codex と Opus の双方がGreen判定を出した |
| 2 | NO-GO原因の全タスク分解完了 | NO-GOの原因が全て具体的なタスクに分解され、対処計画がある |
| 3 | Later残存のみ | 残存する未解決項目が全て「Later（後続フェーズで対処）」分類 |
| 4 | 3ラウンド到達 | 同一観点で3ラウンド反復しても解決しない場合 |
| 5 | ESCALATE | 人間（社長）の判断が必要な論点に到達した場合 |

### ラウンド上限の運用

- 3ラウンドで解決しない場合、4ラウンド目に入る前に社長へエスカレーションする
- エスカレーション内容: 「何が解決しないか」「3ラウンドで試したこと」「推奨案」
- 社長の判断を受けてから継続・中止・方針変更を決定する

## 4. 完了宣言の禁止条件

以下のいずれか1つでも該当する場合、「Phase完了」「レビュー完了」「実装完了」等の完了宣言を出してはならない。

| # | 禁止条件 | 理由 |
|---|---|---|
| 1 | PROGRESS.mdの全項目が未チェック | 進捗管理が機能していない証拠 |
| 2 | Red判定が1件でも残存 | Redは停止を意味するため、完了と矛盾する |
| 3 | E2Eテストシナリオが未実行 | システム全体の動作確認がされていない |
| 4 | Must要件にACC-*またはTC-*が未接続 | 合否判定ができない要件が残っている |
| 5 | 破壊的操作にdry-run/sandboxがない | 黄金ルール#3違反 |
| 6 | レビュー指摘が再リサーチIDに変換されていない | 黄金ルール#5違反 |

---

## 5. RYG判定の記録形式

各判定は以下の形式で記録する。

```markdown
## RYG判定: [項目名]

- **判定**: Green / Yellow / Red
- **判定日**: YYYY-MM-DD
- **判定者**: Codex / Opus / 社長
- **根拠**: [判定の根拠を具体的に記述]
- **12項目チェック結果**: [該当する場合、12項目中N項目クリア]
- **残存リスク**: [Greenの場合でも、認識しているリスクがあれば記述]
- **次のアクション**: [Yellow/Redの場合、GOに戻すための具体的なアクション]
```

## 6. 色の遷移ルール

### 格上げ（より安全な方向への遷移）

| 遷移 | 必要条件 |
|---|---|
| Red → Yellow | 原因が特定され、PoC/sandbox で検証可能な状態になった |
| Yellow → Green | PoC/追加調査が完了し、12項目チェックリストを満たした |
| Red → Green | 原則禁止。Red→Yellow→Greenの段階を踏む（緊急時のみ社長判断で直接遷移可） |

### 格下げ（リスク発見方向への遷移）

| 遷移 | 条件 |
|---|---|
| Green → Yellow | 新しいリスク・未検証項目が発見された |
| Yellow → Red | PoC/調査の結果、Blockerが確認された |
| Green → Red | 重大なセキュリティ脆弱性・規約違反が発見された（即時停止） |

## 7. フェーズ別RYG適用ポイント

| フェーズ | RYG判定タイミング | 主な判定観点 |
|---|---|---|
| Phase 2（リサーチ） | リサーチ完了時 | 根拠の信頼度、情報の網羅性 |
| Phase 3（SRS） | SRS完成時 | 要件のID接続、品質スコア |
| Phase 4（SDD） | SDD完成時 | 技術選定、ハーネス設計、セキュリティ |
| Phase 5（レビュー） | 各ラウンド終了時 | 12項目チェック、Blocker残存数 |
| Phase 6（実装） | マイルストーン毎 | テスト結果、CI通過状態 |
| Phase 7（リリース） | リリース判定時 | 全項目Green、E2E通過 |
