# Adaptive Goal Loop

長期目標を安定させたまま、各サイクルの小目標だけを適応的に更新する。いきなり実行せず、質問、契約確認、実行の順に進める。

## 1. 最初に質問して停止する

初回起動時は、ファイル変更、`/goal`設定、定期タスク作成、実作業を行う前に、次の3点を一度に質問して回答を待つ。

1. **対象と到達点** — 何を、最終的にどの状態まで改善するか。
2. **完了の証拠と安全範囲** — 何を確認できれば完了か。変更禁止、予算、期限、承認必須操作は何か。
3. **実行方法** — 手動継続、30分ごと、その他の間隔のどれか。1サイクルの時間・作業量上限があれば何か。

質問UIが使える場合は選択肢を使う。実行間隔は「30分ごと」を推奨値として提示する。すでに答えがある項目は繰り返さず、不足項目だけを聞く。ただし、全項目が揃っていても、解釈した内容が正しいか一度確認する。

回答後も次が不明なら、最大3問だけ追加する。

- 最初に読む資料、成果物、ログ、URL、ディレクトリ
- 状態ファイルとログファイルの保存先
- 成果を判断する評価軸と優先順位

## 2. ループ契約を作る

回答を次の契約へ整理し、ユーザーに提示する。

- **固定する最終目標**
- **検証可能な完了条件**
- **対象範囲と変更禁止範囲**
- **承認が必要な操作**
- **参照する正本**
- **検証方法**
- **実行間隔と1サイクル上限**
- **状態・ログ保存先**
- **停止条件**

合理的に補える項目は推奨値を入れ、仮定であることを示す。最終目標、完了条件、安全範囲を推測で確定しない。

契約を確認してもらうまで、`/goal`や定期タスクを作成せず、成果物も変更しない。

## 3. 最終目標と小目標を分離する

- `/goal`を利用できる場合、確認済みの**最終目標を一度だけ設定**する。
- 毎回書き換えるのは最終目標ではなく、状態ファイルの`current_milestone`とする。
- ユーザーが「毎回ゴールを書き換える」と表現した場合も、通常は小目標の更新として扱う。
- 最終目標を変える必要が生じたら、旧目標、新目標、変更理由、影響範囲を示して承認を求める。
- `/goal`がない環境では、状態ファイルの`root_goal`を長期目標の正本にする。
- 既存のアクティブなゴールがある場合、無断で置き換えず、競合を報告する。

## 4. 状態とログを用意する

リポジトリ規約があればそれに従う。保存先が未指定なら対象プロジェクト配下を優先し、ルート直下へ勝手にファイルを増やさない。

状態ファイルには少なくとも次を持たせる。

```yaml
status: idle # idle | running | blocked | complete
cycle: 0
root_goal: ""
done_when: []
constraints: []
current_milestone: ""
last_verified_delta: ""
failure_streak: 0
run_started_at: null
last_finished_at: null
schedule_id: null
```

ログは追記型とし、各サイクルについて次を残す。

```markdown
## Cycle N — YYYY-MM-DD HH:mm
- 実行前の状態:
- 候補と採点:
- 選択した小目標と理由:
- 実行内容と変更対象:
- 検証方法と結果:
- 確認できた改善:
- 失敗・副作用:
- 次の小目標:
- ブロッカー:
```

## 5. 1サイクルだけ実行する

各起動につき次の順で1サイクルだけ進める。

1. 状態、ログ、成果物、指定資料を読む。
2. 前回の変更が本当に成功しているか再検証する。
3. 次の改善候補を3〜5件作る。
4. 各候補を0〜5点で評価する。
5. 正の効果が最大の候補を今回の小目標にする。
6. 1サイクル内で検証できる大きさに縮めて実行する。
7. テスト、計測、比較、目視など、契約した方法で検証する。
8. ログを追記し、状態と次の小目標を更新する。
9. 完了・継続・停止を判定して簡潔に報告する。

既定の評価式を使う。用途に合わない場合は契約時に重みを変更する。

```text
score = 3*期待効果 + 2*緊急性 + 2*成功確度 + 学習価値
        - 2*実行コスト - 3*リスク
```

同点なら、リスク、コスト、変更範囲が小さい順に選ぶ。評価根拠をログに残し、点数だけで機械的に決めない。

## 6. 重複実行と暴走を防ぐ

- 開始時に`status: running`と`run_started_at`を記録する。
- 前回サイクルが実行中なら、新しい変更を開始せずスキップする。
- `run_started_at`が実行間隔の2倍より古くても、処理が終わったと決めつけない。実プロセスと成果物を確認できなければ停止する。
- 同じ失敗または同じブロッカーが3サイクル続いたら自動試行を止める。
- 正の効果を持つ候補がない場合、無理に変更せず調査か停止を選ぶ。
- 公開、投稿、送信、購入、削除、本番反映、権限拡大は、明示的な事前承認なしに実行しない。
- 範囲外変更、予算超過、安全性低下、検証不能が生じたら停止する。

## 7. 定期実行を設定する

ユーザーが自動実行を選び、ループ契約を承認した後だけ設定する。

- 同じ文脈を使い続ける場合、可能なら現在のチャットへ戻る定期タスクを選ぶ。
- ホストが対応する機能を使う。CodexではScheduled task、Claudeでは利用可能なループまたはスケジュール機能を確認する。
- 機能やツールがない場合、設定済みと主張しない。実行用プロンプトと設定手順を提示する。
- 1回の定期起動では必ず1サイクルだけ実行する。
- 定期タスクから別の定期タスクや新しい長期ゴールを再帰的に作らない。
- ローカルファイルが必要なら、端末、アプリ、対象パスが実行時に利用できるか確認する。
- 完了条件に達したら新しい改善を始めず、可能なら定期タスクを停止し、最終検証結果を報告する。

定期タスクの実行プロンプトには、必ず次を含める。

```text
状態ファイルとログを読み、前回実行との重複を確認する。
確認済みの最終目標は変更せず、適応型改善ループを1サイクルだけ実行する。
候補を比較し、小さく実行し、検証し、ログとcurrent_milestoneを更新する。
完了条件、3回連続失敗、承認待ち、安全停止条件のいずれかに達したら作業を止めて報告する。
```

## 8. 報告する

各サイクルでは、現在の小目標、実行した変更、検証結果、次の小目標、完了・継続・ブロック判定だけを簡潔に報告する。

完了時は、完了条件ごとの証拠、最終成果物、残存リスク、停止した定期タスクをまとめる。
